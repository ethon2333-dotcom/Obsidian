# 向量数据库 学习笔记

> 学习定位：这是一篇**广度种子笔记**——目标是把"向量数据库"这条线从「为什么需要」一路铺到「2025-2026 在往哪走」，先搭骨架、连概念、列选项；**深度（索引数学、各库调优参数、benchmark 细节）留白给后续补充**。本文是 own-words 综合，不是选型报告；具体数字凡来自三方或厂商自报的，一律标「待核实」。

---

## 一、一句话心智模型

**向量数据库 = 给 embedding 准备的「按意义找近邻」的索引仓库。**

传统数据库按「精确匹配」（WHERE id = 5 / WHERE title LIKE '%猫%'）检索；向量库按「语义距离」（找和这句话最像的 top-k 段）检索。它解决的不是"存"，而是"在百万/十亿条向量里秒级找回最近的几个"——这件事普通数据库做不了，靠的是 ANN（近似最近邻）索引。

一句话补全记忆模型：

> **Embedding 负责把世界变成坐标，向量数据库负责在这个坐标空间里做"就近找人"。** 没有向量库，RAG / 语义搜索 / Agent 记忆就只剩"把向量塞进内存线性扫一遍"的玩具级方案。

## 二、为什么需要向量数据库

### 2.1 前置：embedding 把"东西"变成向量

文本 / 图片 / 音频经过 embedding 模型后，变成一串浮点数（如 768、1536、3072 维）。语义越相近，向量在空间里的距离越近。检索问题因此变成：**给一个查询向量，从库里找出距离最近的 k 个向量**——数学上是 k-NN（k 最近邻）。

### 2.2 为什么不能丢给普通数据库

| 需求 | 关系/文档库（B+树、倒排索引） | 向量库（ANN 索引） |
|---|---|---|
| 精确等值 / 关键词 | ✅ 强项 | ❌ 不擅长 |
| 百万级「语义最近邻」 | ❌ 只能暴力全扫 O(N) | ✅ ANN 把查询压到亚线性 |
| top-k 相似度排序 | ❌ 无距离概念 | ✅ 原生支持 |
| 高维浮点近邻 | ❌ 维度灾难 | ✅ HNSW/IVF 等专门优化 |

### 2.3 它到底在为什么场景服务

- **RAG 检索增强生成**：把知识库切块、embedding、入库，查询时取 top-k 喂给 LLM 当上下文（2026 年仍是向量库第一大生产场景）。详见 [[RAG 检索增强生成]]、[[RAG 详细学习笔记]]。
- **语义搜索 / 混合检索**：向量相似度 + BM25 关键词融合，已成 2026 生产标准。
- **Agent 记忆**：短时序工作记忆 / 情景记忆 / 长时序语义记忆，多由向量库托底（Mem0、Letta 等）。
- **多模态检索**：以图搜图、文搜视频帧、跨模态匹配（见第六节）。
- **推荐 / 去重 / 异常检测**：用户行为、交易模式编码成向量后做近邻/离群判断。

> 关键判断（PM 视角）：向量库不是"被长上下文窗口取代"——而是**演化成混合系统里的一个组件**：向量检索负责"精准定位相关片段"，长上下文负责"把命中的片段整体喂给模型做深度推理"。两者互补，不是替代。这条和 [[Context Engineering 学习笔记]] 里"什么时候检索、塞多少上下文"的取舍是同一道题。

## 三、主流方案分类（表格）

按"要不要独立部署一个向量服务"粗分三大类。**FAISS / hnswlib / annoy 严格说是库不是数据库**（ObjectBox 2026 文明确点出"Faiss is a solid library… but it is not a database"）——它们只做索引，不做持久化、CRUD、并发、元数据管理。

### 3.1 专用向量数据库（独立服务 / 托管）

| 方案 | 定位 | 自托管？ | 语言 | 一句话记忆 | 2025-2026 动向（待核实/已核实） |
|---|---|---|---|---|---|
| **Chroma** | 本地开发 / LLM 原型 | ✅ | 原 Python，2025 Rust 重写（官方称写入/查询快 4×，待核实） | "最小可跑通 RAG 的默认值" | 2025 Rust rewrite |
| **Qdrant** | 高性能、强过滤、边缘 | ✅ + 云 | Rust | "过滤即一等公民" | 2025 ACORN 算法 / MMR / 多语全文；2026 路线图 4-bit 量化；**Qdrant Edge 2026-07 发布**（见第六节，数据自报待核实） |
| **Milvus / Zilliz** | 十亿级、分布式、GPU | ✅ + 托管 | Go/C++ | "工业级大力出奇迹" | v2.6 多向量（ColBERT/CoLQwen/视频/多模态）；v3.0 目标 2026 早（官方 roadmap） |
| **Weaviate** | 多模态、模块化、企业 | ✅ + 云 | Go | "向量是对象的属性" | 被 NVIDIA / IBM / Salesforce 用于生产（厂商口径，待核实） |
| **Pinecone** | 全托管 serverless | ❌（闭源托管） | — | "不想运维就选它" | 多云（AWS/GCP/Azure），规模下 5-10ms（厂商口径，待核实） |

### 3.2 传统数据库 + 向量列（复用现有栈）

| 方案 | 底座 | 向量能力 | 适合谁 |
|---|---|---|---|
| **pgvector + pgvectorscale** | PostgreSQL 扩展 | HNSW + StreamingDiskANN | 已有 PG、中等规模、不想多养一个服务 |
| **Redis** | 内存 KV | 向量索引（HNSW/FLAT） | 本来就用 Redis 做缓存/记忆，顺带检索 |
| **Elasticsearch** | 搜索引擎 | dense_vector + 向量检索 | 已用 ES 做全文，想加语义层、做混合检索 |

> 趋势判断：向量正在从"一个独立数据库品类"变成"一个数据类型"——pgvector、MongoDB、Oracle 都把向量当原生能力加了。这**不削弱**向量检索的重要性，只是把它"下沉"成通用数据库的标准功能，类比当年 JSON 从专用 store 变成关系库标配。

### 3.3 轻量库（嵌进进程，不是服务）

| 方案 | 特点 | 用途 |
|---|---|---|
| **FAISS** | Meta 出品，IVF/PQ/量化全家桶，功能最全但要编译 | 研究 / 服务端自己包一层 |
| **hnswlib** | 极简 HNSW，省内存，端侧到 10 万向量很好用 | 端侧 / 原型 |
| **annoy** | Spotify 出品，只读、建树快 | 静态数据集、读多写少 |

> **一张图收口**：要"开箱即用的生产检索系统"→ 选 3.1/3.2；要"在 App 进程内、零运维、边缘设备里跑"→ 选 3.3 或新兴的 in-process 库（如阿里 Zvec，见第六节）。**FAISS/hnswlib/annoy 是零件，不是整机。**

## 四、索引算法（HNSW / IVF-PQ / 量化）

> 这一节只讲"心智模型 + 取舍"，数学细节（图是怎么跳的、码本怎么训的）留白。

### 4.1 HNSW（Hierarchical Navigable Small World，图索引）

- **是什么**：多层小世界图，查询时从稀疏顶层"俯冲"到稠密底层，对数级找到近邻。
- **强**：超低延迟、召回高，是低延迟检索的"黄金标准"。
- **弱**：整张图必须常驻 RAM（开销约原始向量 1.5–2.5×，2026 benchmark 口径待核实）；十亿级时内存成本吓人；建索引慢。
- **代表**：Chroma / Qdrant / Milvus / Weaviate / pgvector 默认都用它。

### 4.2 IVF-PQ（倒排文件 + 乘积量化，聚类索引）

- **IVF（Inverted File）**：把向量空间切成很多 Voronoi 格子，查询只探最近的几个格子，不扫全量 → 省内存。
- **PQ（Product Quantization）**：把向量切成子向量、各用一个"码本"压缩表示 → 进一步压内存（4–16×）。
- **强**：比 HNSW 省内存得多，适合中等/大规模。
- **弱**：要调参（nlist / nprobe / 码本大小）；召回上限略低于 HNSW。
- **代表**：FAISS 的招牌组合；Milvus 也支持。

### 4.3 量化（Compression，必备而非可选）

高维向量（2026 常见 1536–4096 维）下，**压缩不再可选**：

| 量化 | 压缩比 | 代价 |
|---|---|---|
| FP16（Float32→Float16） | 2× | 几乎无损，低风险高回报，常作默认 |
| SQ 标量量化（→ INT8） | 4× | 配合 cross-encoder 重排可补回召回损失 |
| PQ 乘积量化 | 4–16× | 引入量化误差，需调参 + 周期性重训码本 |
| 二值/二进制量化 | ~32× | 召回通常掉 5–10%（视模型与重排策略），端侧最爱 |

> **端侧为什么关心量化**：一个 1536 维 FP32 向量是 6 KB，二值量化后仅 192 字节——同样内存能塞约 32× 多的向量。这正是 2025-2026 端侧向量检索能跑起来的前提（见第六节）。

### 4.4 （补充留白）其他索引

- [ ] **DiskANN**：向量存 NVMe 而非 RAM，十亿级成本友好，查询略慢于 HNSW——什么时候该从 HNSW 切到 DiskANN？阈值与 benchmark 待补。
- [ ] **Flat / Brute-force**：小数据全扫反而最快，规模边界待补。

## 五、选型维度

给 Ethon 后续做决策时直接套用的 checklist：

| 维度 | 关键问题 | 倾向 |
|---|---|---|
| **规模** | 向量总量？百万还是十亿？ | 百万级随便选；十亿级看 Milvus / DiskANN / 托管 |
| **延迟** | 在线推理路径还是离线批处理？ | 低延迟 → HNSW + 内存；离线 → 可上磁盘索引 |
| **成本 / 运维** | 有没有人养服务？预算？ | 不想运维 → Pinecone / 云；已有 PG → pgvector；零运维边缘 → in-process 库 |
| **自托管 / 数据出境** | 数据能否出端/出公司？合规？ | 敏感/端侧 → 自托管或边缘方案（见第六节） |
| **混合检索** | 要不要关键词 + 向量融合？ | 多数文档检索要 → 看 Weaviate / ES / pgvector + BM25 / Zvec 的 RRF |
| **多模态** | 要不要图文音视频统一空间？ | 多模态 → Weaviate / Milvus 多向量 / 专用多模态 embedding |
| **Agent 记忆 / 工具化** | 要不要让 Agent 当工具调用？ | 支持 MCP 集成（如 Zvec v0.3.0）可让 Agent 直接查向量记忆——与 [[MCP 与设备侧 MCP]] 里"RAG-as-tool"思路一致 |

> **PM 一句话**：没有"最好的向量库"，只有"最匹配你架构模式的那个"。2026 年市场已分化为清晰 niche（serverless 派 / 边缘过滤派 / 工业规模派 / 多模态派），先定模式再选库。

## 六、2025-2026 进展

### 6.1 端侧 / 边缘向量检索（重点，与 Ethon 的端侧 Agent 主线强相关）

2025 下半年到 2026，端侧向量检索从"理论/实验"走向"可部署"，驱动力并行发生：

- **硬件**：2025 起旗舰手机普遍带 NPU（Apple A18/A19 Pro、Snapdragon 8 Elite、Google Tensor G4/G5），专门加速向量检索依赖的点积/矩阵运算。
- **模型变小变好**：EmbeddingGemma（308M）、Qwen3 Embedding（0.6B）等小 embedding 模型在 MTEB 上有竞争力，只占移动端内存一小部分。
- **量化成熟**：二值量化把向量压 ~32×，配合重排召回损失可控。
- **合规与成本推力**：EU AI Act（第 5 条 2025-02 生效、2026-08-02 全面执行，待核实具体条款时间）+ 云成本上涨，把向量管理往端上推。

具体动向（诚实标注来源性质）：

- **Qdrant Edge**（2026-07-23 发布，自报 benchmark）：声称端侧 0.1ms vs 云端 52ms、520× 延迟下降，"Same retrieval engine. Same API. Same queries. Just no network hop." → **数字为厂商自报，待核实**。意义在"云/边同一套 API，部署变成配置而非架构变更"。
- **Zvec**（阿里通义实验室，基于 Proxima 引擎）：定位"向量数据库的 SQLite"，进程内、无 daemon、无网络；2025-12 首发，v0.5.0（2026-06）加全文+混合查询+DiskANN；v0.3.0 起支持 **MCP 集成**（Agent 直接查向量记忆）；Dart/Flutter SDK 支持 Android/iOS 端侧。Stars / QPS / 7× Pinecone 等数字为自报，**待核实**。
- **ObjectBox 等移动端向量方案**：强调"真·端侧"要持久化 + 向量/元数据混合 + 移动 SDK + 增量 CRUD + 离线 + 选择性同步——指出"ANN 索引数学是简单部分，难的是移动端生命周期/发热降频/加密存储/同步"。

> **PM 判断（连端侧 MCP 主线）**：端侧向量检索 = 设备侧 Agent 的"本地记忆层"。它和 [[MCP 与设备侧 MCP]] 里讲的"执行侧本地化"是同一条逻辑——**数据不出端、无网络往返、无外部服务**。但要注意：和 MCP 一样，"检索在端侧"≠"理解在端侧"，Planner 在云上时端到端延迟仍被云上那一跳支配。这条留作待解问题。

### 6.2 多模态向量

- **统一多模态 embedding**：Amazon Nova Multimodal Embeddings（2025 末）号称单一模型覆盖文本/文档/图/视频/音频，支持跨模态检索；Google Vertex AI、Voyage AI 也有同类能力（厂商口径，待核实）。
- **CLIP / ImageBind**：把图文（甚至音视频）压进同一向量空间，实现"以图搜文""文搜视频帧"。2023 实验、2026 已成生产模式。
- **2025 创新点：promptable embeddings**（提示条件化向量）——同一模型能按指令产出任务专用表示。
- **专用库跟进**：Milvus 路线图把"下一代多模态数据库"作为主线，v2.6 引入 Tensor/StructList 类型支持多向量（ColBERT/CoLQwen/视频/多模态）；Weaviate 本就主打多模态。
- **企业侧**：Teradata Enterprise Vector Store（2026-03 发布、2026-04 GA）加多模态 + agentic 能力（文本/图/音频，维度到 8K，待核实）。

> **为什么多模态绕不开向量库**：你没法把 1 万张商品图塞进上下文窗口。跨模态检索本质是"把不同模态映射进同一坐标空间后做近邻"——这正好是向量库的本职。

### 6.3 （留白）其他值得追的方向

- [ ] **RAG-augmented long context**：先向量定位、再长上下文整体推理的混合范式，benchmark 是否真在大多数场景双赢？待补一手数据。
- [ ] **Agent 记忆治理**：记忆"是否可边界化、可审计、可安全"已从"能不能用"变成"敢不敢上生产"的核心问题（IBM/AWS 提出的情景/语义/程序三类记忆）。具体治理方案待补。

## 八、待解问题

- [ ] **十亿级场景 HNSW → DiskANN 的切换阈值到底在哪？** 已知 HNSW 内存 1.5–2.5× 且十亿级昂贵，DiskANN 存 NVMe 成本友好但略慢——但"具体多少向量量、什么 QPS 该切"缺一手 benchmark，待补。
- [ ] **端侧向量检索的"真·离线"成立条件？** 和 [[MCP 与设备侧 MCP]] 里端侧 MCP 的账一样：端侧嵌入+端侧索引+端侧生成三者齐才有离线；被检索的原始内容若需联网拉取，照样离不了线。边界清单待补。
- [ ] **Qdrant Edge 的 520× / 0.1ms 自报数字能否被独立复现？** 厂商自报、The Agent Times 已注明未能从一手源独立验证；作为选型依据前需一手 benchmark。
- [ ] **in-process 库（如 Zvec）的多进程/分布式短板如何补？** 架构上"单进程写、多进程只读、不可跨网络"——什么规模该从 Zvec 迁到 Milvus/Qdrant？迁移成本待评估。
- [ ] **多模态 embedding 的"跨模态对齐质量"如何评测？** 文搜图、图搜文的实际召回差异、不同模态在同一空间的纠缠问题，缺系统性评测笔记。
- [ ] **量化（尤其二值）带来的召回损失，在不同 embedding 模型上差异多大？** 已知典型 5–10%，但是"哪些模型掉得多、重排能补回多少"待一手数据。
