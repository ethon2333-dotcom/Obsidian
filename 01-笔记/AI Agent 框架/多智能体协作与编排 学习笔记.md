# 多智能体协作与编排 学习笔记

## 学习定位
多智能体协作与编排（Multi-Agent Orchestration）研究的是：当单一 agent 的能力或上下文窗口不够用时，如何把复杂任务拆给多个 agent 分工协作完成——重点在「模式」与「框架」，而不是单个 agent 的内部循环。它是 [[AI Agent 框架 MOC]] 下与 [[Loop Engineering 循环工程]]（单 agent 循环）并列的另一条主线：Loop Engineering 讲「一个 agent 怎么转圈」，本篇讲「多个 agent 怎么组队」。实践落地的代码骨架多可参考 [[LangGraph 概览]] 的图式编排，但本篇不重述其 API。

> **心智模型：多智能体像一支分工的团队——有人当项目经理派活（协调者）、有人当专家攻坚（worker）、有人当审稿人挑错（critic），比一个人单干覆盖更全、并行度更高；但人越多，沟通成本和「各干各的」冲突也越容易被放大。**

## 一、概念定义
| 术语 | 定义（核实口径） | 代表 / 备注 |
| --- | --- | --- |
| Multi-Agent System (MAS) | 多个由 LLM 驱动的 agent，在循环中自主调用工具并相互协作完成任务的系统（Anthropic 将其定义为「LLM in a loop calling tools, collaborating」） | 区别于单体 pipeline，强在并行探索与关注点分离 |
| Orchestration（编排） | 谁来把任务拆给谁、按什么顺序、结果如何汇总的调度层 | 可由「中心协调者」或「框架运行时」承担 |
| Role Decomposition（角色分解） | 把任务按职责拆成不同角色 agent（如研究员 / 程序员 / 审稿人） | CrewAI 的核心隐喻；降低单 agent 认知负担 |
| Lead / Manager / Supervisor Agent | 负责规划、派活、汇总的主 agent | Anthropic Research 的 LeadResearcher；LangGraph supervisor |
| Subagent / Worker | 被派活、独立上下文窗口并行执行的专家 agent | Anthropic 研究中 10+ 子代理并行检索 |
| Shared Memory（共享记忆） | 跨 agent 复用的状态/上下文（如计划、线索） | Cognition 强调须「共享完整 trace」而非压缩摘要 |

## 二、常见协作模式
| 模式 | 做法 | 优点 | 代价 / 局限 |
| --- | --- | --- | --- |
| Orchestrator-Worker（协调者-执行者） | 主 agent 拆解任务并并行派给子 agent，最后汇总 | 并行度高、覆盖面广（Anthropic 实测研究任务 +90.2%） | token 消耗约 15× ；子 agent 易重复/遗漏 |
| Supervisor（监督者） | 一个 supervisor 动态选下一个发言者/执行者 | 可控、适合层级化团队 | 监督者成瓶颈；选人逻辑需调 |
| Debate-Critique（辩论-批判） | 多个 agent 互相反驳/审稿，取更优解 | 提升正确率、抗幻觉 | 轮次多、成本高、收敛慢 |
| Role-Playing（角色扮演） | 每个 agent 给定角色/背景故事协作 | 直观、易映射业务流程（CrewAI） | 强耦合任务不灵活 |
| Hierarchical（层级） | 树状：根 agent 委派多层子 agent | 适合复杂多步流水线（Google ADK 原生树） | 层级深则调试难 |
| Blackboard（黑板） | 共享「黑板」空间，agent 读写中间结果 | 松耦合、便于异步协作 | 需解决写冲突与一致性；工业落地较少 |

## 四、通信与协调（agent 之间怎么对话）
| 机制 | 做法 | 优点 | 代价 / 局限 |
| --- | --- | --- | --- |
| 消息传递（Message Passing） | agent 间异步发消息 / handoff 交接（AutoGen 事件驱动、Swarm handoff） | 解耦、支持分布式 | 消息追踪与回放成本高 |
| 共享记忆（Shared Memory） | 共用上下文/计划/黑板（Cognition 主张共享完整 trace） | 减少「传声筒效应」 | 上下文膨胀；跨 agent 一致性难 |
| A2A（Agent2Agent Protocol） | Google 发起的 agent 间标准：JSON-RPC 2.0 + SSE，Agent Card 发现、Task 有生命周期 | 跨厂商/跨框架互通，补 MCP 之不足 | 2025-04 才发布，生态早期 |
| AGP（Agent Gateway Protocol） | AGNTCY（Cisco + LangChain 等）在 Linux Foundation 下的企业级网关协议（类 gRPC、路由/目录） | 面向跨组织部署的「代理互联网」 | 愿景大、落地与治理挑战高 |

> A2A 与 MCP 互补：MCP 是「agent 连工具」（agent-to-tool），A2A 是「agent 连 agent」（agent-to-agent）。更全协议版图见 [[Agent 协议生态 学习笔记]]。

## 五、2025–2026 进展（广度速览）
| 方向 | 关键事实（核实） | 含义 |
| --- | --- | --- |
| A2A / AGP 协议化 | A2A 于 2025-04 由 Google 开源，2025-06 捐给 Linux Foundation，2026-03 出 v1.0；AGP 归入 AGNTCY（Linux Foundation） | 多 agent 互通从「各写各的」走向开放标准，是编排可规模化的前提 |
| Coding 多 agent | 到 2025 末，Claude Code / Codex / Devin / Jules 等以「初始化 agent + 多个 coding subagent（各自独立上下文窗口）」组织长任务；并出现 Developer/QA/Security/Architect 多角色团队编排 | 多 agent 在「高并行、弱耦合」的编码任务先跑通，但 CE 仍强调单线程 + 上下文压缩更稳 |
| Agent 浏览器 / 电脑操作的多 agent | Operator、Claude Code、Codex（云沙箱）等把「电脑操作」作为 agent 工具；多 agent 在云端 VM / worktree 隔离下并行执行 | 端侧/本机的「多 agent 操控 UI」成为可能性的技术预演（见第六节） |
| 反方声音 | Cognition（Devin）2025-06《Don't Build Multi-Agents》：naive 多 agent 违反「共享完整上下文」「动作携带隐式决策」两原则，易冲突 | 多 agent 不是银弹——任务耦合度高时应先用单 agent + 上下文工程（[[Context Engineering 学习笔记]]） |

## 六、对 OS PM 的意义
对 Android OS PM 而言，多智能体编排预示着「端侧一支 AI 团队」的可能：一个系统级协调者（见 [[端侧意图框架 学习笔记]]）把用户意图拆给「设置助理 / 通知管家 / 文件整理 / 跨 App 自动化」等角色 agent，各自调用设备能力并汇总结果——这正是 [[应用层 Agent 框架 vs 系统级意图框架 对照]] 里系统级一层的落地形态。结合 [[手机AI智能体知识库]] 的设备场景，编排模式能显著提升复杂跨 App 任务的覆盖度。

但复杂度同样被放大：编排开销与 token/算力成本在端侧更敏感（多 agent 动辄 15× 消耗，详见 [[Context Engineering 学习笔记]] 的成本视角）；错误会在 agent 间传播、上下文膨胀吃掉有限内存；且「哪个 agent 干了什么」需要可审计——这直接关联 [[工具调用安全 学习笔记]] 与权限边界。因此端侧多 agent 的优先级应是：先用单 agent 上下文工程解决大多数任务，仅在「高并行、弱耦合、价值足够高」的场景（如深度研究、批量整理）引入编排，并配套评测（[[Agent 评测与基准 学习笔记]]）与可追溯机制。

## 待解问题（深度留白）
- [ ] 端侧多 agent 的「协调者」该由系统框架常驻，还是按需唤起？功耗/内存预算怎么定？
- [ ] A2A 在端侧（本地 agent 互操作）是否适用，还是需要轻量版协议？
- [ ] 多 agent 错误传播如何界定的「责任链」，用户出问题找哪个 agent？
- [ ] 弱网/离线时，编排的降级策略（中心协调者挂了怎么办）？
- [ ] 如何评测「编排质量」本身（不只评单 agent 输出），有无像 LLM-as-judge 的编排判官？
- [ ] Role decomposition 在 OS 场景该按「App 边界」还是「能力边界」拆更合理？
- [ ] 与 [[RAG 检索增强生成]] 结合时，多个 agent 共享同一检索索引还是各自索引，冲突如何合并？
