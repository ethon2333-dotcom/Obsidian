# 多智能体编排的容错与错误传播隔离 学习笔记

**心智模型一句话**：多智能体系统里，一个 worker 的错误不是「就地停止」，而是沿着调用链被下游当作「可信输入」继续放大——容错与隔离的目标，是把「故障的传播半径（blast radius）」从「全链路雪崩」压到「单点可丢弃」。容错管「怎么不崩」，隔离管「崩了也不传染」。

> [!note] 与邻笔记的边界
> 本文聚焦**容错机制 + 隔离边界 + 错误传播阻断**，刻意区别于 [[智能体的可观测性与分布式追踪 学习笔记]]（那篇讲 trace/span 如何看见传播，本文讲如何**挡住**传播）。编排模式本身见 [[多智能体协作与编排 学习笔记]]，安全护栏设计模式见 [[Agent 安全护栏模式库 学习笔记]]。

## 一、定义（广度速览）

- **Cascading Failure（级联失败）**：OWASP ASI08 将其定义为「单点故障跨自主 agent / 工具 / 工作流传播并复合，最终放大成系统级损害」。重点在**传播路径**而非故障起源（起源通常归到别的条目，如注入 ASI01、记忆投毒 ASI06）。
- **Error Propagation / Blast Radius（错误传播 / 爆炸半径）**：错误被读它的下游 agent 当作可信输入继承，hop-to-hop 累积漂移；半径从「结构化（写进了编排契约）」到「沿通信边方向性扩散」到「逃逸到用户输出边界」。
- **Isolation（隔离）**：把故障/越权限制在某个执行边界内，边界外的 agent / 租户 / 会话看不到、也读不到它。
- **Fault Tolerance（容错）**：在故障已发生的前提下，让系统仍能给出「降级但正确 / 可恢复」的结果（重试 / 熔断 / 降级 / 超时 / 补偿）。

## 二、分类（错误类型 × 隔离粒度）

### 错误类型（MAST 实证分类 + OWASP 口径，广度对照）

| 错误大类 | 代表模式 | 传播方式 | 主要阻断杠杆 |
|---|---|---|---|
| 系统设计与规格 | 违背任务/角色 spec、步骤重复、丢失对话历史、无终止意识 | 坏指令/丢上下文被所有派生 agent 继承，结构性反复出现 | 修编排契约；强制终止条件与显式 history 交接（**Contain，非 Recover**） |
| 智能体间错位 | 不澄清、任务脱轨、信息 withholding、忽略输入、推理-动作不匹配 | 一个 agent 的部分/错误消息成为另一个的「可信输入」，小漂移逐跳复合 | 类型化校验 handoff；提交前澄清闸门；peer 交叉检查（边缘 Contain） |
| 验证与终止 | 过早终止、无/不全验证、错误验证 | 系统在错误被捕获前就停/批准，错误「带成功标签逃逸到输出」 | 独立验证者（producing agent 不能推翻）；出口硬接受闸门（只能 Gate 出口） |
| 放大类（非根源） | 回声室、权威混淆、资源死锁、提示注入放大、上下文碎片化、成本爆炸、可调试性坍塌 | 让上述三类更隐蔽或更强 | 见下文容错模式 |

> 关键洞见（latenteval）：**系统设计与智能体间错位类要「Contain 在源头」，验证类只能「Gate 在出口」**；单纯 Recover（重跑失败步）对前两类无效——因为被污染的状态已被下游读走。

### 隔离粒度（从粗到细）

| 粒度 | 机制 | 代表技术 | 取舍 |
|---|---|---|---|
| 租户级（Tenant） | 按用户/组织切索引、行级安全、检索元数据过滤 | 每租户独立向量库、RAG 行级过滤 | 解决「A 看不到 B 的数据」，但**管不了同一用户的会话间泄漏** |
| 会话级（Session） | 每会话独立上下文句柄、内存分区 | Session-scoped credentials、对话隔离 | 比租户细，但长会话内仍可能上下文混杂 |
| 事务/调用级（Transaction / per-invocation） | 每次调用 fresh context、写操作在事务末校验提交 | Google Agent Sandbox「每任务一个沙箱」、per-process 隔离 | **最推荐**：让「坏」在结构上不可表达（OS 类比：per-process address space） |
| 进程级沙箱 | LSM（Landlock）、只读 rootfs、空网络命名空间 | Linux Landlock LSM、gVisor 用户态内核 | 近乎零开销，LLM 推理延迟敏感场景的平衡点 |
| 容器级 | 硬件辅助隔离、eBPF  syscall 过滤、OPA 策略注入 | Kata Containers（轻量 VM）、Docker + 策略引擎 | agent 工具调用默认安全域 |
| 微虚机级（microVM） | 内核级隔离、VM 级隔离但容器级速度 | Firecracker（E2B）、gVisor、Kata | 多租户不可信代码执行最强边界，毫秒级启动 |
| 指令级 | capability-based、显式许可执行 | WebAssembly（WASM） | 浏览器/边缘原生、低开销、细粒度 |

## 三、主流容错方案（点到为止）

| 模式 | 一句话 | 适用 | 注意点 |
|---|---|---|---|
| 重试（Retry + 指数退避 + jitter） | 瞬时错误（限流、短断、超时）重试，避免惊群 | 工具/API 调用层 | **只对瞬时错有效**；对「幻觉」类语义错重跑还是同一个错 |
| 超时（Timeout） | 每个 task 都加超时 + 显式 `input-required` 态 | 防资源死锁（A 等 B、B 等 A） | 无超时则一个等待 agent 可阻塞全系统 |
| 熔断（Circuit Breaker） | 错误率超阈值则开路，阻断后续调用一段时间，给 fallback 留空间 | 防成本爆炸 + 防反馈环 | LangGraph 0.2.x 无内建，需手动包 `agent.invoke()`；用「时间窗内失败率」而非墙钟计数 |
| 降级 / Fallback | 专用 agent 失败 → 切更简单 agent / 更低模型档 / 主动缩减输出 | 保「诚实的有限输出」优于级联错判 | 优于沉默返回垃圾 |
| 补偿事务（Saga / Compensation） | 已提交步骤用反向操作回滚，而非分布式事务 | 多步有副作用的写操作 | agent 写操作特别需要，因无传统 2PC |
| 隔离沙箱 | 故障/越权锁在 per-transaction 边界内，结构不可越界 | 代码执行、computer use、不可信工具 | 见第二节粒度表 |
| 类型化错误边界（Typed Schema as Boundary） | 输出强制 Pydantic/JSON Schema/A2A artifact，不符合就拒收而非透传 | 所有 handoff | 同时是错误边界 + token 压缩点（绝不把子 agent 全文 transcript 传给 lead） |
| 单写多读（Single-writer / Read fan-out） | 多 agent 读/提议，只有一个 agent/pipeline 阶段提交 | 防并发写共享状态死螺旋 | Anthropic「多 agent 读扇出稳健、写扇出脆弱」核心原则 |

## 四、2025-2026 进展（广度扫描）

- **OWASP Agentic Top 10 把 ASI08 Cascading Failures 单列**（GenAI Security Project，2025-12 前后发布，待核实）——首次把「传播放大」作为独立风险类，明确借用 SRE 的电路熔断 / 重试预算 / deadline / load shedding / 配额来拦 agent 反馈环。
- **MAST 实证分类**（Cemri et al., arXiv:2503.13657, NeurIPS 2025 spotlight）：基于 150 条专家标注 + 1,642 条 trace 给出首个多 agent LLM 失败实证分类，并区分「Contain vs Recover」。
- **Anthropic 立场演进**：「Don't Build Multi-Agents」(2025-06) → 「Multi-Agents: What's Actually Working」(2026-04)，核心结论收敛为「读扇出稳健、写扇出脆弱 → 单写者原则」。
- **信任即一等安全变量**：Trust-Vulnerability Paradox（Springer 2026）/ 分布式信任传播模型 DTPM / Guardian-Agents（MNI 最小必要信息闸门）用 MAS-FIRE 故障注入框架验证——把「静默错误传播」通过可撤销、可度量信任建模压住（OER 降 80%+，放大倍率从 17.2× 压到 4.4×，待核实具体数字）。
- **内核级隔离成为趋势**：Google 在 KubeCon NA 2025 发布 **Agent Sandbox**（K8s 原语，gVisor + Kata Containers，每任务一个隔离沙箱，预暖池 sub-second）；E2B（Firecracker microVM）、AgentBound（MCP 服务端 Docker 沙箱 + 声明式策略）、WASM 指令级隔离并行发展。
- **框架容错能力分化**（见第五节）；「compounding failure 概率」被反复点名（0.95^N 问题：20 步 ×95% 单步可靠 ≈ 36% 端到端，待核实）。
- **NIST AI 系统安全指南**（SP 800-218A 补充草案，2025，待核实）明确：agent 安全须从**计算运行时层**起步，而非仅靠应用层鉴权。

## 五、代表框架的容错/隔离机制（横向速查）

| 框架 | 容错机制 | 隔离机制 | 备注 |
|---|---|---|---|
| **LangGraph** | 节点级 `RetryPolicy`（指数退避 + jitter + 错误类型过滤）；Super-step 隔离（节点失败丢弃 pending update，base checkpoint 不污染）；子图封装（独立状态 schema + 错误边界） | 检查点（PostgresSaver 等）做状态回滚；`interrupt_before` 做 HITL | `0.2.x` 无内建 circuit breaker，需手包 |
| **AutoGen v0.4 (AG2)** | Actor 崩溃隔离（actor 各自执行上下文，一 agent 未捕获异常不直接拖垮兄弟）；Dead-letter 队列（投递失败 / 未处理异常离线排查）；Supervisor 路由（worker 超时未响应则派替代任务） | 异步 actor 模型天然解耦计算节点 | ⚠️ 有源称 Microsoft 已于 2026-10 前后归档 AutoGen，待核实 |
| **CrewAI** | Task 级 retry 守卫（schema 校验失败自动 reprompt + 附验证错误 trace）；层级 fallback（worker 反复失败，manager 重派任务 / 调约束） | 角色层级、任务产物（artifact）同步传递 | 角色描述需多 agent 上下文常驻内存，RAM 占用偏高 |
| **LlamaIndex Workflows** | Async 异常传播（标准 asyncio task group，`try/except`）；动态错误事件（自定义 `ValidationErrorEvent`/`RetryEvent` 回路由自纠） | 作用域 `ctx` KV 存储；事件驱动 step 分发 | 重 Python 原生 async |
| **Google Agent Sandbox** | （基础设施层）预暖池降低冷启；Pod Snapshots 秒级恢复 | gVisor + Kata 每任务内核级隔离、受限网络 | K8s 原语，CNCF 开源 |
| **E2B / AgentBound / WASM** | — | Firecracker microVM / Docker 策略沙箱 / 指令级 capability | 不可信代码执行与 MCP 服务端隔离 |
