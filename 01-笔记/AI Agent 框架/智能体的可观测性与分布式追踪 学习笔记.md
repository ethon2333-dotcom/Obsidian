**心智模型：把一次"多步、多工具、多智能体"的调用展开成一条可追踪的 trace，每个环节是一个 span，才能定位卡点、成本与失败。** 本文刻意聚焦"分布式追踪 / trace 跨进程跨 agent 传播 / span 关联"这一更窄角度，与 [[Agent 可观测性 LLM Observability 学习笔记]]（那篇聚焦 metrics/logging/eval 面板等泛 observability）互补分工；也区别于 [[模型服务化与 LLM 网关 学习笔记]]（网关层埋点，本篇是 agent 级 tracing）。

## 为什么 Agent 比普通 LLM 更需要 tracing

| 维度 | 普通单 LLM 调用 | 多步 Agent |
|---|---|---|
| 调用结构 | 1 请求 1 响应 | 数十次 model/tool 调用嵌套、分支、循环 |
| 失败藏匿点 | 多在最终输出（HTTP 级即可见） | 常藏在某一步中间（选错工具/检索错/空转循环），最终回答仍"像对的" |
| 成本归因 | 单调用可算 | 自主决定调用次数/工具/外部 API，需 per-trace 归因到 user/模型/agent |
| 调试手段 | 日志足够 | 日志是平的事件，无法重建因果链；无 trace 只能手工重放整段 session |
| 跨进程 | 通常单服务 | supervisor→worker 跨服务/跨框架，span 不关联即 5 段独立日志 |

## 核心概念

| 概念 | 含义 | 在 Agent tracing 中的用法 |
|---|---|---|
| Trace | 一次端到端请求形成的 span 树 | 一条用户任务 / 一个 session 对应一个 trace |
| Span | 单个计时操作（一次 LLM 调用、一次 tool 调用、一次子 agent 委托） | 每个 agent step = 一个 span，嵌套表达因果 |
| Context propagation | 跨服务/跨 agent 边界传递 trace 上下文 | 用 W3C Trace Context（traceparent / tracestate）头在 HTTP/MQ 中注入与提取 |
| Baggage | 跨边界透传的自定义键值元数据 | 携带 user_id、tenant、agent_role 等用于归因与路由的属性 |
| Semantic conventions | 标准化的 span/属性命名 | OTel GenAI 约定 `gen_ai.*`（见下） |

OTel GenAI 关键属性：`gen_ai.request.model`、`gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.operation.name`（枚举含 `chat`、`create_agent`、`invoke_agent`、`invoke_workflow`、`plan`、`execute_tool`、`retrieval`）、`gen_ai.tool.name`、`gen_ai.agent.name`。MCP 也有专属约定：`mcp.client` / `mcp.server` span。

## 主流方案与工具

| 类别 | 代表 | 一句话定位 |
|---|---|---|
| 标准/语义约定 | OpenTelemetry GenAI Semantic Conventions、OpenInference（Arize） | 跨厂商的 span/属性词汇表；OTel 已成事实标准底座 |
| 开源 Trace 后端 | Jaeger、Zipkin、Grafana Tempo、Aspire Dashboard | 接收 OTLP，渲染 waterfall / trace 树 |
| 开源 AI 工程平台 | Langfuse、Arize Phoenix、Helicone、AgentOps | tracing + eval 闭环；均消费 OTLP，**Langfuse 的 `/api/public/otel` 直接吃任意 OTel trace** |
| 框架/厂商托管 | LangSmith（LangChain）、Datadog LLM Observability、Traceloop OpenLLMetry | LangSmith 强在 LangGraph state diff/replay；OpenLLMetry 做无侵入自动埋点；Datadog 借既有 infra 可观测能力 |
| 自动埋点库 | Traceloop OpenLLMetry、框架内置 OTel（Pydantic AI、smolagents、Strands、CrewAI 部分） | 拦截 LLM/工具调用自动发 span，降低接入成本 |

跨 agent / 跨进程关联要点：supervisor 建 root span 并传播 trace 上下文 → worker 提取后建 child span 引用同一 trace_id → 所有 span 落入同一 trace。MCP 调用通过在 `_meta` / 协议头注入 trace context，把 client/server 两段 span 嵌套而非各成孤儿 trace。

## 2025-2026 进展（广度要点，点到为止）

| 进展 | 状态/说明 |
|---|---|
| Agent 语义约定成型 | `invoke_agent` / `execute_tool` / `create_agent` / `invoke_workflow` 等 span 类型落地；专属仓库 `semantic-conventions-genai`（2026 从主仓库拆出） |
| 稳定性分级 | `gen_ai.client`（model 调用）span 已 stable；`gen_ai.agent` span 截至 2026 仍标记 **Development（非 stable）**，属性名可能变动 → 需 pin 版本 |
| MCP 追踪打通 | MCP 专属约定（`mcp.session.id`、`mcp.method.name` + W3C Trace Context）解决"agent 与 MCP server 两段孤儿 trace"问题 |
| 多 Agent 调用图可视化 | Langfuse graph view / LangGraph 自动渲染 agent graph；跨服务靠 trace_id 拼接成单一 trace 树 |
| 与 eval 联动 | trace → eval 闭环（Langfuse 把失败 trace 直接转成回归测试集；span 挂 outcome 评分后做 cohort 分析） |
| 抽样策略收敛 | 反对 head-based 抽样；主张 tail-based：错误/慢/超 eval 阈值 100% 保留，happy-path 抽样 |
| 未解问题（研究侧） | 千 span trace 中定位"唯一因果决定性事件"的反事实重放（arXiv:2606.14805）、"仅最终文本留存"归因难题（arXiv:2603.17445） |

## 代表产品与开源（速查）

- 开源优先：Langfuse（自托管+数据驻留）、Arize Phoenix（OpenInference，eval 深度）、Helicone、AgentOps、Traceloop OpenLLMetry、Jaeger/Tempo/Aspire Dashboard。
- 厂商托管：LangSmith、Datadog LLM Observability、New Relic（2026 推 AI agent 平台 + OTel 舰队管理）、Elastic、Honeycomb（wide events 统一模型）。

## 待解问题

- [ ] 当 `gen_ai.agent` 语义约定仍 Development、各框架命名尚不统一时，生产系统应如何 pin 版本并做向前兼容的埋点抽象层？
- [ ] 跨团队多项目（supervisor 与 sub-agent 分属不同团队/项目）下，如何既保端到端 trace 连续又隔离各团队可见范围？
- [ ] 长时 / 长 horizon agent（trace 达数十万 observation）如何在不丢关键失败信息的前提下做摘要聚合与成本控制？
- [ ] 端侧 / on-device agent 的 trace 能否与云端 OTel 后端对齐，还是另走轻量本地 trace？
