# 📑 OS 产品经理：端侧 3B 模型内存预算（Memory Budget）推演

> [!note] 笔记定位
> 规划端侧 AI 功能（长文档总结、全局搜索）时，PM 不能只说「支持 32k 上下文」，必须精确推算不同上下文下的 **PSS 峰值**。以 3B 级 SLM（Llama-3.2-3B / Qwen2.5-3B 架构）为基准。

## 一、推演基准参数（固定假设）
| 参数 | 符号 | 数值 | 备注 |
| --- | --- | --- | --- |
| 总参数量 | N | 3.21 B | INT4 部署 |
| 网络层数 | L | 28 | Transformer Layers |
| Query 头数 | H_Q | 24 | |
| KV 头数 | H_KV | 8 | GQA 3:1 |
| 单头维度 | d_head | 128 | 3072/24 |

## 二、四大组件公式
`Total RAM = Model Weights + KV Cache + Activations + System Overhead`

### 1. 模型静态权重
- FP16 原始：3.21B × 2B ≈ **6.42 GB**（移动端无法常驻）
- INT4（含 Scales/Zeros）≈ 0.56 Bytes/param → **≈ 1.80 GB**（固定，不随上下文变）

### 2. 动态 KV Cache（关键变量）
`KV per Token = 2 × L × H_KV × d_head × Bytes = 2×28×8×128 = 57,344 元素/Token`
- FP16 (2B)：**0.112 MB/Token**
- INT8 (1B)：**0.056 MB/Token**
- INT4 (0.5B)：**0.028 MB/Token**

### 3. 运行激活值 Activations
- 未优化 Full Prefill：随序列长度暴涨
- Chunked Prefill + FlashAttention（Chunk=512）：峰值锁死 **200~300 MB**，不随 8k/32k 膨胀

### 4. 系统 Overhead（固定 ≈ 400 MB）
- NPU/GPU 驱动 Workspace & DMA Scratchpad：~250 MB
- AI Runtime + Context Engine：~100 MB
- PagedAttention 页表：~30~50 MB

## 三、完整推演表（PSS 峰值）

### 1. 传统未优化（FP16 KV + 无 Chunked Prefill）
| 组成 | 2k | 8k | 32k |
| --- | --- | --- | --- |
| 权重 INT4 | 1.80 | 1.80 | 1.80 |
| KV FP16 | 0.23 | 0.92 | **3.67** |
| 激活 Full Prefill | 0.35 | 1.20 | **4.80** |
| Overhead | 0.40 | 0.40 | 0.40 |
| **PSS 总峰值** | **2.78 GB** | **4.32 GB** | **10.67 GB** (OOM) |

### 2. OS AI Runtime 优化（INT8 KV + Chunked Prefill + PagedAttention）
| 组成 | 2k | 8k | 32k |
| --- | --- | --- | --- |
| 权重 INT4 | 1.80 | 1.80 | 1.80 |
| KV INT8 | 0.11 | 0.46 | **1.84** |
| 激活 Chunk=512 | 0.25* | 0.25* | **0.25*** |
| Overhead | 0.40 | 0.40 | 0.40 |
| **PSS 总峰值** | **2.56 GB** | **2.91 GB** | **4.29 GB** (12GB手机可承受) |

### 3. 极致省电（INT4 KV + Token Eviction 50%）
- 2k → **2.50 GB** ｜ 8k → **2.68 GB** ｜ 32k(等效16k) → **3.35 GB**

## 四、PM 决策与规格结论
1. **32k 必须 Chunked Prefill**：否则激活 4.8GB 超模型本身，致命 OOM。强制拆 512/1024 Token Chunk。
2. **8GB RAM 手机极限 = 8k 上下文**：系统基底占 3.5~4.0GB，AI 安全配额 **3.0 GB**。优化后 8k 占 2.91GB 踩线；硬跑 32k 须开 Token Eviction 压 KV < 1GB。
3. **12GB/16GB 才具长文本全局 Agent 体验**：允许多 32k 3B 模型与相机/游戏后台保活。

## 深化补充

### 一句话心智模型

> **权重是房租（固定，签了就得付），KV Cache 是水电（用多少付多少，但会随上下文线性涨），激活值是押金（一次性尖峰，优化好了可以封顶）。**

这个类比对我最有用的一点是：**它立刻说明了三者的治理手段为什么不同。**
- 房租只能靠**换小房子**（量化、换更小模型）；
- 水电只能靠**少用**（剪枝、驱逐、缩上下文）；
- 押金可以靠**分期**（Chunked Prefill——把一次性尖峰摊成多次小额）。

原文表 2 里最漂亮的一个数字就是押金这一格：**激活值从 4.80 GB 压到 0.25 GB，而且不随上下文增长**。这是三项优化里 ROI 最高的一个——**Chunked Prefill 几乎是纯赚**，代价只是首 token 稍慢一点。

### 这张表真正的用法：反过来算

原文是"给定上下文，算内存"。但我在实际工作里遇到的问题永远是反的——**"这台机器我能承诺多长上下文？"**

把表 2 倒过来读，得到一张我能直接用的规格表：

| 机型 RAM | 系统基底 | AI 安全配额 | **能承诺的上下文** | 备注 |
|---|---|---|---|---|
| 8 GB | 3.5–4.0 GB | ~3.0 GB | **8k（2.91 GB，踩线）** | 32k 需开 Token Eviction，且有召回损失 |
| 12 GB | ~4.0 GB | ~5 GB | **32k（4.29 GB）** | 可与相机/游戏共存 |
| 16 GB | ~4.0 GB | 更宽裕 | 32k 且余量充足 | 长文本 Agent 的舒适区 |

**"8GB 手机的上限是 8k"这一条，是我从这篇里带走的最实用的一句话。** 因为它能直接转化成产品决策：

- 如果我的功能需要 32k（比如"总结整个聊天记录"），那它**在 8GB 机型上就不该出现**，而不是"出现但很慢"。
- 分档的界线不是营销划分，是**物理约束**。这让"为什么低端机没有这个功能"从一个尴尬问题变成一个可解释的技术事实。

### 一个我要警惕的陷阱

这套推演有一个很强的隐含假设：**AI 独占它的配额**。但真实场景里 [[OS-PM-端侧大模型系统级挑战]] 已经指出——前台游戏、相机会来抢。

所以表里的 "8GB 手机 8k 踩线（2.91/3.00 GB）" **实际上是不安全的**。踩线意味着：只要前台多要 100MB，要么 AI 被杀（3-10s 重载），要么前台被杀（用户直接看到闪退）。

**我的判断：产品规格不应该按"理论上限"定，应该按"理论上限 × 0.7 左右的安全水位"定。** 也就是 8GB 机型实际能承诺的可能只有 4k-6k。⚠️ 这个 0.7 的系数是我拍的，**待核实**是否有行业惯例或内部标准可参照。

### 待解问题

- [ ] "AI 安全配额 3.0 GB"这个数是怎么来的？是行业惯例、内部标准，还是这篇的作者推的？**如果是推的，那整张表的结论都建立在一个未经验证的假设上**，得找一手数据核实。
- [ ] Token Eviction 会"丧失被驱逐 token 的精准回忆"。那**对用户来说这表现为什么**？是"总结漏了中间一段"还是"问细节答不上来"？—— 这个体验损失如果说不清，就没法判断该不该在 8GB 机型上开它。
- [ ] 权重 1.8 GB 是固定成本。有没有可能做**分层加载**（只加载常用的若干层，其余按需从 mmap 读）？如果可行，房租就能变成半浮动，8GB 机型的账会好看很多——但代价是延迟。这个 trade-off 有人做过吗（待核实）。
