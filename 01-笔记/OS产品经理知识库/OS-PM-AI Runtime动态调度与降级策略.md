# OS-PM-AI Runtime 动态调度与降级策略

> [!note] 补建说明
> 本笔记由 MOC `[[OS产品经理知识库 MOC]]` 引用但原文件缺失，现据 OS PM 知识库既有内容补全。文中**矩阵阈值与具体档位为推断示意**，非厂商公开一手数据，落地前需以 Android/iOS/HarmonyOS 官方文档核实。

## 一、为什么需要动态调度与降级

端侧大模型推理受三大实时约束钳制（详见 [[OS-PM-端侧大模型系统级挑战]]）：
- **热（Thermal）**：NPU/GPU 持续高负载升温，触发温控降频，算力骤降。
- **电（Battery）**：低电量下系统限制后台/高功耗任务以保续航。
- **存（Memory）**：RAM 紧张时传统 LMK/ZRAM 失效，KV Cache 与权重争抢内存（PSS 双重挤压）。

静态配置（一套参数跑到底）在约束波动时会要么过热/耗电、要么卡顿。因此 OS AI Runtime 必须**按三维实时状态动态调度推理配置，并在极端状态下降级**。

## 二、调度与降级的对象：SpecDec 投机采样

核心可调度单元是 [[OS-PM-投机采样原理与能效优化]] 的 **SpecDec（Speculative Decoding）**：
- 小模型（draft）快速猜若干 token → 大模型（target）并行验证。
- 把 Memory-Bound 转 Compute-Bound，提升吞吐、降时延。

可调参数：
- **draft 模型规模**（小/中/关）
- **draft length**（每次猜的 token 数，如 4/8/16）
- **target 模型档位**（小/中/大，或更小的端侧蒸馏模型）

## 三、三维动态降级矩阵（示意）

| 热 | 电 | 存 | 调度动作 | 用户可感 |
|---|---|---|---|---|
| 正常 | 正常 | 充足 | draft 中 + length 8 + target 大 | 最优质量/速度 |
| 升温 | 正常 | 充足 | draft 小 + length 4 | 轻微变慢 |
| 高温 | 正常 | 充足 | 关 draft（纯 target）或降 target 档 | 明显变慢，保不烫手 |
| 任意 | 低电 | 充足 | 降 target 档 + 限频 | 省电优先 |
| 任意 | 任意 | 紧张 | 降 target 档 + 缩短上下文 + 驱逐 KV | 防 OOM/杀进程 |
| 高温+低电 | 任意 | 任意 | 暂停生成长文本 / 转云端或提示稍后 | 兜底，不崩 |

> ⚠️ 上表档位与阈值（8/4、大小模型划分）为**推断示意**，非厂商公开数据；需以官方文档核实。

## 四、降级的不变量（PM 必须守住）

降级只能动"速度/质量/功耗"三角，**不能动安全边界**：
- 任何档位下，敏感意图仍须走 [[Confirmation UI 安全机制]]（确认机制）与 [[Agent Workspace 隔离执行]]（隔离执行）。
- 降级导致能力变弱时，若无法保证确认/隔离，应**主动降级为"不可用并提示"**，而非带病运行。

## 深化补充

### 一句话心智模型

> **降级不是"变差"，是"用一种用户能接受的方式变差"。没有降级策略的系统不是不会变差，是会以最难看的方式变差——闪退、卡死、烫手。**

这个视角一换，降级就从一个技术话题变成了**产品设计话题**。核心问题不是"怎么降"，而是：

> **在速度、质量、功耗、可用性四者里，用户在不同场景下愿意先牺牲哪个？**

我试着给一个初步答案（这比原文的三维矩阵更接近我该做的决策）：

| 场景 | 用户最在意 | 应该先牺牲 | 绝不能牺牲 |
|---|---|---|---|
| 主动提问（"帮我总结"） | **质量** | 速度（可以转圈） | 结果正确性 |
| 实时翻译 / 字幕 | **速度** | 质量（译得糙点没关系） | 连续性（不能卡住） |
| 后台整理（静默任务） | 都不在意 | 速度 + 功耗都可以让 | — |
| 支付 / 高危动作 | **正确性** | 速度、质量都可以让 | **确认与隔离** |

**最后一行就是原文第四节"降级不变量"的具体化。** 我想强调的是：这条不变量的正确表述不是"安全边界不能降"，而是——

> **能力降级时，风险阈值必须同步收紧。** 模型变笨了，确认反而要更强，因为它判断错的概率上升了。

这是个反直觉但我觉得很重要的推论：**很多系统会在降级时同时放宽确认（因为"要快"），这恰恰是最危险的组合。**

### 三维矩阵的一个结构性缺陷

原文的矩阵是（热 × 电 × 存）三维。但我觉得少了最关键的一维：**用户是否在等**。

同样是"高温 + 低电"：
- 用户正盯着屏幕等结果 → 应该**降质量保速度**，或者干脆提示"现在不太行"；
- 后台静默任务 → 应该**直接暂停**，等充电时再跑。

**这两种处理完全相反，但在原文的三维矩阵里落在同一格。** 所以矩阵应该是四维的：**热 × 电 × 存 × 前台性（用户是否在等）**。

而"前台性"这一维其实已经有现成的东西可以对齐——[[OS-PM-端侧大模型系统级挑战]] 里的 **AI Workload QoS 分级（P0 Real-time / P1 Interactive / P2 Background）**。**把 QoS 等级作为矩阵的第四维，比我自己造一个新概念要好**，因为它和 NPU 调度用的是同一套语言。

### 降级要不要让用户知道？

原文没讨论这个，但我觉得这是降级策略里最难的产品问题。

- **完全不告知**：用户觉得"这功能时好时坏，不可靠"→ 信任崩塌。
- **每次都告知**："当前性能受限已降级" → 弹一百次没人看，且暴露系统的窘迫。

我倾向的原则：**按"用户能否察觉"来决定是否告知。**
- 察觉不到的降级（draft 长度从 8 调到 4）→ **不告知**，纯内部优化。
- 能察觉的降级（明显变慢、结果变短）→ **给一个轻量的、非阻断的提示**，最好带原因（"设备较热，已切换省电模式"）。
- **功能不可用** → 必须明确告知 + 给替代方案（"稍后重试"或"用云端处理"，后者要征得同意，因为涉及数据出端）。

**最后一条尤其重要**：从端侧降级到云端，表面是性能决策，实际是**隐私决策**。这个切换绝不能静默发生。这一点和 [[跨端与多设备意图流转]] 里"执行位置决策"是同一类问题。

### 待解问题

- [ ] 降级状态下的指标该**单独统计还是混在一起**？如果混着算，"平均首字延迟"会被降级样本污染，看不出真实水平；如果分开，又需要每条埋点都带降级档位标签。哪个成本更低？
- [ ] "模型变笨时确认要更强"——这条怎么落地？**系统怎么知道自己变笨了**？是靠档位（降级了就收紧）还是靠置信度（模型自报）？前者简单但粗糙，后者精确但模型的置信度本身在降级后也不可信了。
- [ ] 端→云的降级需要用户同意，但如果每次都问，体验很差。能不能做成**一次性授权 + 可撤销**（"允许在设备繁忙时使用云端处理"）？这个开关放哪、默认值是什么？—— 参考 [[Windows Copilot Actions 竞品观察]] 里"默认关 + 需 opt-in"的姿态。
- [ ] 原文矩阵的阈值全是推断值。**要拿到真实阈值，我该找谁要？** （Thermal Governor 的温控曲线应该是芯片厂 + 系统团队共同定的，这个数据可能根本没有单一 owner —— 这本身就是个值得确认的事。）
