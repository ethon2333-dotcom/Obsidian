# 📑 OS 产品经理：性能与稳定性指标体系及诊断逻辑

> [!note] 笔记定位
> App PM 关注单 App 业务转化；OS PM 必须掌控**全局资源健康度**。性能与稳定性是系统「基建」，决定用户对 OS 流畅度的直观感知。

## 模块一：核心指标详解

### 1. 流畅度与帧率
- **VSYNC 驱动**：60Hz 单帧窗口 16.6ms；120Hz 仅 8.3ms。超窗口未完成即**丢帧 Jank**。
- **FPS**：基本指标，但单独看无法评估微小卡顿。
- **丢帧率 Jank Rate**：
  - Slow Frame：渲染 > 单 VSYNC 周期（如 >16.6ms）的帧占比
  - Frozen Frame：渲染 > **700ms** 的严重卡顿（用户感到死机）
- **触控响应时延 Touch-to-Response**：硬件中断到首帧渲染。优秀 OS 控制在 **30~50ms**。

### 2. 启动与切换时延
- **冷启动 Cold Start**：进程不在内存，点击到首帧。系统应用标准 **1~1.5s**（含 TTID）。
- **热启动 Warm/Hot**：进程在内存，恢复状态。通常 **< 500ms**。
- **窗口转场时延 Window Transition**：触发跳转到动画播完可响应触控。

### 3. 系统稳定性（红线）
```text
崩溃/卡死分类
 ├── App Crash（Java/Native 未捕获异常）
 ├── System UI Crash（桌面黑屏/闪烁）
 ├── Kernel Panic / Watchdog Dump（内核崩溃/重启）
 └── ANR（主线程阻塞）
```
- **Crash 率**：UV Crash 率 = 崩溃用户数 / DAU，行业要求 **< 0.1%~0.5%**。
- **ANR 触发阈值**：
  - Input 5s 未响应 / 前台 Service 20s / 后台 200s
  - BroadcastReceiver 前台 10s / 后台 60s
  - **User-Perceived ANR Rate** 官方警告阈值 **0.47%**（Google Play）。

### 4. 资源与内存消耗
- **PSS（Proportional Set Size）**：**OS PM 看内存最核心指标**（独占 + 按比例平摊共享）。
- **Base RAM**：开机无任何三方 App 的基础占用。
- **LMK 触发频率**：频繁杀后台 = 保活率差。
- **功耗/热**：Excessive Partial WakeLock（异常锁 CPU）、Thermal Throttling 热降频触发率（阈值 ~45~50°C）。

## 模块二：埋点与日志采集（低开销 / 无侵入 / 隐私优先）
```text
操作 ─> 框架/内核 Hook ─> 环形缓冲区 Ring Buffer
                ├─> [常态指标] 低频聚合: 平均FPS/PSS峰值 → 夜间WiFi充电批量上报
                └─> [异常事件] 高精度Trace: 丢帧>700ms/ANR/Crash → 即锁Ring Buffer导出堆栈
```
- **UI 卡顿监控**：Choreographer 帧监听，间隔 > 16.6ms×N 即算丢帧 N。
- **ANR 监控**：Looper 消息队列前后打点，单条 > 2s 抓主线程堆栈。
- **内存监控**：订阅 `proc/meminfo` 与 `lmkd` 事件。
- **分层上报**：常态只记统计值（WiFi+充电批量）；异常才固化导出 Systrace/Perfetto。

## 模块三：诊断三步法（收到「桌面滑动卡顿」类需求）
```text
[发现问题] → Step1 归因: 单App自身问题 or 系统级资源争抢
          → Step2 抓 Trace: MainThread阻塞? RenderThread延迟? CPU被抢占?
          → Step3 定位: 锁争抢→异步回调 / 内存瓶颈→调ZRAM / 硬件降频→调温控
```

### 核心诊断工具
- **Perfetto / Systrace**：CPU 调度、线程状态、VSync 同线展开。主线程处于 **Runnable** = CPU Bound；**D 态(Uninterruptible Sleep)** = I/O Bound。
- **Heap Dump / Page Fault**：高 GC 伴随卡顿 → 查内存泄露 / Page In-Out 频繁。
- **Batterystats / Bugreport**：查熄屏下谁在频繁 Alarm 唤醒或持 WakeLock。

> [!tip] 关联
> 端侧 LLM 会直接恶化上述多项指标（内存膨胀、NPU 长占、热降频），详见 [[OS-PM-端侧大模型系统级挑战]]。

## 深化补充

### 一句话心智模型

> **指标不是用来"证明系统好"的，是用来"在系统变坏之前发出声音"的。所以一个指标值不值得建，看的不是它能不能被测，而是它变化时我能不能采取行动。**

用这个标准回看原文那一长串指标，可以分成三类，价值完全不同：

| 类型 | 例子 | 价值 |
|---|---|---|
| **可行动的** | LMK 触发频率、Frozen Frame 率、Thermal Throttling 触发率 | **高**——一涨就知道该去调什么 |
| **诊断用的** | Perfetto trace、Heap Dump | 中——出事后才用，但必须有 |
| **汇报用的** | 平均 FPS、Crash 率总数 | **低**——好看，但涨跌都不知道该干嘛 |

**我要警惕的是第三类。** 平均 FPS 是最典型的例子：一个 59.8 的平均帧率可以完美掩盖每分钟一次的 700ms 冻屏，而后者才是用户真正会投诉的东西。**平均值天生掩盖长尾，而用户体验由长尾决定。**

这也是为什么原文强调 **Frozen Frame（>700ms）** 和 **P95/UV 口径** —— 这些是"长尾可见"的指标。**能记住的一条原则：凡是能被平均掉的指标，都要配一个分位数或触发频次的孪生指标。**

### AI 时代要补的指标：从"系统坏了"到"结果错了"

原文的指标体系有一个共同的隐含假设：**失败是可观测的系统事件**（崩溃、卡顿、超时）。AI-Native OS 打破了这个假设——

> **Agent 最常见的失败方式是「一切正常地干错了事」。** 不崩、不卡、不超时，只是结果不对。

现有三件套（Crash / ANR / Jank）对此完全失明。我把需要补的指标按"用户损失"排了个序：

| 新指标 | 定义（我的初稿） | 对应的失败 | 优先级 |
|---|---|---|---|
| **误执行率** | 执行了用户未意图的高风险动作 / 总高风险动作 | **最严重**——涉及钱和隐私 | **P0** |
| **中途取消率** | 用户在确认前放弃 / 总触发 | 意图理解错了 | P0 |
| **执行后返工率** | 执行完用户立即手动重做 / 总执行 | 执行结果不对 | P1 |
| **该拒未拒率** | 无合适能力时仍强行执行 / 无匹配用例 | 幻觉式调用（呼应 BFCL v4 的 Hallucination 子集） | P1 |
| **TTFT / TTFL** | 首 token / 首个可感知反馈时延 | 体感慢 | P1 |

**"误执行率"必须是 P0，而且它应该是一条红线指标而非优化指标**——就像 Crash 率一样，超过阈值直接卡版本。理由在 [[PM 需求定义 跨学科发散]] 的 FMEA 那一支：严重度 × 不可探测度都极高（用户可能几天后才发现钱少了）。

⚠️ 上表的定义是我自己拟的初稿，**行业没有公认口径，待核实**是否有成熟参考（BFCL v4 的 Hallucination 子集是目前找到的最接近的东西，但那是模型评测口径，不是线上指标口径）。

### 诊断三步法在 AI 场景的变形

原文的三步法（归因 → 抓 Trace → 定位）针对的是**性能**问题。AI 的"结果错误"问题需要一套平行的流程，我试着写一版：

```text
[用户反馈"它干错了"]
  → Step1 归因: 意图理解错? 参数填错? 工具选错? 执行环境变了?
  → Step2 复现: 拿到当时的 上下文快照 + 路由决策 + 置信度  ← 关键前提：得先埋这些
  → Step3 定位: 模型问题(换模型/微调) or Schema 问题(意图定义有歧义) or 数据问题(记忆污染)
```

**Step2 是整套流程的前提，也是最容易被忽略的一步。** 性能问题有 Perfetto 可以事后抓，但"Agent 为什么做了这个决定"如果当时没记，事后永远查不出来。**这意味着"决策可追溯"必须在设计阶段就内建**，不能等出了问题再加——这一点恰好和 [[Windows Copilot Actions 竞品观察]] 里"防篡改日志/可审计"的合规要求撞在一起，**一个是排障需求，一个是合规需求，但落地是同一件事**。这是个能一举两得的投入。

### 待解问题

- [ ] "误执行率"怎么测？用户不主动投诉的话，系统**根本不知道自己错了**。有没有可能用"撤销/退款/申诉"这类下游信号做代理指标？
- [ ] 新指标要不要设**发布红线**（像 Crash 率那样卡版本）？如果设，阈值定多少？—— 但没有历史数据就定不出阈值，**这是个鸡生蛋问题**，得先跑一段时间收基线。
- [ ] "决策可追溯"要记录上下文快照，但上下文里全是用户隐私（屏幕内容、位置、对话）。**排障需求和隐私要求直接冲突**，怎么设计才能两全？（本地保留 N 天不上报？只记决策不记内容？）
- [ ] 传统指标（FPS/ANR）和 AI 指标（成功率）**打架时听谁的**？比如为了提升意图成功率要多跑一次大模型，代价是掉帧——这个权衡该由谁拍板，用什么规则？
