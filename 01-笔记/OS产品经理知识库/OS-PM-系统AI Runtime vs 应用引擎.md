# 📑 OS 产品经理：系统级 AI Runtime 与应用级推理引擎的分工与边界

> [!note] 笔记定位
> 为什么 OS 厂商（Android AICore、Apple Foundation / Apple Intelligence、HarmonyOS NPU 调度框架）要死磕自研 **System AI Runtime**，而不让 App 各自集成推理引擎（如 ONNX Runtime / llama.cpp / MNN）？本篇讲清边界与 4 大护城河。

## 一、核心区别一句话
- **App 推理引擎（MNN / llama.cpp）**：目标 = 单 App 在自己进程内把模型跑起来，不管全局。
- **System AI Runtime（NNAPI / Core ML / CANN）**：目标 = **跨 App、跨硬件、跨场景的全局资源仲裁与系统级能力封装**。

## 二、为什么不能让 App 自己搞（4 大护城河）

### 1. 硬件异构与驱动碎片
- 端侧芯片极复杂：NPU（多代）、GPU、CPU、DSP/ISP 各家不一
- App 自集成要为每种 SoC 单独适配，不现实
- Runtime 统一抽象 HAL：App 只写一次，Runtime 在底层映射到高通/联发科/海思 NPU 指令集

### 2. 全局资源仲裁（最核心）
若多个 App 同时拉起 NPU 模型会直接 OOM/Crash，必须全局仲裁者。
- NPU QoS 分级：相机/AR(P0 Real-time) > 主动 AI 对话(P1) > 静默语义抽取(P2)
- 跨 App KV 缓存共享：System Prompt 的 KV 常驻共享页表，所有 App 复用，内存↓60%
- 内存压力联动：临近 OOM 由 Runtime 统一驱逐冷 KV Block，而非各 App 抢资源

### 3. 安全与隐私沙盒
- App 沙盒内模型数据可读性差，云控策略更新滞后
- Runtime 在 TEE / 安全世界加载权重、做 AI 鉴权，防权重被逆向、防 Prompt 注入越权调系统能力
- 系统级权限网关：AI Agent 调「发微信」须 Runtime 鉴权，App 自引擎易越权

### 4. 系统级特性（App 做不到）
| 能力 | App 推理引擎 | System AI Runtime |
| --- | --- | --- |
| Cocktail/混合调度 | ❌ | ✅ NPU+GPU+CPU 协同切分算子 |
| 跨 App Context Engine | ❌ | ✅ 屏幕OCR/剪切板/位置融合 |
| SpecDec 动态降级 | ❌ | ✅ 温控/电量/内存三维触发 |
| 低功耗常驻唤醒 | ❌ | ✅ 订阅 Display/传感器事件低开销触发 |
| OTA 模型热更 | ❌ | ✅ 系统级权重下发（不更 App） |

## 三、两者如何共存（现代 AI-Native OS 范式）
```text
[应用层: 字节/微信/笔记App]  ──调──> [AIDL/IPC] ──> [系统 AI Runtime]
[系统服务: 全局搜索/智慧助手] ─────────────────────> [系统 AI Runtime]
                                              └─> NNAPI/Core ML/CANN ─> 驱动 ─> NPU
```

### PM 决策建议
1. **全局、常驻、跨 App 的系统 AI 能力** → 必须进 System AI Runtime
2. **单 App 内、私有、强性能敏感的特殊模型**（如美图自研分割） → 可 App 自集成，但需向 Runtime 申请 NPU 算力配额
3. **标准开放能力**（OCR/翻译/语音） → Runtime 暴露标准 API，App 免集成

## 深化补充

### 一句话心智模型

> **这不是"技术上谁做得更好"的问题，是"公地悲剧"问题。NPU 和内存是公共草场，让每只羊自己决定吃多少，草场必死。System AI Runtime 就是那个牧场管理员。**

原文列了 4 大护城河，但我认为它们不是并列的——**只有第 2 条（全局资源仲裁）是不可替代的**，其余三条都是"顺带的好处"：

| 护城河 | App 能不能自己解决 | 真实性质 |
|---|---|---|
| ① 硬件异构适配 | 能（用 MNN/llama.cpp 这类跨平台引擎） | **便利性**，不是必需 |
| ② **全局资源仲裁** | **绝对不能**——单个 App 看不到全局 | **唯一的硬理由** |
| ③ 安全与隐私沙盒 | 部分能（TEE 需要系统支持） | 强理由，但可以靠系统提供 TEE API 解决 |
| ④ 系统级特性 | 不能，但这些能力本来就属于系统 | 循环论证——"系统能力只有系统能做" |

**把这个想清楚很重要，因为它决定了我该怎么和 App 开发者谈判。** 如果我拿"我们适配得更好"去说服字节接入系统 Runtime，对方会说"我们自己适配得也不错"。但如果我说的是"**你不接入，NPU 冲突时你会被无差别限流；接入了你才有 QoS 优先级**"——这是个对方无法自己解决的问题，才有说服力。

### 这套逻辑其实是老剧本重演

我意识到这跟安卓历史上的几场仗是同一个剧本：

| 时代 | 争夺的公共资源 | 系统给出的答案 |
|---|---|---|
| 2015 前后 | 后台进程 / 唤醒 | Doze、后台限制、JobScheduler |
| 2018 前后 | 推送连接 | 统一推送（国内）、FCM |
| 2020 前后 | 定位 / 隐私数据 | 运行时权限、分区存储 |
| **2026** | **NPU / AI 内存** | **System AI Runtime** |

**每一次的模式都一样：先野蛮生长 → 公地悲剧（耗电/卡顿）→ 系统收权 + 提供统一 API → App 抱怨但最终接入。**

这个类比对我有两个用处：
1. **可以预判 App 侧的反弹路径**——他们会先自研绕过、再抱怨限制、最后接入。国内厂商尤其会经历"保活对抗"阶段。
2. **可以借鉴历史上的过渡策略**——比如运行时权限当年是给了很长的兼容期（targetSdk 分级推进）。AI Runtime 大概率也要走类似的渐进式强制路径，而不是一刀切。

### 一个原文没提的紧张关系

护城河 ③ 说"Runtime 在 TEE 加载权重，防权重被逆向"。但这条对 App 是**双刃剑**：

- 对 OS 厂商：好事，系统模型受保护。
- 对 App：**"我的自研模型交给系统 Runtime 跑，会不会被厂商看到？"**

这个信任问题在国内生态里尤其尖锐——头部 App 和手机厂商本来就是竞合关系。**"把我最核心的模型权重交给竞争对手的 Runtime 加载"，这个要求可能比"开放意图接口"还难谈**（见 [[意图框架的商业与生态博弈]]）。

所以原文的"PM 决策建议 2"（单 App 私有模型可自集成，但要申请算力配额）其实是个**很关键的妥协设计**——它承认了这条信任边界的存在。我觉得这条应该被明确说成一个原则：

> **系统 Runtime 应该竞争"公共能力"，不应该试图接管"私有模型"。** 前者靠资源仲裁权自然获胜，后者会引发生态对抗。
