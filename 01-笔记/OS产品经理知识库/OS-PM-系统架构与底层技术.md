# 📑 OS 产品经理：系统架构与底层技术

> [!note] 笔记定位
> OS PM 不一定要写内核代码，但必须懂「资源流转」与「能力边界」。系统本质 = **在有限的硬件资源（算力、内存、电量、带宽）下，做收益最大化的调度与抽象**。

## 模块一：系统分层与能力解耦

### 1.1 经典 5 层架构
```text
+-------------------------------------------------------+
|  应用层 (Applications / System UI)                    |  <- 用户直接感知
+-------------------------------------------------------+
|  框架层 (Framework / System Services / Daemons)       |  <- 系统能力封装
+-------------------------------------------------------+
|  硬件抽象层 (HAL)                                     |  <- 屏蔽硬件差异
+-------------------------------------------------------+
|  内核与驱动层 (Kernel & Drivers)                      |  <- 物理资源掌控
+-------------------------------------------------------+
|  硬件物理层 (CPU, NPU, RAM, Display)                 |  <- 物理芯片与外设
+-------------------------------------------------------+
```

### 1.2 为什么 PM 必须懂「能力解耦」
- **HAL 的价值**：Framework 不直接读写驱动，芯片厂商更新驱动时 OS 系统服务无需重写。
- **IPC 成本**：App（沙盒进程）调系统能力（如打开相机）必须走 IPC（Binder / Socket / D-Bus / 共享内存）。
- **PM 权衡**：高频高吞吐数据（如 60fps 相机预览）**绝不能走普通 IPC**，必须用**共享内存（Gralloc）**传句柄。

> [!warning] PM 核心决策点
> 设计系统级新能力（如「全局屏幕实时翻译」）时，先回答：放**应用层**（迭代快、风险小、权限低、性能损耗大）/ **框架层**（全局可用、性能好、但增大镜像体积、升级难）/ **内核/硬件层**（特定芯片加速）？

## 模块二：资源调度与功耗管理（算力/内存/电量的黄金三角）

### 2.1 算力调度（CPU/GPU/NPU）
- **EAS 能量感知调度**：异构 SoC（大/中/小核）按任务紧急度实时分配核与频率。
- **前台优先级 Touch Boost**：触摸瞬间拉高 CPU 频率锁大核，确保首帧不卡；松手即回落省电。

### 2.2 内存管理
- **OOM Killer**：物理内存不足时按 LRU + 进程优先级杀后台（前台交互 > 前台后台服务 > 后台普通 App > 空进程）。
- **ZRAM 内存压缩**：用 CPU 计算换可用内存（后台 App 堆栈压缩存放）。
- **冷启动 vs 热启动**：热启动在内存中直接恢复（毫秒级）；冷启动需从 Flash 读入、初始化（耗时较长）。

### 2.3 功耗与后台治理
- **后台冻结 Freezer**：退后台超阈值（如 5 分钟）暂停 CPU 进程、保留内存，切回即解冻。
- **对齐唤醒 Alarm Alignment**：后台定时任务攒批统一唤醒，减少 CPU 从 Deep Sleep 醒来次数。

> [!tip] PM 性能权衡矩阵
> | 策略 | 优势 | 代价 |
> | --- | --- | --- |
> | 激进杀后台 | 释放 RAM、前台流畅 | 后台频繁冷启动耗电、体验断层 |
> | 大容量 ZRAM | 膨胀可用内存、保活更多 | 增加 CPU 解压开销、可能掉帧发热 |
> | 激进 CPU 限频 | 提升续航、降发热 | 高负载明显掉帧 |

## 模块三：系统级 AI（AI-Native OS）

传统 OS 以 App 为中心、指令驱动；AI-Native OS 以**意图为中心、上下文为驱动**。

```text
[用户输入: 语音/手势/屏幕文本]
   ▼
[1. 系统上下文引擎 Context Engine] 聚合屏幕OCR/剪切板/位置/传感器/App状态
   ▼
[2. 意图识别与路由 Intent Framework] 端侧SLM识别意图 → 端侧 vs 云端
   ▼
[3. 执行引擎 Execution Engine] 调系统API / 三方App / 本地RAG
```

### 3.1 端侧 vs 云端模型
- **端侧（1B~7B SLM）**：零延迟、离线、隐私好；但能力上限受限、极耗 RAM/NPU。
- **云端（70B+ LLM）**：能力强；但依赖网络、有延迟、Token 成本与隐私风险。
- **量化**：3B FP16 ≈ 6GB 跑不起，必须 INT4 压到 ~1.5GB，空闲卸载、需要时快速加载到 NPU。

### 3.2 系统上下文引擎
- 屏幕语义感知（无障碍/OCR 理解实体）
- 多源传感器融合（GPS/蓝牙/运动状态预测行为）
- 本地向量数据库（相册/聊天/笔记本地 Embedding，隐私安全语义搜索）

### 3.3 意图识别与服务分发
- 从 GUI → LUI/LUA（语言用户界面 / 语言用户 Agent）
- **App Action 抽象**：定义系统级 API 标准（如「打车」「发微信」），AI 跨过 App 界面完成链式任务。

> [!question] 思考题
> 用户反馈「系统用久了卡顿发热」，从**内存管理 / 后台治理 / 芯片调度**三个方向分别推查哪些原因？
> 详见 [[OS-PM-性能与稳定性指标体系]] 的诊断三步法。

## 深化补充

### 一句话心智模型

> **分层的本质是"谁能被谁替换"。一个能力放在哪一层，等价于回答"它多久能改一次、改错了炸多大"。**

我用这个视角重读那张 5 层架构图，它就从一张静态的图变成了一把**决策尺**：

| 层 | 迭代周期 | 改错的爆炸半径 | 适合放什么 |
|---|---|---|---|
| 应用层 | 天/周（可热更） | 单 App 崩 | 策略、UI、还在验证的能力 |
| 框架层 | 版本级（月/季） | 全系统 | 已收敛的通用能力、需要跨 App 一致的契约 |
| 内核/HAL | 大版本 + 芯片厂协同 | 开不了机 | 只有硬件加速才能达标的东西 |

**所以"放哪一层"这个决策，真正在权衡的是"我对这个设计有多确定"。** 不确定的东西放低层，就是在给自己上枷锁——改一次要等一个大版本。这跟软件工程里"稳定的依赖抽象原则"是一回事：**越底层，越应该只放已经稳定的东西。**

反过来说，这也给了我一个反对某些提案的现成理由：**"这个能力我们自己都还没想清楚交互形态，现在下沉到 Framework，一年内改三次怎么办？"** 比空谈"风险大"有说服力得多。

### 把这把尺子用在意图框架上

拿我关心的问题练手——**系统级意图框架该放哪一层？** 拆成三块分别定位：

| 组件 | 我的判断 | 理由 |
|---|---|---|
| **意图声明格式（Schema）** | **框架层，且要最稳定** | 这是对开发者的契约，改一次全生态返工。宁可少定义，不可乱改 |
| **意图路由 / 编排引擎** | 框架层，但允许较快迭代 | 是策略不是契约，模型换了策略就得换 |
| **端侧模型推理** | 走 System AI Runtime（见 [[OS-PM-系统AI Runtime vs 应用引擎]]） | 需要全局仲裁，App 层做不了 |
| **具体意图的 UI 呈现** | **应用层 / System UI** | 交互形态还在探索，必须能快改 |

**这个拆分让我看清了一个之前混在一起的问题**：大家争论"意图框架要不要下沉"，其实是把"Schema 契约"和"路由策略"混为一谈了。前者必须稳、必须下沉；后者必须活、不能焊死。分开讨论，争论就消解了一半。

### IPC 那条经验的一般化

原文说"60fps 相机预览绝不能走普通 IPC，要用共享内存传句柄"。我想把它抽象成一条能复用的规则：

> **数据量 × 频率 = IPC 成本。超过某个阈值，就该从"传数据"改成"传引用"。**

这条规则在 AI 时代有个新的适用对象：**Agent 的屏幕上下文**。每次意图识别都要把整屏的 OCR/无障碍树序列化传给推理服务吗？如果是 1 秒 10 次的实时感知，这跟 60fps 相机预览是同一类问题。**答案大概率也一样——共享内存 + 增量更新，而不是全量传。** 这也解释了为什么 [[端侧 AI 基建与算力预算]] 里"相邻帧拓扑变化 <5% 就复用上次决策"这种优化是必要的：不只是省算力，也是省 IPC。

### 待解问题

- [ ] "Schema 必须稳定"和"AI 能力快速演进"是直接冲突的。有没有办法设计一个**可扩展但不破坏兼容**的意图 Schema？（类似 protobuf 的字段编号机制？）这可能是整个意图框架最关键的工程设计。
- [ ] Context Engine 聚合屏幕/剪贴板/位置——**这本身就是一个超级权限**。它该放框架层（全局可用）还是该有独立的权限模型？如果框架层默认能看所有屏幕内容，那和无障碍服务的权限争议是同一个问题。
- [ ] 后台冻结 Freezer 遇上"常驻的 AI 服务"怎么办？传统规则是"退后台 5 分钟冻结"，但 AI Runtime 不能被冻。**那它凭什么豁免？豁免的边界谁来定？** —— 这会不会变成新一轮的"保活白名单"乱象？
