## 一句话心智模型

**Agentic UX 的核心矛盾是"自主性越高越省事，但可控性越低越不敢用"——用户给 agent 的信任额度从来不是被 demo 的惊艳度授予的，而是靠「我随时看得见、随时叫得停、随时撤得掉」一笔一笔挣来的。所以 agent 的界面本质不是在设计一段对话，而是在设计一份"可撤销的授权契约"：契约条款写在 UI 上，违约成本由产品方承担。**

推论三条（后文各节都是这三条的展开）：

1. **可见性是信任的利息**——用户看不见的自主行为，会被默认为最坏情况。
2. **可撤销性是信任的本金**——能撤销的错误只是摩擦，不能撤销的错误是背叛。
3. **能力边界的表达比能力本身更早影响留存**——用户不会为"其实它能做"买单，只会为"我知道它能做"买单。

## 一、定义与边界：什么是 Agentic UX

「Agentic UX」（也被叫作 AX / agentic experience / delegative UI）指的是：当软件不再只是"响应点击"，而是**接受目标 → 自主规划 → 调用工具 → 改变系统状态**时，为这个循环设计的交互层。

它和传统 UX 的分水岭在于一条被打破的假设：**传统可用性启发式默认"人在看屏幕、人在点按钮、同样输入同样输出"**。Agent 三条都不成立——它可能在后台跑、可能自己决定下一步、同样目标每次路径都不同。

### 三层能力的界面差异（对照表）

| | Chatbot（问答） | Assistant（受命执行） | Agent（自主执行） |
|---|---|---|---|
| 交互契约 | 我问，它答 | 我下令，它执行 | 我给目标，它自己拆步骤 |
| 状态数量 | 单轮，无中间态 | 少量中间态 | 大量中间态 + 并行态 |
| 副作用 | 无（只产文本） | 有，但用户逐条批准 | 有，可能在用户没看时发生 |
| 失败形态 | 答错 | 执行错一步 | 走偏整条路径 / 卡死 / 部分完成 |
| UI 重心 | 对话气泡 | 命令 + 结果确认 | **计划 / 进度 / 轨迹 / 回滚** |
| 设计难点 | 幻觉表达 | 确认时机 | **授权粒度 + 可观测性 + 可逆性** |

> **关键结构性建议（行业共识度较高）**：agent 产品应把「对话线程」和「活动流（activity panel）」**在信息架构上拆开**——对话是设目标的地方，活动流是看它在干什么的地方。把两者混在一个聊天气泡流里，结果是"既不像对话、也不像任务管理器"，两头都失败。

## 二、设计模式速查表（主体）

> 这是本篇的骨架。按 agent 生命周期的**六个侧面**组织：输入 → 过程 → 输出 → 控制 → 失败 → 信任。每个模式只给"是什么 / 什么时候用 / 典型坑"，不给规格。

### 2.1 输入侧：用户怎么把意图交给 agent

| 模式 | 一句话 | 适用 | 典型坑 |
|---|---|---|---|
| 对话式输入 | 自然语言描述目标 | 开放探索、长尾需求、意图未成形 | 「prompt 税」：用户得先猜它能干什么，再组织语言，反复劳动成本高 |
| 命令式 / 结构化控件 | 滑杆、下拉、预设、快捷指令 | 高频重复任务、参数明确 | 覆盖不了长尾；但对重复工作**几乎总是优于**打字 |
| 混合式（推荐默认） | 结构化控件为主 + 自然语言兜底 | 大多数生产力场景 | 两套心智模型不一致时用户困惑 |
| 环境感知 / 主动触发（proactive） | agent 根据时间、位置、日程、屏幕内容自己起个头 | 用户不知道自己需要帮助时 | **打断预算**是稀缺资源，见下方警示 |
| 意图消歧（disambiguation） | 请求含糊时列出候选让用户选 | 多候选且代价不对称时 | 每次都问＝退化成表单；从不问＝猜错代价高 |
| 澄清式提问（clarifying question） | 缺关键参数时反问一句 | 参数缺失且无法安全默认 | 问题要**具体**：Apple HIG 明确要求「Which soup?」优于「Which one?」 |
| 渐进式意图收窄 | 先给宽结果，再让用户圈定 | 探索类任务 | 首屏结果太宽会被判定"不懂我" |
| 屏幕上下文引用 | "把**这个**加到相册" | OS 级 agent 的杀手锏 | 需要应用把屏上实体标注给系统（见第七节） |

> ⚠️ **主动触发的打断成本**：CHI 2025 一项针对主动式编程助手（探针名 Codellaborator，18 人被试）的研究报告称，主动协助相对纯 prompt 基线**提升了效率，但同时造成可测量的工作流打断**；加入"存在感指示器 + 交互上下文"能**减少但无法消除**打断。（转引自二手报道，ACM DL 原文待核实）
> 结论方向对 PM 有用：**主动 ≠ 更好，主动是在花用户的注意力预算**。行业里也有从业者把"每天不请自来的 AI 通知条数"当作有上限的衰减资源来管理，但目前我看到的具体数字都出自个人博客estimates，**不可引用为数据**。

### 2.2 过程侧：让"正在发生的事"可见

| 模式 | 一句话 | 备注 |
|---|---|---|
| 流式输出（streaming） | 逐字/逐块吐，降低感知延迟 | 已是基线，不再是差异化 |
| **具体化进度文案** | 说"正在总结要点"而不是"处理中…" | Apple HIG「Generative AI」明确写了这条（2026-06-08 版） |
| 计划预览（plan preview） | 执行前先把 N 步计划摊开给人看 | 高代价任务的**第一道闸门**；也是"意图对齐"的最便宜检查点 |
| 思维链 / 推理摘要展示 | 展示它为什么这么选 | 全量思维链 ≠ 好体验；**摘要级 + 可展开**更实用 |
| 工具调用轨迹（agent trace） | 时间线：调了什么工具、碰了哪些文件、引了哪些源 | 「当自动化失败时，trace 就是 UI」。参见 [[工具调用安全 学习笔记]] |
| 可中断（interruptibility） | 随时"停"，且停得干净 | 难点是**停在半路的状态怎么收尾**——脏状态回滚是产品问题不只是工程问题 |
| 并行/多任务状态呈现 | 多个 agent 同时跑时的状态面板 | 2026 年的新战场，尚无成熟范式 |
| 后台/常驻态指示 | 系统级常驻指示器（类似"正在录音"小圆点） | OS 级 agent 的**必备件**，见第七节 |
| 存在感指示器（presence） | "我在看着，但还没插手" | 降低主动式打断的突兀感 |

### 2.3 输出侧：把不确定性诚实地摆上台面

| 模式 | 一句话 | 典型坑 |
|---|---|---|
| 不确定性表达 | 用措辞/视觉暗示"这可能不准" | 数字化置信度（"87% 确信"）对普通用户几乎无意义，甚至造成伪精确 |
| 引用与溯源（citation / grounding） | 每条结论挂来源可点开 | 有研究（NN/g，转引待核实）指出：**用户声称引用增加信心，但实际很少真去点验**——引用是"信任信号"多过"验证工具"，别把责任转嫁给用户 |
| AI 生成物视觉标记 | 斜体 / 图标 / 边框区分 AI 产出与原文 | Apple 在通知摘要翻车后正是补了斜体标记（见第六节）；但**标记解决的是"识别"，不解决"准确"** |
| 差异视图（diff） | 改了什么，红绿高亮 | 对"修改型" agent 是最强的信任装置 |
| 多候选并排 | 给 2-3 个方案让人选 | 降低"一次生成必须对"的压力，同时暗示"这是概率产物" |
| 结构化输出而非纯文本 | 表格/卡片/图表代替一段话 | 更易扫读、更易验证、更易被下游复用 |
| 非 AI 兜底 | AI 不可用时仍有传统路径 | Apple HIG 举例：Genmoji 旁边永远留着普通 emoji |

### 2.4 控制侧：Human-in-the-loop 的分级（**本篇与 [[Confirmation UI 分级与产品责任边界]] 的接口**）

| 模式 | 一句话 | 适用档位 |
|---|---|---|
| 自动执行（fire-and-forget） | 不打断，事后可查 | 可逆 + 低代价 + 高置信 |
| 事后通知（notify-after） | 做完了告诉你，附撤销入口 | 可逆 + 中低代价 |
| 执行前确认（confirm-before） | 关键动作弹一次闸 | 不可逆 或 有外部可见副作用 |
| 逐步确认（step-by-step） | 每步都批 | 新用户期 / 极高风险 / 调试期 |
| 预览与 dry-run | 先给"如果执行会发生什么"的模拟结果 | **代价高但可预演**的任务，性价比最高的一档 |
| 撤销（undo） | 单步撤销，不需要整会话重置 | 应是**默认能力**而非高级功能 |
| 检查点 / 回滚（checkpoint） | 多步任务的存档点 | 长链路 agent 必备 |
| 权限授予粒度 | 按资源域 / 按动作类型 / 按时间窗 / 按金额阈值 | 见下方"授权四轴" |
| 渐进式授权（progressive delegation） | 权限随可靠性记录扩张 | 行业里反复出现的建议：**开局就给全自主 = 低采纳 + 低信任** |
| 全局开关（kill switch） | 一键关掉全部 agent 行为 | HAX Guideline 17「Provide global controls」的直系后代 |

**授权四轴（我自己的归纳，供 Figma 原型时当参数用）**：
- **域轴**：能碰哪些应用 / 目录 / 账户
- **动作轴**：只读 / 写入 / 发送 / 支付 / 删除
- **阈值轴**：金额、条数、影响人数
- **时间轴**：单次 / 本会话 / 30 天 / 永久

> 📌 **分工声明**：本篇只做"控制模式有哪些"的**版图铺陈**。"哪一档确认对应哪一级产品责任、出事了算谁的、法务/合规如何切分"——这些属于 [[Confirmation UI 分级与产品责任边界]] 的范畴，本篇不重复。做具体 agent 动作的安全设计时，走 [[Agent 执行安全（PM视角）]]。

### 2.5 失败侧：agent 一定会出错，UX 决定出错的代价

| 模式 | 一句话 | 典型坑 |
|---|---|---|
| 优雅降级 | 不确定时**缩小服务范围**而不是硬编 | HAX Guideline 10「Scope services when in doubt」正是这条 |
| 高效纠错 | 让人能就地改，而不是重开一轮 | HAX Guideline 9；重新 prompt 是**最昂贵的纠错方式** |
| 具体错误信息 | Apple HIG 举例：「抱歉，鸡汤面卖完了」优于「抱歉，无法完成订单」 | 泛化错误文案 = 把排障成本丢给用户 |
| "卡住了"的处理 | 超时 / 循环 / 等外部响应，三种要分开表达 | 沉默的进度条是信任杀手；至少要能"告诉我卡在哪一步" |
| 部分完成的表达 | 5 步做完 3 步失败 2 步，状态要能分别看 | 二值化的"成功/失败"在多步 agent 里是错误抽象 |
| 失败的可逆化 | 失败后自动回滚到检查点 | 比"报错让用户自己收拾"高一个量级 |
| 无感知错误的暴露 | PAIR 提的"后台错误"：系统没干对但用户没察觉 | **最危险的一类**，尤其在 OS 级后台 agent 上 |
| 升级到人 | 无法完成时明确交还控制权 | 别让 agent 假装还在努力 |

### 2.6 信任侧：用户凭什么敢用

| 模式 | 一句话 |
|---|---|
| 能力边界表达（capability discovery） | 用户怎么知道它能干什么？——示例输入、模板、能力卡片、首用引导（HAX G1） |
| 能力**可靠度**表达 | 不只是"能做什么"，还有"多久会错一次"（HAX G2，最常被跳过的一条） |
| 心智模型建立与纠偏 | 用户是把它当"搜索引擎"还是"朋友"？PAIR 明确指出 Gemini 用户存在这两种分裂的心智模型 |
| 拟人化的剂量控制 | 拟人化降低理解门槛，但抬高不合理预期。有研究（转引待核实）提示：**用户信任表现出胜任力的 agent，而非表现出温度的 agent** |
| 解释的克制 | PAIR 原则：解释是为了**理解**而非**完整**——只讲用户决策所需的信息 |
| 一致性 | 同一动作每次表现相似；probabilistic 系统要靠 UI 兜出可预期性 |
| 变更告知 | 能力增删要通知（HAX G18）、更新要谨慎（HAX G14） |
| 反馈闭环 | 粒度化反馈（HAX G15）+ 让用户看到反馈生效（Apple HIG 2026 新增） |

## 三、官方设计指南横向对比

### 3.1 三大厂对比表（硬核对照）

| 维度 | **Microsoft HAX Toolkit** | **Google PAIR — People + AI Guidebook** | **Apple HIG** |
|---|---|---|---|
| 出品方 | **Microsoft Research**（不是 Fluent 设计团队） | **Google PAIR (People + AI Research)** 团队（不是 Material 团队） | Apple Design / Developer Relations |
| 载体 | microsoft.com/en-us/haxtoolkit | pair.withgoogle.com | developer.apple.com/design/human-interface-guidelines |
| 核心结构 | **18 条 Guidelines for Human-AI Interaction** + Design Library（模式与案例）+ Playbook / Workbook（团队工作坊） | **6 章**（用户需求与成功定义 / 数据收集与评估 / 心智模型 / 可解释性与信任 / 反馈与控制 / 错误与优雅失败）；有说法为 6 章 23 条原则（待核实） | 按页面组织：**Generative AI**、**Siri**、**App Shortcuts**、**Snippets**、Machine learning 等 |
| 起源与迭代 | 源自 CHI 2019 论文（Amershi et al.），是三家里**学术根基最扎实**的一套 | 2019 年首发；生成式 AI 浪潮后访问量激增，内容持续扩充 | Generative AI 页 **2025-06-09 首发，2026-06-08 更新**；Siri 页 **2026-06-08「Revised for Siri AI」**；Snippets 为 2026-06-08 **新页** |
| 抽象层级 | **准则 → 模式 → 案例**，三层可落地，可直接当 checklist 用 | **方法论 + 工作坊**，偏"怎么把团队组织起来想清楚" | **规范 + 平台能力绑定**，最贴具体实现（App Intents / schemas） |
| 对 Agent 自主性的直接覆盖 | 部分（准则写于 agent 时代之前，但 G7-G11「出错时」一组高度适用） | 部分（"自动化 vs 增强"的权衡讲得清楚） | **较直接**：明确要求「执行不可逆任务前获得许可」 |
| 最适合拿来干什么 | **评审 checklist**、跨团队共同语言 | **前期问题定义**、心智模型与信任策略 | **落地时的具体规范**，尤其 iOS 侧 agent 集成 |
| 局限 | 偏"AI 功能"而非"多步 agent"，缺并行/长任务范式 | 抽象度高，落到控件级要自己补 | 平台绑定强；**Generative AI 页面竟无 citation/溯源相关指引**（我逐页核过） |

> **一个容易搞混的点（归属纪律）**：
> - **HAX Toolkit → Microsoft Research**，不是 Fluent Design。
> - **People + AI Guidebook → Google PAIR**，**不是 Material Design**。
> - **Material 3 Expressive → Google Material 团队**，它是**视觉/动效语言，不是 AI 交互准则**——别把它当 AI 设计指南引用。
>
> 也就是说：Google 的"AI 该怎么交互"住在 PAIR，"AI 界面该长什么样"住在 Material，两者**没有合并**。这本身就是个信号：连 Google 内部都还没把 Agentic UX 收编进主设计系统。

### 3.3 Apple 侧：2026 年的实际动向（对 OS 级 agent 最相关）

核实自 Apple Developer「What's new」变更日志（2026-06-08 批次）与两个 HIG 页面正文：

| 项 | 内容 | 对 PM 的含义 |
|---|---|---|
| HIG「Generative AI」更新 | 新增"**让用户细化结果 + 生成过程中提供反馈**"指引；更新"选择模型类型"指引 | 官方把 **refine / revert / retry** 抬成了标准动作，不是加分项 |
| HIG「Generative AI」原有硬条款 | **执行不可逆任务前必须获得许可**（举例：删照片、代下单）；错误要用平实语言说明并给下一步；AI 不可用时要有非 AI 兜底 | 与本篇 2.4「控制侧」完全同构 |
| HIG「Siri」修订 | 标注为「**Revised for Siri AI**」；Siri AI 由 Apple Intelligence 驱动 | Siri 正式从"语音命令"转向"系统级 agent" |
| App Intents + **app schemas** | 应用把 actions（intents）与 content（entities）暴露给系统；schema 是系统已理解的**预置模板** | 这就是 OS 级 agent 的"能力注册表"。见 [[Apple Intelligence 与 App Intents]]、[[App Intent 的核心作用]] |
| 屏上实体标注 | 应用给视图标注 entities，Siri 才能理解"这个/它" | **跨应用指代**的技术前提 |
| **Snippets（2026-06-08 新页）** | Siri 响应中可展示的静态/交互式片段 | agent 的"结果不必回到 App"——OS agent 的输出容器 |
| Liquid Glass 的一年期中考 | iOS 26 引入后可读性受批评；据报道 iOS 27 重修材质扩散、加暗边、增强高光，并在设置中提供**透明度滑杆** | 视觉语言层的教训：**新颖性不能牺牲可读性**——AI 界面同理 |

> Apple 的 Siri 文案规范里有几条对做中文 agent 也直接可抄的：追问要具体（「哪种汤？」而非「哪一个？」）；选项太多时改问开放式问题；错误要具体到原因；回答要设备无关（可能在 AirPods 上只有语音）。

## 四、自主性光谱（autonomy spectrum）

### 4.1 分级表

| 档位 | 名称 | agent 做什么 | 人做什么 | UI 重心 | 典型例子 |
|---|---|---|---|---|---|
| **L0** | 纯工具 | 什么都不主动做 | 全手动 | 传统 UI | 普通设置页 |
| **L1** | 建议（Suggest） | 给建议，不动手 | 采纳/忽略 | 内联建议、一键接受 | Gmail Smart Reply、代码补全 |
| **L2** | Copilot（受命执行） | 执行单个明确指令 | 下令 + 验收 | 结果 diff、撤销 | "把这段改成正式语气" |
| **L3** | 半自主（Plan-and-Confirm） | 自己拆步骤，关键步骤前停下 | 批计划 + 批关键动作 | **计划预览 + 确认闸门 + trace** | 多步任务型 agent（当前主流落点） |
| **L4** | 高自主（Supervised Autopilot） | 全程自己跑，只在触发阈值时求助 | 事后审阅 + 异常介入 | **活动流 + 检查点 + 回滚 + 全局开关** | 后台常驻 agent |
| **L5** | 全自主（Autopilot） | 完全不打扰 | 事后不看 | 只有审计日志 | 目前**几乎不应该**用在消费级系统 agent 上 |

> 我的判断：2026 年消费级 OS agent 的**合理落点是 L2–L3**，L4 只应在"可逆 + 低代价 + 用户显式开启 + 有完整活动流"四条同时满足时启用。任何把 L4/L5 当作默认卖点的方案，都是在用用户的信任额度做投机。

### 4.2 判断维度：什么任务该放在哪一档

四个维度打分（我建议做成 Figma 里的一个评估卡片组件）：

| 维度 | 问题 | 低分（→ 低自主档） | 高分（→ 可高自主档） |
|---|---|---|---|
| **可逆性** | 做错了能撤回吗？撤回的窗口多久？ | 已发出的消息、已完成的支付、已删除的数据 | 草稿、本地整理、可回滚的配置 |
| **代价** | 错了的后果多大？谁承担？影响多少人？ | 涉钱、涉隐私、涉对外可见、涉他人 | 只影响自己、只是浪费几秒 |
| **用户熟悉度** | 用户干过这事吗？知道正确结果长什么样吗？ | 新场景、用户无法判断对错 | 高频熟练任务，一眼能验收 |
| **agent 置信度** | 模型对本次任务的把握 + 历史成功率 | 长尾意图、跨应用链路长、依赖外部不确定状态 | 短链路、schema 覆盖、历史成功率高 |

**组合规则（简化到能直接拍板）**：

| 可逆性 | 代价 | 建议档位 | 必备 UI |
|---|---|---|---|
| 可逆 | 低 | L4 自动执行 | 事后通知 + 撤销入口 + 活动流可查 |
| 可逆 | 高 | L3 执行前确认 | 计划预览 + diff |
| **不可逆** | 低 | L3 执行前确认 | 一次明确闸门（哪怕代价低） |
| **不可逆** | **高** | **L2 或逐步确认** | 计划预览 + dry-run + 逐步闸门 + 二次确认 |

> 两条修正项：
> - **用户熟悉度低** → 整体降一档（他没法验收，就别让他事后担责）。
> - **agent 置信度低** → 不是降档那么简单，而应触发 HAX G10「**Scope services when in doubt**」：**缩小服务范围**或转入消歧，而不是硬着头皮低置信度执行。
> - 档位应随时间**可上调**（渐进式授权），但升档要用户显式同意，不能靠产品悄悄放宽。

## 六、失败案例与批判（仅公开报道，客观陈述）

> 用途：这些不是段子，是**"UX 设计不到位会以什么形式变成公共事件"**的样本。均为公开媒体报道，我不做未经证实的指控。

| 案例 | 公开报道的经过 | 报道来源性质 | UX 教训 |
|---|---|---|---|
| **Apple Intelligence 通知摘要（2024-12 → 2025-01）** | 据 BBC、Guardian、AP 等公开报道：通知摘要功能生成了与 BBC 报道不符的内容（含一条关于 Luigi Mangione 的错误表述），且**顶着 BBC 的品牌出现在锁屏**；另有报道称 NYT 相关摘要出现错误表述。BBC 正式投诉，无国界记者组织（RSF）、英国全国记者工会（NUJ）公开呼吁调整/下线。Apple 随后在 iOS 18.3 / iPadOS 18.3 / macOS 15.3 测试版中**临时下线"新闻与娱乐"类别的通知摘要**，并加入斜体标记、beta 提示、锁屏上按 App 关闭摘要等改动 | 主流媒体报道 + Apple 官方声明 | ①**摘要会借用双重权威**（Apple 的 + 发布方的），错误代价被放大；②**默认开启 + 系统级分发 = 无法靠"用户不用"止损**；③事后补的斜体标记解决的是"能不能认出是 AI"，**不解决"内容对不对"**；④压缩类功能在**高风险信息域**（新闻/医疗/金融）需要单独的风险分级 |
| **Windows Recall（2024-05 → 2025-04）** | 据 TechRepublic、TechSpot、Computing 等公开报道：2024 年 5 月 Build 发布，因隐私与安全质疑（早期版本被研究者指出敏感数据存储保护不足）多次推迟；后改为**默认关闭 + 需手动 opt-in**、本地加密、Windows Hello 认证、可排除应用/网站、可完整卸载，2025 年 4 月面向 Copilot+ PC 开放。此后仍有安全研究者提出新的取数路径质疑，据报道 Microsoft 将其判定为"非漏洞"（**此后续争议为二手报道，待核实**） | 科技媒体报道 + 安全研究者公开材料 | ①**默认开启是隐私功能的原罪**——从 default-on 改 opt-in 是这个案例最大的产品修正；②"数据只在本地"**不等于**用户感到安全，感知安全需要单独设计；③一个功能的**信任一旦透支，后续再多安全措施也难以回收** |
| **Google AI Overviews 早期错误（2024-05）** | 据当时大量公开报道，搜索结果页的 AI 概览生成过明显荒谬的建议（最广为流传的是"在披萨上加胶水"一类），Google 随后收缩了触发范围 | 主流媒体报道（本次未逐条回溯原始出处，**细节待核实**） | **把生成内容放在最高权威位置（搜索结果第一屏）＝把幻觉直接升格为"官方答案"**。位置本身就是信任声明 |

**共同规律（我的归纳）**：
1. 三个案例全部是**默认开启 + 系统/平台级分发**，用户无法自然规避。
2. 三个案例的翻车点全部不在"模型不够强"，而在**"放置位置的权威性"与"模型可靠性"不匹配**。
3. 三个案例的修补动作高度一致：**降低默认开启 → 增加视觉标记 → 增加粒度化关闭入口 → 缩小适用范围**。这四步基本可以当成 AI 功能的**危机预案模板**提前写进设计稿。

## 七、对 OS 级 Agent 的意义（本篇最该被反复读的一节）

### 7.1 系统级 agent vs App 内 agent 的 UX 差异

| 维度 | App 内 Agent | **OS 级 Agent** | 设计后果 |
|---|---|---|---|
| 作用范围 | 单应用沙箱内 | **跨应用、跨账户、跨数据域** | 一次授权可能连带打开一串门；需要**按域/按动作**的分轴授权，而非一个总开关 |
| 权限敏感度 | 应用自有数据 | 通讯录、位置、相册、消息、支付、屏幕内容 | 权限本身要成为**一级界面**，不能藏在设置三级页 |
| 失败面 | 局部，用户能看见 | **可能在用户不看屏幕时发生，跨应用连锁** | 必须有系统级活动流 + 检查点 + 跨应用回滚（后者是真正的难点） |
| 归因难度 | 出错知道是哪个 App | **用户分不清是 agent 错、App 错、还是系统错** | 责任表达要在 UI 上前置——这直接接到 [[Confirmation UI 分级与产品责任边界]] |
| 信任预期 | "这是个第三方工具，出错正常" | **"这是系统，系统不该出错"** | 同样的错误率，OS 侧的**主观容忍度显著更低** |
| 退出成本 | 卸载 App 即可 | **换手机才能躲开** | 必须提供彻底的关闭/卸载路径（Recall 案例的核心修正） |
| 可发现性 | App 内引导 | 用户不知道系统 agent 能干什么 | 能力边界表达（HAX G1/G2）在 OS 侧难度**高一个量级** |
| 能力来源 | 自己实现 | **依赖三方 App 注册意图/实体** | 能力版图是动态的、参差的 → "它能不能做 X"这个问题**本身就没有稳定答案**，UI 要能表达"部分支持" |
| 打断权 | 只能在 App 内 | **可占用锁屏、通知、状态栏** | 打断预算是系统级稀缺资源，需要中央调度 |

### 7.2 这如何影响确认机制的设计（可直接进原型的五条）

1. **确认档位必须由"动作"决定，不能由"应用"决定。**
   系统 agent 跨应用执行时，同一条链路里可能混着"读日历（可逆低代价）"和"发消息（不可逆外部可见）"。**闸门要下在动作粒度上**，而不是"这个 App 我信任所以全放行"。

2. **跨应用链路要有"链路级预览"，而不只是"步骤级确认"。**
   逐步确认在跨 5 个应用时会退化成疲劳点击，用户会开始无脑点"允许"——**确认疲劳本身就是安全漏洞**。更优解：一次**计划预览**（把全链路摊开）+ 只对不可逆节点单独设闸。

3. **系统级 agent 必须有常驻可见的运行指示器。**
   参考"正在录音/正在定位"的既有心智模型——用户已经被训练过认这类小圆点。**复用已有心智模型比发明新的便宜得多**。

4. **撤销必须做到跨应用。**
   "系统 agent 帮你在 A 里改了、在 B 里发了"，如果撤销只能在各 App 里分别做，等于没有撤销。**跨应用撤销做不到的动作，就不该给到 L3 以上的自主档**——这是我认为最硬的一条产品红线。

5. **能力边界要能表达"部分支持"。**
   由于能力依赖三方注册（App Intents / schemas 这类机制），系统 agent 的真实能力是**参差且随安装列表变化的**。UI 需要一个诚实的三态：**能做 / 不能做 / 这个 App 没接**。第三态最容易被产品经理跳过，但它恰恰是用户困惑的最大来源。

## 待解问题

- [ ] **跨应用撤销**到底能做到什么程度？哪些动作物理上不可撤销（已发消息、已支付、已通知对方），产品上是否应直接禁止进入高自主档？需要一份「不可撤销动作清单」。
- [ ] **确认疲劳的临界点在哪**？逐步确认在几步之后开始退化为无脑点击？有没有公开的实证研究，还是必须自己做（走 [[用户研究方法 学习笔记]]）？
- [ ] **不确定性的视觉表达**：数字置信度、措辞对冲、视觉弱化，三种方式在中文语境下哪种最不容易被误读？需要做对比测试。
- [ ] **主动触发的打断预算**如何在系统层做中央调度？多个 agent 竞争同一块锁屏/通知位时的优先级规则怎么定？
- [ ] **"部分支持"的三态表达**用什么控件？用户如何理解"这个 App 没接入所以我做不了"而不迁怒于系统？
- [ ] **agent trace 展示到什么颗粒度**？全量工具调用会吓到普通用户，摘要级又不足以排障——是否需要"普通/开发者"双档？
- [ ] **渐进式授权的升档触发条件**：靠成功次数、靠用户显式操作、还是靠置信度模型？升档的 UI 时机怎么选才不显得在"套路用户放权"？
- [ ] **Generative UI 的设计交付物形态**：界面运行时组装后，Figma 里交付什么？规则 + 状态机 + 护栏清单，具体模板长什么样？（这条最直接影响 Ethon 的日常产出）
