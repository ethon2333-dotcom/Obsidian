# GUI Agent vs 原生 API 产品决策树

> 作为 PM，核心决策：**一个用户任务，优先走原生意图 API，还是允许 GUI Agent 视觉点击兜底？**
> 技术底子见 [[端侧执行通道 GUI 与 MCP 路线之争]]；安卓落地架构见 [[安卓厂商意图识别破局策略]]。

## 决策树
1. **该 App 是否已开放原生 Intent / Schema，且覆盖本任务？**
   - 是 → **强制走 L1 原生 API**（高稳定、低延迟、隐私可控）。✅ 不允 GUI 抢跑。
   - 否 → 2
2. **是否有可用的 DeepLink / URL Scheme / 系统服务（通知、剪贴板）能直达目标页？**
   - 是 → **走 L2 深层协议**（免打开 App 全界面，体验接近原生）。
   - 否 → 3
3. **是否是不可逆 / 高敏感动作（支付、删除、发消息）？**
   - 是 → **禁止 L3 GUI 自动执行**，改为「自动填参 + 跳 App 原生界面让用户最后点确认」（商业上也不破坏 App 转化）。
   - 否（低敏、可重试，如查信息、加提醒）→ **允许 L3 GUI Agent 兜底**，作为体验保底。

## PM 视角的关键权衡
- **稳定性 vs 覆盖**：原生越全，体验越稳；GUI 兜底保证「没适配也能动」，但慢、易因改版失效。
- **商业博弈**：强行 GUI 会逼大厂对抗（反无障碍/反爬）；用「导流倾斜 + 利益共享」拉拢开放原生（见 [[国内安卓厂商做 App Intent 的阻力]]）。
- **体验底线**：GUI Agent 必须做「工业级」（无障碍树 + 端侧 VLM 双引擎、状态校验自愈），否则是玩具。

## 指标
- L1/L2 占比、L3 触发率、L3 任务成功率、因 App 改版导致的 L3 失效次数。

## 深化补充（2026-08）

### 一句话心智模型
**这不是技术选型，是生态位选型。** 走结构化通道要和 App 谈判（签约/授权），走 GUI 不用谈但会被风控封。同一个能力，两条路的成本科目完全不同：一个是 BD 成本，一个是被封禁的期望损失。

### 决策树要补的一层：MCP / 跨端协议是独立的第二通道
原树把 L2 写成「DeepLink / URL Scheme」。2026 的现实是第二通道已经升级为**协议级对接**——支付宝 **AHA** × OPPO 小布（小布理解需求、阿宝调用支付宝生活服务）、Windows 的 **ODR + MCP 连接器**、Android AppFunctions 官方定位就是「MCP 中工具的移动端等效实现」。

**修订后的三通道对照：**

| 维度 | ① 官方 Intent/Function | ② MCP / 跨端协议 | ③ GUI 模拟 |
|---|---|---|---|
| 可靠性 | 最高（结构化返回） | 高 | 受 UI 改版影响 |
| 覆盖面 | 仅已适配 App | 已接协议方 | 理论全覆盖 |
| 准入成本 | 需 App 适配/授权 | 需协议对接 | **无需对方同意** |
| 风控风险 | 无 | 低 | **高（可被封禁）** |
| 可审计 | 强 | 强 | 弱 |
| 适用任务 | 支付/交易/写操作 | 跨生态服务编排 | 长尾只读/低风险 |

**决策顺序：官方 Intent → MCP/协议 → GUI。** 只有「无官方通道 + 任务低风险 + 可容忍失效」三条**同时**成立才用 GUI。

### 2026 的三条实证（支撑上面的决策顺序）
1. **官方架构已给出同构分工**：Google 明确 `actions.xml` **已弃用**；**built-in intents** = 拉起并履约，**AppFunctions** = 带类型参数调用 + 返回结构化结果，**UI Automation** 只作未适配长尾兜底。潜台词：「**你不接入也有覆盖，但失去对执行方式的控制权**」。
2. **能力天花板已抬高，厂商反而在撤离 GUI**：OSWorld 2026-07-31 首破 **90.2%**（⚠️ 媒体口径，官方榜单**待核实**）；同期豆包手机二代 NaviX Ultra **放弃一代 GUI 视觉模拟、改用 MCP 与 App 官方接口直连**，公开动机是**规避风控封禁**。→ **能力问题在收敛，准入问题在恶化。**
3. **准入边界被公开可视化**：华为小艺「帮帮忙」实测可 GUI 操作支付宝/淘宝/拼多多，**微信提示「尚未接入」**。

### 对第 3 步（高敏动作）的加强
原树只说「禁止 L3 自动执行高敏动作」。补两条更硬的判据：
- **确认要落在被调用 App 的原生界面**（支付停在支付 App），责任链才清晰、可审计、可追责。WAIC 演示（Amoo × 美团跑腿）就是这么停的。
- **三分边界已成行业共识**：**系统理解意图 / App 保留履约与支付 / 用户保留最终决定权**。这三条同时也是商业上不破坏 App 转化的设计——安全和商业在这里是一致的，不是取舍。

### 指标补三条
- **风控封禁事件数 / 被反制次数**（反无障碍、反爬检测触发）——L3 的真实成本科目。
- **准入谈判进度**：已开放官方通道的 App 覆盖的任务量占比（比 App 家数更有意义）。
- **L3 → L1 转化率**：用 L3 的真实调用数据反推「该优先游说哪些 App」，并追踪游说成功率。**GUI 本身不是解法，是筹码和探针。**

### 待解问题
- [ ] 「GUI 不做写操作和支付」是安全上的正确答案。但**用户不理解通道差异**——他会问「你能帮我在淘宝下单吗」。产品上怎么把这条边界表达成用户能接受的话术，而不是「本功能暂不支持」？
- [ ] 如果某个高价值 App 永远不开放官方通道，**是接受能力缺口，还是承担封禁风险硬上 GUI**？这个决策该由谁签字（PM？法务？还是业务一号位）？我们有没有一个明确的风险接受门槛？
- [ ] 三通道的**降级是自动的还是可解释的**？用户看到的是「悄悄变慢了」还是「这次走的是兼容模式，可能出错」？后者更诚实但会暴露能力短板——**这个取舍我还没想清楚。**
