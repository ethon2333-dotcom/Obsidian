# 增长模型 学习笔记

> 学习定位：这是一篇**广度种子笔记**——把增长领域最主流的几套模型（AARRR / RARRA / 北极星 / Aha Moment / 增长飞轮 / 漏斗与复利）**先铺开、建地图、标边界**，各自的深度（指标口径、阈值、实验方法）留白给后续补充。
> 本文是 **own-words 综合**，不是情报简报。具体数字凡来自媒体/三方口径的，一律标「⚠️ 待核实」，不编造。

---

## 一、一句话心智模型

**增长模型 = 把「用户从哪来、为什么留下、怎么带来更多」这件事，从玄学变成可拆解、可度量、可优化的结构。**

更直接一点：

> **漏斗负责"找漏点"，飞轮负责"滚复利"，北极星负责"对齐所有人朝同一个数使劲"。**
> 三件事不互斥：先拿漏斗找到最漏的那一段，用北极星对齐资源，再用飞轮把留存好的部分转成复利。

## 二、主流增长框架（表格）

> 这一节只给"是什么 + 边界"，深度（具体指标、阈值、实验设计）见第七节待解问题。

| 框架 | 提出 / 起源 | 核心逻辑 | 一句话定位 |
|---|---|---|---|
| **AARRR 海盗模型** | Dave McClure（500 Startups），约 **2007** 年 "Startup Metrics for Pirates" 演讲 | 漏斗五段：**获客 A**cquisition → **激活** A ctivation → **留存** R etention → **收入** R evenue → **推荐** R eferral | 诊断"漏斗哪一段在漏"的标准五问 |
| **RARRA** | Thomas Petit & Gabor Papp，约 **2017** | 把 AARRR **重排为 留存→激活→推荐→收入→拉新**，留存置顶 | "先把桶补好再倒水"，留存优先的优先级 |
| **北极星指标 North Star Metric** | Sean Ellis（growth hacking 圈，约 2010）/ 2017 起由 Amplitude《North Star Playbook》系统化 | 选**一个**能代表"用户价值被交付"的核心指标，全公司对齐 | 全公司只朝"一个数"使劲的指南针 |
| **Aha Moment（惊喜时刻）** | Facebook / Twitter / Dropbox 增长团队实践中提出 | 用户**首次感知产品核心价值**的那个具体行为事件 | 激活（activation）的"可测量代理"——你量不了感受，只能量行为 |
| **增长飞轮 Flywheel** | Jim Collins《从优秀到卓越》(2001) 提出概念；贝佐斯约 2001 年画在餐巾纸上落地为亚马逊飞轮 | 多个相互强化的要素形成**正反馈循环**，缓慢启动后自我加速 | 复利式增长，而非线性漏斗 |
| **漏斗与复利模型** | 概念层（非单一作者） | 把"线性漏斗诊断"与"网络效应/复利的叠加"分开算账 | 既看漏点（漏斗），也看复利（效应） |

**三句关键纠偏（最容易讲混的）**

1. **AARRR 与 RARRA 覆盖的是同一组指标**，区别只在"排序/优先级"：AARRR 偏"诊断框架"，RARRA 偏"资源投放顺序"。不是两套独立理论。
2. **Aha Moment ≠ 激活**：Aha 是"感受到价值"的瞬间（概念），激活是你选来**代理**它的那个可度量行为（如"7 天内加 7 个好友"）。量的是行为，不是感受。
3. **北极星指标 ≠ 收入**：收入是滞后指标；好的北极星是"用户价值"的先行指标（如 Airbnb 的"预订晚数"、Slack 的"团队发消息量"）。

## 三、各框架适用场景

| 框架 | 最适合 | 不太适合 / 注意点 |
|---|---|---|
| **AARRR** | 早期产品、需要快速定位"增长断在哪一段"；团队需要统一语言（市场管获客、产品管激活、客户成功管留存） | 易被当成"必须按序修完"的瀑布；它对电商复购、企业大客户增购（upsell）覆盖较粗 |
| **RARRA** | 拉新成本（CAC）高、留存差的 App / 订阅制 / PLG 产品；"不投广告就不增长"的困局 | 当产品尚处"有没有人要用"阶段，空谈留存无意义——先有 PMF 再谈 |
| **北极星指标** | 多团队（产/研/营/销）需要对齐、避免各自追不同 dashboard 的中大型产品 | 选错（选成虚荣指标或纯收入）比没有更糟；需配 3–5 个"输入指标"拆解才可落地 |
| **Aha Moment** | 设计 onboarding、压低早期流失的所有产品；是激活工作的最高杠杆点 | 阈值因产品而异，**不能照搬别人家的数字**（Facebook 的 7 好友 ≠ 你的阈值） |
| **增长飞轮** | 平台型 / 有网络效应 / 生态型业务（市场、OS、硬件+服务）；用于战略对齐与资源优先级 | 飞轮是**假说不是事实**，每段 A→B 的因果需数据验证；起点若建立在"投放买量"上，本质还是线性增长 |
| **漏斗 + 复利** | 既要做精细化漏斗诊断、又要评估网络效应 / 口碑复利的产品 | 两者常被混为一谈——漏斗看"转化效率"，复利看"自传播系数"，要分开建指标 |

## 四、OS / 系统产品增长的特殊性

OS / 系统级产品的增长，和纯 App / SaaS 有结构性差异——**它同时是"产品"和"分发基础设施"**。

**（1）预装 = 获客被前置，但留存规则不变**
- 预装把 AARRR 的 Acquisition 几乎"免费"前置了——用户开箱即"已获客"。
- ⚠️ 但预装解决不了 Activation / Retention：被塞进来的用户若没走到 Aha Moment，依然是"装机量"这种虚荣指标。预装是放大器，**放大的是已有的留存质量，不是替你补留存**。
- → 对 OS PM 的启示：预装之后的"首次激活路径"（默认开启什么能力、首屏引导什么价值）才是真正该优化的漏斗段。

**（2）分发 = OS 自己就是增长引擎**
- 系统级入口（应用商店推荐位、系统搜索、默认 App、负一屏、设备侧意图框架）本质上是**把"获客渠道"内化到系统里**。
- 这带来一个 AARRR 框架里没有的变量：**分发权本身即是增长杠杆**，且掌握在 OS 厂商手里。
- 与库内 [[端侧意图路由选型 PM Checklist]] 的关联：当 App 能力被 OS 以"工具"形式调度，入口价值从 App 图标向系统 Agent 转移，增长模型要从"App 自己拉新"转向"被系统分发/被 Agent 调用"。

**（3）生态飞轮 = OS 的增长飞轮长这样**
- 经典亚马逊飞轮：**更低价格 → 更多用户 → 更多卖家 → 更丰富选品 → 更好体验 → 更低成本**，自我强化。
- OS 版飞轮（待我后续补一版完整图）：**更多设备装机 → 更大用户基数 → 更多开发者/应用接入 → 更丰富的能力与生态 → 更强用户留存与换机黏性 → 更多装机**。
- 关键点：OS 飞轮的"限速节点"往往是**开发者生态规模**与**杀手级系统能力**，而非单纯营销获客——这点和纯 App 把预算砸在 Acquisition 上截然不同。

> **PM 判断**：OS 产品的增长难点不在"把人引进来"（预装+分发已解决），而在"让被引进来的人真的走到系统核心价值、并形成生态正循环"。所以 OS PM 应更重 **RARRA（留存优先）+ 飞轮（生态复利）**，而非 AARRR 的"获客优先"心智。

## 五、2025—2026 与 AI 产品增长

> 这一节的数字多来自 2026 媒体/机构口径，凡未对上一手源的，一律「⚠️ 待核实」，见文末清单。

**（1）PLG 进入 2.0 / 3.0（AI 原生）**
- **PLG 1.0**：产品帮用户"减少操作步骤"达成价值（用户自己 build）。
- **PLG 2.0**：**AI 完成大部分工作，用户从"建造者"变"编辑者"**——产品先给一份 AI 生成结果，用户再改。代表：Cursor、Lovable、Harvey。
- **PLG 3.0（概念中）**：产品面向 **AI Agent** 编排，人类只 review 输出（Reviewer）。
- 相关提法：**"Halving Principle（减半原则）"**——任何能被数字化的任务，"从意图到结果"的时间每隔几年减半，AI 让它"一夜减半"。用户的耐心基准是被上一款 AI 产品训练的，而非被竞品训练的。

**（2）Time-to-Value 被压缩到分钟级**
- 2026 媒体口径：头部 PLG 公司把"首次价值时间"压到 **3–5 分钟以内**，靠产品内嵌 AI 助手实时适配 onboarding。⚠️ 上述 65%+ 激活率、15–25% 激活提升等具体数字为媒体/厂商口径，待核实。
- "可重复的 'Wow，它一直能这样' 时刻"正在取代单一 "Aha Moment"——AI 让产品"懂你的工作方式"，留存来自习惯化而非一次性惊艳。

**（3）AI 增强的 PLG + Sales 混合模型**
- 纯自服务 PLG 对有大企业机会的产品是不完整的；2026 的成熟做法：产品用**用量遥测（telemetry）自动识别扩张信号**（团队级采用增长、付费意愿相关功能使用、参与高峰），再由 AI 在"意图出现的那一刻"触发对应动作（小账户弹升级、中端自动培育、企业派 AE）。
- 这意味着 AARRR 的 Referral/Revenue 段正在被 **AI 驱动的 PQL（Product-Qualified Lead）打分** 重新接线。

**（4）对 OS / AI 系统产品的延伸思考（留白）**
- 设备侧 AI（端侧 Agent）若成为系统级能力，增长飞轮的"杀手级能力"节点会不会变成"本地隐私 + 离线可用 + 一句话完成任务"？→ 见第七节待解问题。

## 七、待解问题

- [ ] **OS 版增长飞轮的"限速节点"具体是什么？** 我上文给的是"开发者生态规模 + 杀手级系统能力"的粗判，但需要一张完整的 OS 飞轮图（装机→用户→开发者→能力→留存→装机），并标出每一段的输入/输出指标。→ 待补。
- [ ] **Aha Moment 在"系统级 AI 能力"上如何定义？** App 的 Aha 是"完成某个动作"（发消息/加好友），但端侧 Agent 的价值是"一句话搞定复杂任务"——它的激活事件该怎么量化？是"首次成功完成跨 App 任务"还是"首次免唤醒触发"？→ 待研究，建议结合 [[用户研究方法 学习笔记]] 的 cohort 方法。
- [ ] **预装用户的留存 cohort 如何隔离分析？** 预装把获客"免费化"后，AARRR 的 Acquisition→Activation 转化率在预装人群上会失真。如何单独建预装 cohort 的激活/留存基线？→ 待核实业界做法。
- [ ] **北极星指标在"OS 厂商"该选什么？** 是"日活设备数""日均系统级任务完成数"还是"生态内第三方调用次数"？不同选择会引导团队走向"堆功能"还是"养生态"，需要一手案例。→ 待补。
- [ ] **PLG 2.0/3.0 的"减半原则"有没有可引用的权威一手源？** 目前来自 ProductLed 的提法（含 ™ 商标式命名），更像方法论主张而非实证研究。→ 待核实是否有一手数据支撑。
- [ ] **AI 产品"北极星"是否应该从"使用量"转向"任务完成率/首次成功延迟"？** 当 AI 替用户干活，DAU 这类指标可能失真（用户未必天天来，但一来就办成大事）。需要重新设计 NSM。→ 待研究。
