# 智能体身份与信任（Agent Identity & Trust）

> **心智模型一句话**：当 Agent 能替你做事，"它是谁、谁授权它、你怎么认出它是 AI" 就成了产品责任与信任的第一道闸门——身份标识、授权委托、人类可识别，是三件必须分开设计的事。

> 本文是「PM 决策层 / 端侧安全」向外辐射的🌱广度种子笔记。它与 [[AI 监管与合规落地 学习笔记]]（监管框架视角）、[[Confirmation UI 分级与产品责任边界]]（人类确认 UX 视角）形成互补：本文聚焦"Agent 身份标识 / 授权委托 / 可识别 AI"的技术与产品机制，不重复监管条文与确认弹窗设计。

## 一、为什么这是个 PM 问题（广度定调）

Agent 从"被调用的一次性工具"变成"能持凭证、跨系统、代用户行动"的长期主体后，传统 IAM 的"人 or 机器"二分法破裂。Gartner 预测到 2026 年底约 30% 企业将部署"最小人工干预"的 Agent（待核实口径，不同机构数字差异大）。PM 需要拍板的不是算法，而是：**给不给它身份、给多大权限、用户怎么知道对面是 AI、出事谁担责。**

## 二、三大类对比（定义 / 分类）

| 维度 | ① 身份标识 Identity | ② 授权委托 Authorization | ③ 人类可识别 Disclosure |
|---|---|---|---|
| 回答的问题 | "它是谁 / 谁造的它" | "它能做什么 / 在谁名下 / 权限多久" | "用户/监管怎么认出这是 AI" |
| 核心机制 | AgentCard、目录身份、硬件 attestation | OAuth 委托、scoped permission、human-in-the-loop | 水印、AI 标识、UI 提示、溯源元数据 |
| 责任落点 | 归属与审计（谁干的） | 最小权限与可追溯（能干多少） | 用户知情权与防欺骗（这是 AI） |
| 库内关联 | [[Agent 身份与硬件级审批]] | [[Agent 执行安全（PM视角）]] | [[Confirmation UI 分级与产品责任边界]]、[[AI 监管与合规落地 学习笔记]] |
| PM 决策钩子 | 是否给每个 Agent 独立身份 vs 共享服务账号 | 权限是静态密钥还是动态委托+可吊销 | 何时强制显式"这是 AI"、水印是否机器可读 |

## 三、主流方案横向表（点到为止，不钻协议细节）

| 方案 / 组织 | 定位 | 关键技术 | 状态（2025-2026） |
|---|---|---|---|
| **Google A2A + AgentCard** | Agent 间通信标准，AgentCard 是"名片" | JSON 元数据（能力/端点/认证/签名），`.well-known/agent-card.json` | 2025-04 Google 发布，2025-06 捐 Linux 基金会；v1.0（2026 初）引入**签名 AgentCard** |
| **Microsoft Entra Agent ID** | 把 Agent 当"一等公民"目录身份 | Agent 身份蓝图、OAuth 2.0（on-behalf-of / client-credentials）、Conditional Access | 2025-05 预览，Ignite 2025 扩展；与 AWS Bedrock、n8n 等第三方集成 |
| **Okta Cross App Access (XAA)** | 扩展 OAuth 管 Agent↔App 连接 | OAuth 授权扩展、企业托管授权（Enterprise Managed Auth，已进 MCP） | 2025-06 发布；2025-09 进 IETF OAuth WG；2025-11 纳入 MCP；2026-06 超 25 家 ISV 接入 |
| **IETF OAuth for Agents** | 委托授权标准草案 | `requested_actor` + `actor_token`（On-Behalf-Of 草案）、AAuth 草案竞争 | 至少两份竞争草案在飞（待核实最终归并） |
| **MCP 鉴权** | Agent↔工具层 OAuth | OAuth 2.1 + PKCE、RFC 8707 资源指示、RFC 9728 受保护资源元数据 | 2026-07 规范 RC；远程 MCP Server 须作 OAuth 2.1 资源服务器 |
| **SPIFFE / SPIRE + TEE** | 工作负载身份 + 硬件锚定 | SVID、远程证明（attestation）、TEE  enclave | 与 OAuth 委托分层使用（"是什么" vs "为谁行动"）；见 [[Agent 身份与硬件级审批]] |

## 四、2025-2026 进展（广度时间线）

- **2025-04**：Google 发布 A2A 协议，提出 AgentCard 发现机制。
- **2025-05**：Microsoft Entra Agent ID 预览；Okta 在 Oktane 推 "Okta for AI Agents" 套件思路。
- **2025-06**：A2A 捐 Linux 基金会；Okta 发布 Cross App Access (XAA)；IBM 的 ACP 并入 A2A。
- **2025-08**：EU AI Act 禁令条款生效（Article 5）。
- **2025-09 / 11**：XAA 进入 IETF OAuth WG，并纳入 MCP 作为企业授权扩展。
- **2026-初**：A2A v1.0，签名 AgentCard、多租户、多协议绑定。
- **2026-06**：EU AI Act **Article 50 透明度义务生效（2026-08-02）**；Code of Practice 于 2026-06-10 发布；Okta XAA 生态扩至 25+ ISV（Anthropic Claude、Slack、Zoom、Cursor、VS Code 等）。
- **2026-02**：NIST 启动 AI Agent 标准倡议（概念 paper，待核实具体产出）。

## 六、与端侧 / 安全的连接点

- **硬件级审批**：端侧 Agent 要"可识别且不可伪造"，趋势是用 TEE/secure enclave 做远程证明（confidentiality + integrity + attestation），把身份锚到处理器硬件根。详见库内 [[Agent 身份与硬件级审批]]。
- **执行安全**：授权委托若用静态密钥、无最小权限、无吊销，就是 [[Agent 执行安全（PM视角）]] 里最大的盲区——Agent 跑在共享 API Key 上、无预算上限、无审计。
- **越狱关联**：端侧模型一旦被越狱，身份与授权机制可能被绕过，呼应 [[端侧模型安全与越狱 学习笔记]]。

## 七、待解问题（BREADTH > DEPTH，留作后续深耕）

- [ ] **跨厂商 Agent 身份互认**：A2A/Entra/Okta 各自发身份，跨云跨厂商如何互信、证书如何交叉验证？（标准未定）
- [ ] **授权吊销机制**：Agent 被 offboard、密钥泄露后，如何在多跳委托链上即时级联吊销？XAA/Okta 路径较清晰，但 A2A 多跳仍依赖各跳 token exchange。
- [ ] **端侧 Agent 硬件锚定成本**：TEE attestation 在手机/端侧 NPU 落地的性能、功耗、芯片依赖与可审计性成本？（待核实实测数据）
- [ ] **多跳委托的可审计性**：Agent 调 Agent 调 Agent，如何保证每跳都留下"带 actor 标识"的归因，而非把用户身份一路冒用？
- [ ] **AI 标识与 UX 的平衡**：EU 要求"首次交互即告知是 AI"，但在 Agent 主动服务/后台动作场景，何时显式、何时仅元数据标记，产品体验如何不崩？
