# 用户研究方法 学习笔记

> 学习定位：这是一篇**广度种子笔记**——目标是把用户研究的「地图」先画全（为什么做、有哪些方法、何时用、核心原则、与 AI 的结合），**深度留白给后续补充**。
> 本文是 **own-words 综合**，不是方法论教科书。经典框架（定性/定量、JTBD、Say-Do gap）是稳定共识；2025-2026 的 AI 结合部分已做检索核实，但凡带百分比的数字均标「待核实」。文末待解问题是我自己的判断缺口。

---

## 一、一句话心智模型

**用户研究 = 在 PM 拍脑袋之前，先向「不是你自己」的真实的人求证。**

PM 最大的系统性盲区是「我 = 用户」的错觉：你懂技术、你有上下文、你天天看数据，但你的目标用户大概率三者都不占。用户研究存在的全部理由，就是**用结构化方式替代直觉**，把需求从「我觉得」变成「我证过」。

三个层层递进的认知：

- **定性**告诉你「为什么」（动机、语境、情绪）
- **定量**告诉你「有多少、多普遍」（规模、显著性）
- **JTBD 视角**告诉你「他其实想雇这个产品去完成什么人生任务」

> 一句最关键的、我自己最容易忘的：**用户说的是一回事，做的是另一回事（Say-Do gap）。** 研究方法的全部分工，本质上都是在对抗这个 gap。

---

## 二、为什么 PM 要做用户研究

| 动机 | 不做的代价 | 研究能补什么 |
|---|---|---|
| **降决策风险** | 凭直觉做方向，错了沉没成本极高 | 用真实信号替代假设 |
| **打破「我即用户」盲区** | PM/工程师偏好 ≠ 大众偏好 | 把"异质用户"拉进决策 |
| **区分 Say 与 Do** | 问卷说"想要"≠ 真用 | 行为数据 + 田野观察兜底 |
| **挖隐性需求** | 只收到"加个按钮"的表层诉求 | JTBD 问出底层任务 |
| **需求优先级有据** | 谁嗓门大谁排前面 | 用频率/痛点强度排序 |
| **避免功能交付陷阱** | 做完没人用，KPI 假繁荣 | 上线前验证Problem-Solution Fit |

> PM 视角一句话：**用户研究不是"锦上添花的可选动作"，而是「需求定义」这道关口的证据底座**——它直接喂给 PRD 里的「背景/问题/目标用户」。深读 [[PRD学习笔记]] 与 [[PM 需求定义 跨学科发散]]。

## 三、研究方法分类（表格：定性 / 定量 / 何时用）

### 3.1 先分清两大家族

| 维度 | **定性 Qualitative** | **定量 Quantitative** |
|---|---|---|
| 问什么 | 为什么、怎么想、什么感受 | 多少人、多普遍、多显著 |
| 样本 | 小（5–30） | 大（数百–数万） |
| 输出 | 主题、故事、洞察 | 统计、分布、显著性 |
| 代表 | 用户访谈、焦点小组、田野观察、可用性测试（少样本） | 问卷调查、A/B、埋点数据分析 |
| 局限 | 不能外推总体 | 说不清"为什么" |

### 3.2 七种常用方法速查

| 方法 | 定性/定量 | 何时用（典型场景） | 最适合回答 | 成本/样本 |
|---|---|---|---|---|
| **用户访谈** 1:1 | 定性 | 早期探索、挖动机、JTBD | "你为什么这么做？" | 中 / 5–15 人 |
| **焦点小组** | 定性 | 看群体互动、态度碰撞 | "大家怎么议论这件事？" | 中 / 6–10 人/组 |
| **田野观察 / 民族志** | 定性 | 真实使用环境、Say-Do gap | "他实际怎么做？" | 高 / 少量深访 |
| **问卷调查** | 定量 | 大规模态度/需求普查 | "多少人这么想？" | 低–中 / 数百+ |
| **可用性测试** | 偏定性 | 原型/界面能否被用懂 | "人卡在哪一步？" | 中 / 5–10 人即可发现多数问题 |
| **A/B 测试** | 定量 | 已上线方案择优 | "哪个转化更高？" | 高（需流量）/ 大样本 |
| **数据分析（埋点）** | 定量 | 行为复盘、漏斗诊断 | "用户在哪流失？" | 中 / 全量 |

> **选型口诀（判断题）**：
> - 还不知道问题是什么 → **定性先行**（访谈/观察）
> - 已有一堆假设要排序 → **定量**（问卷/数据）
> - 界面/流程能不能用 → **可用性测试**（常与 [[Figma 学习笔记]] 里的原型联用）
> - 两个方案赌转化率 → **A/B**
> - 想懂"真实生活里怎么用" → **田野观察**，问卷和访谈都补不到这块

- [ ] **深度盲区**：每种方法的「最小可信样本量」与「统计功效」计算；A/B 的 MDE（最小可检测效应）与流量分配规则——待补一节。
- [ ] **深度盲区**：混合方法（Mixed Methods）设计，定性→定量→定性闭环怎么排期——待补。
- [ ] **深度盲区**：OS/系统级功能（非 App 界面）怎么做用户研究？田野观察与可用性测试的改造——待结合 [[OS产品经理知识库 MOC]] 深想。

## 四、核心原则与常见偏差

### 4.1 操作铁律

- **避免引导性提问**：不问"你是不是觉得这个按钮太丑？"，改问"你第一次看到这个界面时发生了什么？"。引导 = 把你的结论塞进问题里。
- **先听后说**：访谈里 PM 的话越少越好，沉默是合法的追问工具。
- **原话记录 > 你的转述**：引语是 PRD 里最有说服力的证据。
- **招募要对齐目标用户**：别拿同事/亲友当"用户"凑数（见 4.2 样本偏差）。

### 4.2 常见偏差（这张表要常看）

| 偏差 | 是什么 | 怎么缓解 |
|---|---|---|
| **引导性偏差** | 问题/语气暗示"标准答案" | 中性措辞、第三方主持 |
| **招募偏差** | 样本不代表目标人群 | 用画像配额，别只找"方便的人" |
| **幸存者偏差** | 只听到还在用的/愿意填的 | 主动找流失用户、沉默数据 |
| **确认偏误**（PM 自身） | 只收集支持自己判断的证据 | 预设"证伪"目标、双人编码 |
| **社会期望偏差** | 用户说"政治正确"的话 | 行为数据交叉验证 |
| **Say-Do gap** | 说的和做的背离 | 观察 + 埋点，不只靠问卷 |

### 4.3 JTBD 视角（重点）

Clayton Christensen 的 Jobs-to-be-Done：**用户"雇"产品去完成一个任务**，任务的语境（什么时候、和谁、替代方案是什么）比人口统计学标签更预测行为。问"你是什么年龄段"不如问"上次你雇 XX 是为了什么"。

> 这一条直接决定需求挖掘深度：表层诉求（"要更快的马车"）和底层任务（"更快到达"）之间的差，就是产品机会。详见 [[PM 需求定义 跨学科发散]]。

- [ ] **深度盲区**：JTBD 的「开关型访谈（Switch Interview）」具体话术与编码框架——待读 Christensen 原书补一节。
- [ ] **深度盲区**：在 Android OS 场景，JTBD 怎么落到"系统能力/入口"层面而非单 App——待结合知识库思考。

## 五、2025-2026 与 AI 结合

这一节基于 2026-08-06 的公开检索，**趋势判断可信，具体数字标待核实**。

### 5.1 LLM 辅助研究的三个落点

1. **访谈转录与编码自动化**：LLM 把录音转写、做开放式编码（open coding）、抽主题，把研究员从机械劳动里解放出来，只做判断。
2. **跨访谈合成（synthesis）**：把 N 场访谈的引语自动聚类成主题地图，加速"从数据到洞察"。
3. **AI 主持访谈（AI-moderated interviews）**：用 AI 代替人做 1:1 访谈，可多语言、可同时跑上百场、可即时追问——适合规模化但低风险的探索。

### 5.2 合成用户 / Synthetic Users（重点，且要警惕）

- **是什么**：用 LLM 扮演 persona，模拟"用户会怎么反应"，分钟级、零招募成本，用于概念测试、信息排序、定价敏感度初筛。
- **最佳实践（2026 共识）**：**双阶段工作流**——Phase 1 用合成用户快速收窄选项集；Phase 2 用真实用户（或 AI 主持的真实访谈）验证"活下来的方案"。**合成是初筛，不是决策依据。**
- **已文档化的偏差（必须写进纪律）**：
  - **Sycophancy（讨好）**：合成用户倾向于对每个概念都说好，对"找被拒绝的想法"反而有害。
  - **Sign-flipping（符号翻转）**：有研究对比 ChatGPT 生成问卷与真实数据，约 **32% 的效应方向完全反了**——标「待核实」。这意味着基于合成数据的路线图可能"比没有数据更危险"，因为它给你假信心。
  - **无真实生活经验**：合成用户"没有传记"，给不出"上次被某隐藏费用坑了所以弃购"这类来自经历的 why。
  - **训练数据继承偏差**：绕过招募偏差，但继承了训练数据本身的偏差；Nielsen Norman Group 的结论是"对很多研究活动来说太浅、没用"——标「待核实」。

> **PM 判断**：2025-2026 的真相是——**AI 把"做研究的门槛"打下来，但把"解读研究的纪律"门槛抬上去**。合成用户能替你跑量，替不了你把关偏差。高利害决策（合规/医疗/大资金）仍必须真实用户兜底。

- [ ] **深度盲区**：LLM 编码与人工编码的一致性（inter-rater reliability）怎么评估？有没有可复现的基准——待查一手论文。
- [ ] **深度盲区**：合成用户的"样本量"该取多少才有定性可信度（有厂商称 30–100+ persona/研究）——方法论依据待核实。
- [ ] **深度盲区**：在 OS 侧做"合成用户"模拟系统能力接受度，是否比 App 场景更不可靠（用户本就难想象未存在的能力）——待想。

## 七、待解问题

- [ ] **OS 系统级功能怎么做用户研究？** App 界面可用原型+可用性测试，但"负一屏智能入口""系统级 Agent"这类尚未存在的系统能力，用户根本想象不出——田野观察/访谈的范式要怎么改？→ 待结合 [[OS产品经理知识库 MOC]] 深想。
- [ ] **小样本定性研究的"代表性"怎么向老板交代？** 5–10 人访谈常被挑战"代表不了全体"，有没有一套话术/框架把定性结论的"探索价值"和定量的"外推价值"讲清——待补。
- [ ] **JTBD 与埋点数据怎么打通？** 定性挖出的"任务"如何翻译成可观测的行为指标，形成闭环——待补一节。
- [ ] **合成用户时代的"研究伦理/合规"边界在哪？** 哪些决策严禁用合成数据做唯一输入——待查行业规范。
- [ ] **A/B 与用户研究的分工边界**：当 A/B 能直接看行为，什么时候还值得先做定性——待补决策树。
