# 端侧意图路由选型 PM Checklist

> 场景：你要给某个系统能力（或推动某 App）定义「可被端侧 Agent 调起的意图」。下面是要 PM 拍板的项，不是工程实现细节。
> 技术底子见 [[Android AppFunctions 设备侧意图 2026]] / [[Apple AppIntents Schema Protocol 2026]] / [[Intent Schema Protocol 意图模式规范]]。

## 1. Schema 与语义契约
- [ ] 意图是否用**强类型 Schema** 声明（参数名/类型/必填），而非让模型自由生成调用？
- [ ] 是否登记进**系统级 Registry**（如 Android `EXECUTE_APP_FUNCTIONS` Registry），可被全局路由发现？
- [ ] 是否提供**语义索引 / 实体（Entity）** 让跨应用检索能定位到它？（参考 Apple `IndexedEntity` + Spotlight 语义索引）

## 2. Slot-filling 与歧义
- [ ] 必填槽位缺失时，策略是「反向追问用户」还是「用默认值静默补全」？→ **禁止静默默认**（安全红线）
- [ ] 歧义消解（如「明天」指哪个时区/哪张卡）是否定义在产品层，而非丢给模型？

## 3. 路由与降级
- [ ] 是否定义原生 API（L1）→ DeepLink/Schema（L2）→ GUI Agent（L3）的**渐进降级**链路？（见 [[GUI Agent vs 原生 API 产品决策树]]）
- [ ] 路由失败时用户看到什么？失败是否可解释、可重试？

## 4. 端侧 Planner 选型（如需本地决策）
- [ ] 是否要求端侧 Planner 跑**双基准**：BFCL（格式合规）+ NexusRaven（语义理解）？只测 BFCL 会在跨应用编排选错模型。
- [ ] 量化策略按「保 Schema 合规」选，而非「保精度」——1-bit 量化在结构化输出上可能反而更稳（见 [[Function Calling 端侧工具调用]]）。

## 5. 隐私与权限
- [ ] 意图暴露的数据实体是否经过**最小化**？App 开放了哪些 Entity 给系统 AI？
- [ ] 是否有 **Per-Intent 隐私声明 / 权限清单**？

## 6. 可衡量指标（PM 拥有）
- [ ] 意图路由准确率（不是模型准确率）
- [ ] 端到端任务完成率 / 首次成功路径率
- [ ] 降级触发率（L3 GUI 占比越高 = 原生适配越差）
- [ ] 确认弹窗的「误确认率」与「被绕过率」（安全）

## 深化补充（2026-08）

### 一句话心智模型
这份 Checklist 的作用只有一个：**把不确定性从运行时挪到设计时**。每一条没拍板的项，都会在真机上变成一次「模型自由发挥」——而模型自由发挥的失败模式是不可复现的。

---

### 7. 🔴 评测口径纪律（新增，最容易踩坑的一节）

第 4 节写的「BFCL + NexusRaven 双基准」需要升级为**三基准三件事**，因为 BFCL 换版了：

| 基准 | 测的是 | 用在哪 |
|---|---|---|
| **BFCL v3** | 能不能**按格式把槽填对**（格式合规） | 窄域单应用 Schema 选型 |
| **NexusRaven** | 懂不懂**这个 API 是干嘛的**（语义理解） | 跨应用意图编排选型 |
| **BFCL v4** | 多轮 + agentic + **该不该调** | 端到端 Agent 循环选型 |

- **同一模型在 BFCL v3 与 NexusRaven 上可以差 30 个点且排名完全倒转**（库内已记录实例）。只测一个必然选错。
- **BFCL v4 权重已重排**：Agentic 40% / Multi-Turn 30% / Live 10% / Non-Live 10% / **Hallucination 10%**——经典单轮 function calling 只剩 20%。⚠️ 权重数字来自第三方拆解，**Berkeley 官方博客原文表述待核实**。
- **`Hallucination` 那 10% 是 OS 意图框架最该盯的一栏**：它测「系统里没有任何意图能满足这句话时，模型会不会硬凑一个来调」。**Registry 越大，误召回代价越高**，而工具微调模型系统性偏向「调点什么」——恰是其弱项。

- [ ] 选型表是否**三列并存**，且每个分数都标了**基准版本号**？
- [ ] 端侧回归集里是否补了「**空 Registry / 无匹配意图**」用例？

### 8. Registry 是动态的，不是静态清单（新增）
- [ ] 意图可见性是否随**账号态 / 会员态 / 灰度 / 地区合规**实时变化？
  - Android 已有公开 API：`@AppFunction(isEnabled = false)` + `AppFunctionManager.setAppFunctionEnabled(...)`。**四平台中目前唯一有动态可见性 API 的**（Apple / HarmonyOS / Windows 待补）。
  - 不做这条会产生最难查的一类 bug：**用户没开会员，Agent 却在工具列表里看到了会员功能**。
- [ ] 反向治理：如何识别「注册了但常年禁用」的**形式适配**？

### 9. 意图元数据的来源分级（新增，防 ADI 的最低成本一档）
- [ ] Registry 每条元数据是否带 **`source.type`**（平台写的 / 开发者声明 / 运行时抓取 / 第三方内容）与 **`classification`**（`public→internal→confidential→restricted`）两列？**没有这两列就无法回答「这条元数据能被伪造吗」。**
- [ ] 会话敏感度是否**单调棘轮**（只升不降）？只有分级没有棘轮 = 模型下一轮就「忘了」刚读过高敏内容。
- [ ] 谁来打标？**若由 App 开发者自报就回到了可伪造的靶面**，只有系统按来源类型强判才有安全意义。这是搬进 OS 时的核心设计题。
- ⚠️ 现状：成熟参考实现（微软 Agent Governance Toolkit）是**开源治理层，不是 OS 层**；**四大 OS 截至 2026-08 均未采纳**。成本远低于符号化隔离（约 15× 调用开销），是端侧性价比最高的一档。

### 10. 确认要三点部署，不是一点（对第 2 节的补充）
- [ ] **动作前**（经典 Confirmation UI）
- [ ] **`post_tool`**（工具返回后）——堵住「脏数据已经进上下文才想起来确认」
- [ ] **`pre_output`**（输出前）——含 PII 转人工/二次确认
- [ ] 确认落在**谁的界面**上？高危动作应停在**被调用 App 的原生页面**（支付停在支付 App），责任链才清晰可审计。
- [ ] 平台路线选择：**Apple = 系统级统一确认**（据 entity ownership 差异化提示）；**Android = 下放给 App 自己实现**（官方甚至建议「加不止一步确认」）。做 ROM 的话，**Android 这块空缺就是厂商可以补位的地方**。
- [ ] 是否有「**可逆**」兜底（一键撤回 + 任务中止）？Confirmation 管执行前、隔离管执行中、Undo 管执行后。

### 6 节指标补两条
- [ ] **云端逃逸率**（本地承接率 / 升级率 / 上云率）——端侧路由的成败核心指标不是准确率，是本地承接比例；本地接不住，成本与延迟优势就不成立。
- [ ] **误召回率**（无合适意图却硬调的比例），随 Registry 规模增长必须单独监控。

### 待解问题
- [ ] 「云端逃逸率」和「路由准确率」冲突时怎么取舍？（升级云端能提准确率，但成本/延迟/隐私三重代价）**这条红线该由 PM 定死一个数字，还是按场景分档？**
- [ ] 来源分级的「谁来打标」如果只能靠系统强判，那**系统凭什么知道一条 AppFunction 返回值里混了 UGC 内容**？是不是必须要求 App 在 Schema 里声明返回字段的内容来源类型？
- [ ] 第 4 节的「1-bit 量化按 Schema 合规选而非按精度选」这条反直觉结论，**在我们要落地的机型 SoC 上复现过吗**？（库内数据来自 Mac Mini M4，**非手机 SoC，待核实**）
