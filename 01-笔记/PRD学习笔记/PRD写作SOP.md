# PRD 写作 SOP（标准作业流程）

> 配套：[[PRD学习笔记]]（方法论）、[[PRD_Template]]（可直接填的模板）、[[OS PM PRD 专项]]（OS 产品补充章节）。
> 适用：从"一个模糊想法 / 一个需求"到"一份可评审、可验收的 PRD"。
> 输入：需求来源（用户反馈 / 工单 / 竞品 / 经营指标）、干系人清单。
> 输出：一份 `.md` PRD + 评审通过。

---

## 阶段 0 · 前置准备（5–10 min）
- [ ] 明确触发：这个需求来自哪？有没有证据（数据 / 截图 / 工单号）？
- [ ] 拉齐 stakeholder：研发 / 设计 / 测试 / 运营 / 合规 谁要参与评审？
- [ ] 确认计划窗口（迭代 / 里程碑），避免无期限。

## 阶段 1 · 问题定义（最重要，先把"为什么"写透）
- [ ] **三段式问题陈述**：
  1. 现状与证据（数据 / 事实 / 案例，避免纯观点）
  2. 影响与代价（不解决损失什么：钱 / 时间 / 风险 / 机会）
  3. 时机与约束（为什么现在必须做：窗口期 / 合规 / 合同 / 竞争）
- [ ] **范围与非范围**：
  - Must：本期必须交付的最小闭环
  - Should：增强但不影响闭环
  - Not now：明确不做
- [ ] **假设（Assumptions）**：列出关键假设 + 不成立时的处置（延期 / 降级 / 替代）

## 阶段 2 · 目标与成功指标
- [ ] 业务结果指标（转化率 / 流失率 / 客诉量 / 响应时效）+ 基线 → 目标
- [ ] 交付结果指标（上线范围 / 性能 SLA / 合规口径 / 可用性）
- [ ] 符合 SMART；百分比指标必须带基线。

## 阶段 3 · 用户与场景（任务闭环，不是功能清单）
- [ ] 用户角色 + 权限模型（谁可见 / 可操作）
- [ ] 主路径：最常见的 1 条流程写透（建议 Mermaid 流程图）
- [ ] 高频异常：权限不足 / 数据缺失 / 网络异常 / 重复提交
- [ ] 关键约束：审计 / 合规 / 设备 / 网络

## 阶段 4 · 需求拆解（共识 → 可实施条目，不替研发写方案）
- [ ] 用户故事：`As a [角色], I want [动作], so that [价值]`，每条带验收标准
- [ ] 业务规则：条件 / 例外 / 边界 / 口径（完整、准确、无歧义）
- [ ] 交互与原型说明：状态 / 校验 / 错误提示 / 空态 / 异常态
- [ ] 数据字典：字段名 / 类型 / 长度 / 必填 / 说明 / 示例值

## 阶段 5 · 非功能需求（最易被忽略）
- [ ] 性能（响应时间 / 并发 / QPS）
- [ ] 安全与合规（加密 / 传输 / 隐私 / 权限）
- [ ] 兼容性（OS 版本 / 浏览器 / 设备）
- [ ] 数据埋点（事件名 + 属性 + 触发时机）

## 阶段 6 · 验收标准（AC）
- [ ] 区分 **验收标准（AC）**（某条需求成功的条件）与 **完成的定义（DoD）**（团队质量门槛）
- [ ] 每个核心功能 ≥1 条可执行验收条件

## 阶段 7 · 评审与迭代
- [ ] 评审会：提前预设可能被怼的问题并准备答案；引导回 PRD 本身
- [ ] 版本管理：每次修改更版本号 + 记录（改了什么 / 为什么 / 影响 / 谁确认）
- [ ] 变更控制：需求变更正常，但提前预估并沟通；把"你的问题"变成"我们的问题"

## 阶段 8 · AI 辅助加速（推荐，人在环中）
- [ ] 用持久"产品宪章"喂背景，让 AI 出结构初稿（30min vs 传统 4–8h）
- [ ] 你聚焦：取舍决策、边界补全、跨模块兼容、替换通用套话
- [ ] 透明标注"AI 辅助初稿"；涉密走私有化部署

## 质量检查清单（输出前逐项自查）

| # | 检查项 | 标准 |
| :--- | :--- | :--- |
| 1 | 背景与目标 | 有业务 + 用户目标，可量化 / 可验证 |
| 2 | 角色与权限 | 所有角色已列，权限边界清晰 |
| 3 | 主流程 | 有流程图，主流程完整闭环 |
| 4 | 功能模块 | 每模块有用户故事 / 前后置 / 交互 / 数据字典 |
| 5 | 异常流程 | 网络 / 权限 / 数据异常已覆盖（≥90%） |
| 6 | 数据字典 | 字段名 / 类型 / 必填 / 说明 / 示例，缺一不可 |
| 7 | 埋点方案 | 关键页 / 操作有埋点，事件名 + 属性明确 |
| 8 | 非功能需求 | 安全 / 性能 / 存储 / 集成至少各 1 条 |
| 9 | 验收标准 | 每核心功能 ≥1 条可执行验收条件 |
| 10 | 待确认项 | 假设与信息缺口已标注汇总 |
| 11 | 无空话 | 无"提升体验 / 优化性能"等不可执行描述 |
| 12 | 版本记录 | 头部有版本号 / 日期 / 修订人 / 备注 |

## 失败兜底策略
若满足 ≥2 条，不要硬写完整 PRD，改出 **需求梳理文档**：
- 用户答不出"这个功能解决什么问题"
- 核心流程说不清（连主流程都没有）
- 目标用户不明确
- 用户明确说"我也没想好"

> 需求梳理文档结构：当前理解 / 待回答关键问题（按优先级）/ 可能方案方向（2–3 个优劣）/ 建议下一步。
