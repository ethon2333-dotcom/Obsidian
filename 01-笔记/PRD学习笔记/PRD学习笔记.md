# PRD 学习笔记（OS 产品经理视角）

> 本笔记配套 [[PRD_Template]]（可直接套用的标准模板）、[[PRD写作SOP]]（可执行的写作流程与检查清单）、[[OS PM PRD 专项]]（系统级产品的 PRD 要点）。
> 定位：把"怎么写出让研发/设计/测试都满意的 PRD"拆成可复用的方法论，而不是又一份模板。

## 一、PRD 到底是什么
- **定义**：Product Requirements Document，将商业/市场需求（BRD/MRD）翻译成"图纸化"的需求说明，是产品从概念到落地的桥梁，也是团队协作的"宪法"。
- **与 BRD/MRD 的关系**：BRD 讲商业价值与可行性 → MRD 讲市场与用户 → PRD 讲"具体做什么、做到什么程度"。国外常合并为 MPRD。
- **使用对象**：开发（获知逻辑）、测试（建用例）、项目经理（拆工作包）、交互设计（定细节）、运营（做准备）。评审通过前，PRD 是必须锁定的最重要文档。
- **核心原则**：描述"what & why"，**不写"how"**（实现细节留给技术设计文档 / Tech Spec）。每条需求都应能追溯到一个用户需要。

## 二、高质量 PRD 的 5 大核心要素
1. **背景与目标**：为什么做比怎么做重要；"为什么现在做"要有证据（数据 / 合规 / 竞争窗口）。
2. **结构化需求描述**：从全局到细节——新项目走"业务流程 → 系统架构 → 功能模块"；迭代项目聚焦单功能全要素（描述 / 主流程 / 分支 / 异常 / 规则 / 交互）。
3. **细节与边界**：覆盖中间态（加载中）、网络异常、空数据、重复提交、极值；异常流程覆盖率建议 ≥90%。
4. **可测试（可验证）**：每条需求有量化验收标准；避免"提升体验 / 优化性能"等空话。
5. **术语一致**：专有名词统一（iOS 非 IOS，登录非登陆）；必要时附术语表。

## 三、标准结构（与 [[PRD_Template]] 一致）
1. 文档基本信息（修订日志 / 干系人 / 相关文档）
2. 需求背景与业务目标
3. 用户画像与使用场景
4. 业务流程与逻辑图（主流程 + 状态机）
5. 产品功能清单（模块 / 功能点 / 优先级 / 终端）
6. 详细功能需求（原型 / 校验 / 边界 / 异常）
7. 非功能需求（性能 / 安全合规 / 兼容 / 埋点）
8. 上线策略与运营运维（灰度 / 客服 / 监控）
> OS 产品还需补充：能力暴露 / 接口面、意图 Schema、权限与审批流、系统编排与 Fallback、生态治理 → 见 [[OS PM PRD 专项]]。

## 四、写前四步法（从想法到文档，唐杰方法论）
1. **信息结构图**：用思维导图罗列功能信息内容（标题 / 作者 / 时间…），不求全。
2. **产品结构图 + 用户流程图**：梳理频道 / 页面 / 功能，画出操作流程。
3. **原型设计**：手绘 → 灰模 → 交互原型，论证可行性、对齐理解。
4. **撰写文档**：有原型 + 描述即可，必要时补正式模板归档。

## 五、优先级与范围管理
- **MoSCoW**：Must / Should / Could / Won't（本期）。
- **P0/P1/P2**：P0 最小闭环必做，P1 增强，P2 可选。
- **RICE**：Reach × Impact × Confidence ÷ Effort，做路线图排序（AI 可辅助，但决策权在你）。
- **范围边界**：显式写"非范围（Not now）"与假设（Assumptions），假设不成立时的处置（延期 / 降级 / 替代）。

## 六、常见坑（避坑清单）
- 术语 / 格式错误（IOS → iOS，登陆 → 登录）。
- 交互不对齐（弹窗问"确认删除？"按钮却是"删除 / 取消"）。
- 场景遗漏（只有成功 / 失败，忽略加载中、网络断）。
- 空话泛滥（"用户友好""高性能"无法验收）。
- 把实现细节写进 PRD（那是 Tech Spec）。
- 成功指标只写百分比不给基线。
- 遗漏待确认项（open questions 不写 = 埋雷）。

## 七、AI 辅助写 PRD（2026 实趋势）
- **定位**：AI 做结构、样板、补全；你做判断、取舍、上下文。**人在环中（Human-in-the-loop）**，决策权不能外包。
- **持久记忆**：把产品定位 / 用户 / 约束写成"产品宪章"，喂给 AI（Claude / ChatGPT / ChatPRD / Notion AI），后续每份 PRD 自动对齐，不用每次重说背景（noumi 的"self-evolving PRD"思路）。
- **多智能体**：MetaGPT 用 SOP 把"产品经理 / 架构 / 测试"角色化，多 agent 互审，质量优于单 agent（IBM 实践，DeepSeek + Ollama 本地可跑、数据不出域）。
- **提效**：传统 4–8h，AI 初稿约 30min；审阅 + 修订为主，效率 3–5 倍。
- **风险**：AI 易在业务逻辑准确性、边界完整性、跨模块兼容性出错——必须严格审阅；AI 写的通用套话要替换成你产品的具体引用；建议向团队透明标注"AI 辅助初稿"。
- **安全**：客户反馈 / 需求涉密时优先私有化部署，避免泄露商业数据。

## 八、OS PM 视角（详见 [[OS PM PRD 专项]]）
系统级产品的 PRD 不是"一个功能点"，而是"一类能力的暴露与编排"：要定义接口面、意图 Schema、权限 / 审批、系统编排与兜底、生态治理、向后兼容。和单 App PRD 差异显著。

## 九、自查清单（完整 12 项见 [[PRD写作SOP]]）
背景可量化 / 角色权限清晰 / 主流程闭环 / 模块要素齐全 / 异常覆盖 / 数据字典完整 / 埋点明确 / 非功能达标 / 验收可量化 / 待确认已标注 / 无空话 / 版本记录齐全。
