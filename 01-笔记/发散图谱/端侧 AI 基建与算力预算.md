# 端侧 AI 基建与算力预算

> 发散方向：端侧 Agent 能不能跑、跑多快、多省电，取决于底层算力与基建。这是安卓 PM 推端侧意图/工具调用时必须懂的「地壳」。
> 技术底：[[OS-PM-3B模型内存预算推演]] · [[OS-PM-投机采样原理与能效优化]] · [[OS-PM-PagedAttention与KV Cache剪枝]] · [[Function Calling 端侧工具调用]] · [[App Infra 应用基建]]。

## 1. 算力：NPU 是第一公民
- 端侧推理主力是 **NPU**（不是 CPU/GPU），安卓侧通过 **NNAPI / NPU delegate** 调度。
- PM 决策点：目标机型的 NPU 算力档位（旗舰 vs 中端）决定能跑多大模型、多低延迟。
- 异构调度：VLM 走 NPU，轻量路由走 CPU，必要时 GPU 补位。

## 2. 量化：体积 / 时延 / Schema 合规的三角
- 常见档：FP16 → INT8 → INT4 → **1-bit QAT**。
- 反直觉事实（见 [[Function Calling 端侧工具调用]]）：1-bit 量化在**结构化输出（JSON/工具调用）**上可能反而更稳（Bonsai 1-bit 73.3% BFCL vs 同族 FP16 25.3%）——因为量化把模型压向「只吐合法格式」。
- **PM 选型纪律**：端侧 Planner 的量化按「保 Schema 合规」选，不按「保精度」选；且必须实测量化版本，不能拿 FP16 分数外推。

## 3. 端侧 Runtime：模型的运行环境
- 常见：LiteRT（TF Lite）、ExecuTorch、MNN、NCNN。安卓端侧 Agent 的执行容器。
- PM 关心：Runtime 是否支持流式输出、工具调用循环、与系统 API 的桥接。

## 4. 内存 / 显存预算（端侧最紧的资源）
- 模型权重 + KV Cache + 激活值，中端机显存极易爆。
- 相关技术：[[OS-PM-PagedAttention与KV Cache剪枝]]（分页注意力省显存）、[[OS-PM-3B模型内存预算推演]]（3B 模型在端侧的预算推演）。
- PM 决策点：端侧模型规模上限（如 ≤ 3B 还是能上 4B/8B）、是否允许卸载到系统内存。

## 5. 延迟优化：让端侧 Agent「跟手」
- [[OS-PM-投机采样原理与能效优化]]：小模型 draft + 大模型 verify，压首字延迟。
- GUI Agent 场景：相邻帧 A11y 树拓扑变化 <5% 时复用上次决策，平均延迟压到 100ms 内（见 [[工业级 GUI Agent 架构（VLM+无障碍树）]]）。

## 6. 端侧 vs 云端分流（PM 的核心权衡）
- 端侧：隐私好、低延迟、离线可用，但算力有限。
- 云端：能力强，但有网络/时延/成本。
- 混合栈范式：端侧小 Planner 路由 + 低置信升级云端（如 FunctionGemma 本地 + Gemini Flash 兜底）。

## 深化补充

### 一句话心智模型

> **端侧算力不是"我有多少"，而是"我能借到多少、借多久"。Agent 在手机里是租客不是房主——前台 App、相机、游戏随时会把它赶出去。**

这个视角是我觉得最容易被忽略的：所有的 benchmark 数字都是在**独占设备**的实验室条件下测的。真实场景是"用户一边刷抖音一边让 Agent 订外卖"，这时候 NPU 在给视频超分、内存被前台占了 60%。

所以**端侧 PM 该问的不是"这模型能跑多快"，而是三个更狠的问题**：
1. **被抢占后多久能恢复？**（冷启动 / 权重重载代价）
2. **降级路径是什么？**（跑不动时是变慢、变笨、还是上云、还是直接失败）
3. **失败时用户看到什么？**（这是产品问题，但根子在算力）

### 把算力预算写成一张可算的账

我需要一张能在评审会上直接摊开的表。按"一次典型意图执行"拆：

| 环节 | 谁在跑 | 大致代价 | 能不能砍 |
|---|---|---|---|
| 唤醒 / 意图分类 | 极小模型（270M 级）或规则 | 毫秒级 | 不能砍，这是入口 |
| 语义路由 / 工具选择 | 小 Planner（0.3–2B） | 百毫秒级 | 可缓存（高频意图命中缓存直接跳过） |
| 屏幕理解（如需） | VLM，NPU | **最贵的一段** | **可砍**——有无障碍树时不看像素 |
| 参数填充 / 追问 | 同 Planner | 低 | 不能砍 |
| 执行 | 系统 API / GUI 操作 | 极低 | — |

**看完这张表我的判断：真正的算力大头在"屏幕理解"，而这一段恰恰是最可能被绕开的。** 能走结构化通道（AppFunctions / 无障碍树）就别走视觉——这不只是准确率问题，是**能耗和内存预算问题**。这也反过来解释了为什么各家都在拼命推官方意图通道，而不是躺平做 GUI Agent（见 [[端侧执行通道 GUI 与 MCP 路线之争]]）。

### 一个可用的选型参考点（注意版本口径）

库里 [[Local Agent Bench 端侧智能体基准]] 记了 Round 3 的两个样本，正好对应两种定位：

| 模型 | 分数 | 定位 | 我该什么时候用 |
|---|---|---|---|
| `qwen3:1.7b` | 0.960（Round 3 #1） | **端到端办事** | 需要多步规划的复杂意图 |
| `functiongemma` | 0.640 / 435ms | **快路由分流** | 高频简单意图、第一跳分类 |

**这两个数字说明了一件挺重要的事：1.7B 级模型在端侧已经能跑通完整 Agent 循环。** 也就是说"端侧只能做路由、复杂任务必须上云"这个前提，在 2026 已经开始松动了。但要注意 ⚠️：这是 Round 3 数据、来源 URL 仍待回填，且**与 BFCL 分数不同量纲不可换算**。

还有一个我之前的评测盲区：**BFCL v4 把 Hallucination（"没有合适工具时正确地不调用"）单列了 10% 权重**。这个维度 Local Agent Bench Round 3 没覆盖，但它恰恰是**意图 Registry 规模变大之后最致命的失败模式**——注册了 1000 个意图，用户说了句闲聊，模型硬要匹配一个去执行。**自建端侧回归集必须补"无匹配意图"用例。**

### 反直觉点再挖一层

原文第 2 节记了"1-bit 量化在结构化输出上反而更稳"。我想补的是**为什么这不奇怪**：

Planner 的任务本质是**分类 + 填空**，不是自由创作。量化削掉的是模型的"表达自由度"，而表达自由度对 JSON 输出来说**是负资产**——模型越自由越容易在 schema 外发挥。所以量化在这里起到了类似"约束解码"的作用。

**推论（我自己的，待验证）：如果这个机制成立，那对 Planner 来说更该投入的不是"更大的模型"，而是"更强的格式约束"**（grammar-constrained decoding / 结构化输出 API）。这可能比堆参数便宜得多。

### 待解问题
