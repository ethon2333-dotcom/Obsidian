# Agent 执行安全（PM视角）

> 执行安全不是工程团队的专属问题——**定义「什么必须确认、什么必须隔离、出了事谁负责」是 PM 的发布 blocker**。
> 技术深度见知识飞轮：[[XPIA 跨提示注入]] / [[Agent Data Injection 数据注入攻击]] / [[Dual View 智能体数据视图隔离]] / [[Confirmation UI 安全机制]]。

## PM 必须拥有的 4 个决策
1. **确认分级**：哪些动作 L0/L1/L2（见 [[Confirmation UI 分级与产品责任边界]]）。
2. **隔离边界**：Agent 执行会话是否跑在**隔离工作区 + 低权限账号**（参考 Windows Agent Workspace 的 isolated sessions / low-privilege account / ACL，见 [[Windows Copilot Actions 与 Agent Workspace 2026]]）。敏感动作绝不在主用户上下文裸跑。
3. **注入防护产品策略**：系统/文档/网页里的指令不能指挥 Agent——产品上如何呈现「这是数据不是命令」（Dual View：Agent 看到的数据视图与用户看到的分离）。
4. **失败与追责**：Agent 误操作后的回滚/补偿路径、责任主体、用户告知。

## 三个最容易踩的坑
- ❌ 把确认做成「事件」而非「凭证」（可被注入绕过）。
- ❌ 用 GUI Agent 自动执行支付/删除等不可逆动作。
- ❌ 信任模型「理解了意图」而不留可审计凭证。

## 竞品怎么做的（值得对标）
- **Windows**：Agent accounts + 隔离工作区 + ACL + 用户透明（四支柱）。
- **Apple**：系统级 Confirmation UI + 沙盒授权，仅响应明确定义的 Intent。
- **HarmonyOS**：元服务沙盒 + 意图框架权限（见 [[HarmonyOS 意图框架竞品观察]]）。

## 深化补充（2026-08）

### 一句话心智模型
**执行安全是 PM 的「发布闸门」，不是工程细节**。你不定确认分级，工程师就只能在「全弹确认（烦死用户）」和「全不弹（出事）」之间二选一——这是产品责任，不是技术债。

### 2026 年的两个新变量（库内已核实）
- **EU AI Act Article 15（2026-08-02 生效）**：把 prompt injection / 对抗样本 / 投毒列为高风险 AI 系统须抵御的攻击面，罚则 €15M 或营业额 3%。执行安全从「产品选择」变成「法律义务」——这是分水岭级变化。
- **ADI（Agent Data Injection，arXiv 2607.05120）**：把威胁定义从「一次注入」升级为「**数据源本身不可信**」（同环境对照 0–0.7% vs 最高 100%）。PM 的直接判据变成：**意图元数据是否做来源校验**？现状是四大 OS 均未采纳来源分级（仅治理层有成熟模型，见 [[数据溯源分级与单调棘轮]]）。

### 具体例子（用来跟团队讲清楚）
同一个「给张三转 500」指令：
- 走 **Intent**：确认 UI 落在被调用 App 的原生界面，产物是**可审计的数据凭证**，注入难绕过。
- 走 **GUI 自动点**：确认是**一次性事件**，注入可在点击链路里替换收款人——这就是「把确认做成事件而非凭证」的坑（见 [[Confirmation UI 分级与产品责任边界]]）。
