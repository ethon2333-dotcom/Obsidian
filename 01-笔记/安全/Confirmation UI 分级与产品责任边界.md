# Confirmation UI 分级与产品责任边界

> 当 Agent 代替用户执行动作，确认 UI 不是「弹个窗」这么简单——它是**产品责任的分界线**。
> 安全机制技术细节见 [[Confirmation UI 安全机制]] / [[XPIA 跨提示注入]]。

## 三级确认强度（按风险递增）
| 级别 | 适用动作 | 确认形态 | 产品责任 |
|---|---|---|---|
| L0 静默执行 | 查信息、加本地提醒、非敏感只读 | 执行后轻量回执，可撤销 | 系统 |
| L1 轻确认 | 发消息、加日历、创建待办 | 轻量弹窗/卡片，一键确认，可撤销 | 用户确认即转移 |
| L2 强确认 | 支付、删除、对外发布、不可逆 | 独立原生界面 + 显式意图摘要 + 二次要素（指纹/密码） | 用户承担，但**系统须保证摘要真实不被注入** |

## 关键原则（PM 红线）
1. **确认 UI 的产物应该是「数据」不是「事件」**：弹窗点确认只产生一个可被 XPIA 绕过的事件；应产出**带意图内容哈希的凭证**（谁能调、调什么、额度、时效）。这是防线从 UI 层下沉到协议层的入口（见 [[意图支付授权协议 APOP]]）。
2. **摘要必须来自可信源**：确认框显示的「你要做 X」必须来自系统对意图的解析，不能被页面/文档里的注入指令篡改（见 [[Agent Data Injection 数据注入攻击]] / [[Dual View 智能体数据视图隔离]]）。
3. **不可逆动作不给静默默认**：slot 缺失、意图模糊时禁止默认补全。
4. **可审计**：每次确认留痕（谁、什么意图、什么时间、凭证哈希），满足合规（参考 EU AI Act Art.15 人类监督）。

## 深化补充（2026-08）

### 一句话心智模型
**Confirmation UI 的本质是把「信任」从一个模糊的「用户点了确认」事件，变成可被协议层校验的「凭证」**。事件会被注入替换（页面里一句「忽略确认」就能绕过），凭证带哈希和要素，难替换——这是防线从 UI 层下沉到协议层的入口。

### L2 强确认的「凭证四要素」（与 C 层 SOP 对齐）
一个合格的 L2 确认凭证至少让用户能看清四件事（详见 [[端侧执行通道选型 SOP]]）：
1. **内容**——调什么能力、参数是否真实（摘要须来自系统解析，非页面注入）。
2. **额度**——单次/累计上限（如转账上限、调用次数）。
3. **时效**——凭证多久有效（如 30 秒），过期须重确认。
4. **责任主体**——谁授权、谁执行，出事追责有依据。

### 例子（区分「事件」vs「数据凭证」）
- ❌ 事件型：「确认支付？」一个按钮——注入可在点击链里把收款人替换掉。
- ✅ 凭证型：「向张三转账 ¥500 · 有效期 30s · 凭证 #a1b2」——内容/额度/时效/责任主体全可见，且带哈希可审计。

### 与 APOP 的衔接
[[意图支付授权协议 APOP]] 里「**意图内容 ↔ 凭证绑定**」正是 L2 的产品落地形态；可审计凭证哈希也对齐 [[数据溯源分级与单调棘轮]] 的 provenance 思路。
