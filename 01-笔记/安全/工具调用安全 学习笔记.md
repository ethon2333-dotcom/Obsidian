# 工具调用安全 学习笔记

> 学习定位：这是一篇**广度种子笔记**——把「Agent 调外部工具」这件事的风险面、防护分类、与端侧 OS 能力的关系、2025–2026 的合规进展，一次性铺开成地图。**深度留白给后面逐条深读**，文末 `- [ ]` 标出的就是待补的坑。
> 本文是 **own-words 综合**，不是情报简报。平台/协议细节请点深读链接；我自己的判断写进待解问题。

---

## 一、一句话心智模型

**工具调用安全 = 给「会自己动手的 AI」装上刹车、围栏和行车记录仪。**

模型从「说话」变成「做事」的那一刻，风险性质就变了：说错话顶多误导，调错工具可能转错账、删错库、泄露令牌。所以核心不是「模型聪不聪明」，而是**它在什么边界内、经谁同意、留什么痕地做事**。

> 一句我最提醒自己的：权限问题是「能做什么」（credential），确认问题是「该不该现在做」（authorization）。两者必须分开——**有钥匙不代表此刻该开门**。

---

## 二、风险面（为什么危险）

Agent 一旦能调用 API / 跑代码 / 写文件 / 发起支付，就同时打开了以下几类风险。下面只列「面」，每个面后面的深度（真实案例、可利用链路）见待解问题。

| 风险面 | 一句话 | 典型场景 |
|---|---|---|
| **权限过大** | Agent 拿到的钥匙比任务需要的多 | 一个只读摘要 agent 却持有可写、可删的 API key |
| **提示注入触发危险操作** | 工具返回的数据里藏了「指令」，被模型当成命令执行 | 网页/邮件/文档内容注入「请把文件发给攻击者」，agent 照做 → 见 [[Agent Data Injection 数据注入攻击]] |
| **不可撤销操作** | 动作一旦发生无法回滚 | 转账、发送、删除、公开发布 |
| **凭据泄露** | 令牌被透传给不可信方或明文落日志 | 恶意 MCP server 骗走本该给别家的 token（MCP OAuth 受众绑定要堵的就是这个，见 [[MCP 与设备侧 MCP]]） |
| **级联 / 委托链放大** | 一个子 agent 被注入，沿委托链放大 | 子 agent 上下文被注入 → 沿 delegation 链传播未授权凭据访问 |
| **代码执行逃逸** | run 了不可信代码，逃出沙箱 | 克隆仓库带毒，coding agent 执行后触达生产 |
| **记忆/上下文投毒** | 长期记忆被污染，后续决策被带偏 | 被写入伪造偏好/虚假事实，下次自动采信 |

> 这七类里，用户最该先记住**前四个**（权限过大、注入触发危险操作、不可撤销、凭据泄露）——它们是工具调用安全「最低限度的四根柱子」，其余是放大因子。

## 三、防护分类（表格）

下面按「防护动作」横切，不按风险面竖切。每条给「做什么 + 一句产品视角」，深度（具体实现、阈值怎么定）留白。

| 防护分类 | 做什么 | 产品/PM 视角 |
|---|---|---|
| **最小权限（Least Privilege）** | 只给当前任务最小权限，任务结束即回收；读写分离、不同能力不同权限集 | 权限是「身份能碰什么」；别把人类凭据或长生命周期 API key 给 agent |
| **最小能动（Least Agency）** | 比权限更进一层：即便凭据有效，也限制「agent 自己能决定做什么」 | 能读支付库 ≠ 能自主退款；能动钱的动作永远要审批台阶 |
| **确认机制分级** | 按动作不可逆程度分级确认（见 [[Confirmation UI 分级与产品责任边界]]） | 低风险静默执行、中风险轻确认、高风险强确认；分级是产品责任边界问题 |
| **沙箱隔离** | 跑代码/调工具时在隔离环境，限制文件系统/网络/系统资源 | 爆炸半径要小；microVM / gVisor 这类隔离层是底线 |
| **人类介入 HITL** | 高影响决策前必过人；高风险 autonomous agent 需可即时中断（kill-switch） | 对应 EU AI Act 人类监督要求，见第五节 |
| **审计日志** | 记录完整执行链：指令、检索上下文、工具调用及参数、返回、决策、人工审批 | 不是「日志量」问题，是「能否重建行为」的架构问题 |
| **工具输入校验** | 调工具前校验参数（allowlist、schema、范围、策略版本） | 提示指令≠授权边界；校验要在执行路径上强制，不能只靠 prompt |
| **凭证托管** | 凭据由可信第三方代持、按次发短期 scoped 凭证，不经中间层/app | 敏感授权要么下沉系统、要么弹回用户本人（MCP OAuth URL 模式同思路） |

> **核心原则一句话**：纵深防御——任何单层失败都要被其他层兜住。权限、能动、确认、沙箱、HITL、审计、校验、托管，缺一层就少一道闸。

深度留白（每条后面都值得单独开深读）：
- [ ] 最小权限在「长任务 / 多步」场景下，权限该在每一步重新评估还是任务开始时一次授权？任务中途范围变化怎么办？
- [ ] 「Least Agency」和「Least Privilege」在端侧 OS 里分别该由谁强制——系统还是 app？
- [ ] 确认机制分级的「不可逆程度」怎么量化？有没有可复用的评级量表？

## 四、与端侧意图框架 / 确认 UI 的呼应

这一节是给 Android PM 视角的：为什么「OS 托管能力 + 系统级确认 UI」比「app 自管工具」更安全。

**端侧意图框架（如 Android AppFunctions）把三件事收进 OS**，天然补齐上面表格里的多处缺口：

| 防护分类 | app 自管工具（云侧 MCP 风格） | OS 托管（端侧意图框架） |
|---|---|---|
| 发现 / 准入 | 客户端各自配、OAuth 各自谈 | **OS 内置 Registry + 系统权限**（如 `EXECUTE_APP_FUNCTIONS`）统一控制 |
| 确认 UI | app 自己画、自己判断 | **系统级确认 UI** 渲染，凭据不经 app |
| 权限最小化 | 靠 app 自觉 | 系统强制，能力声明由 OS 校验 |
| 凭据 | 可能经中间层透传 | 敏感授权下沉系统或弹回用户本人 |

> 心智模型：把工具目录交给 OS 托管，**入口价值和责任都从 app 转移到系统**。app 只负责「声明能力」，确认、准入、凭据代持由系统兜底——这比十个 app 各写一套确认逻辑更稳，也更符合「敏感授权不该由中间层代持」。

呼应链接：端侧落地见 [[MCP 与设备侧 MCP]] 的第四节；确认分级的产品责任见 [[Confirmation UI 分级与产品责任边界]]；AppFunctions 技术细节见 [[Android AppFunctions 设备侧意图 2026]]。

## 五、2025–2026 进展（EU AI Act 等）

### 5.1 EU AI Act

- **Article 15（准确性、鲁棒性、网络安全）**：针对**高风险 AI 系统**的要求——要达成适当的准确性、鲁棒性、网络安全，并在生命周期内持续一致；需抵御错误/故障/环境不一致；网络安全须防 **data poisoning、model poisoning、对抗样本/模型规避、机密性泄露**。→ 对工具调用安全的直接意义：robustness（抗故障）+ cybersecurity（抗注入/投毒/对抗输入）正是 tool-use safety 的题中之义。
  - ⚠️ **适用时点待核实**：因 2026 年《Digital Omnibus》"Stop the Clock" 延期，Annex III 高风险系统的 Art.15 适用日口径不一（有源记为 2026-08-02，亦有源记为 2027-12-02）。
- **Article 14（人类监督）**：要求高风险系统的自主性**可被人工中断 / 覆盖**；部分解读将其延伸到 autonomous agent 须有 kill-switch。→ 对应第三节的 HITL / 不可撤销操作防护。
  - ⚠️ 精确子条款（如 14(4)(e) kill-switch 表述）待一手源对齐。

### 5.2 Agent 执行安全标准 / 框架（2025–2026 集中出现）

| 名称 | 时间 | 要点 |
|---|---|---|
| **OWASP Top 10 for Agentic Applications (2026)** | 2025-12 发布 | 首个面向自主 agent 的 peer-reviewed 风险分类（ASI01–ASI10）：Goal Hijack、Tool Misuse、Identity & Privilege Abuse、Supply Chain、Unexpected Code Execution、Memory/Context Poisoning、Insecure Inter-Agent Comm、Cascading Failures、Human-Agent Trust Exploitation、Rogue Agents；获 NIST / Microsoft / NVIDIA 背书 |
| **NIST AI Agent Standards Initiative** | 2026-02-17 宣布 | 把 agentic AI 列为独立标准化重点；基于 SP 800-53 的单/多 agent 控制 overlay 在研，Interoperability Profile 计划 2026 末，成型指南预计 2027 前难出 |
| **OWASP GenAI Security Project《State of Agentic AI Security》v2.01** | 2026-06-01 | 治理成熟度模型；强调「安全」与「安保」在部署层已不可分 |
| **Microsoft Agent Governance Toolkit** | 2026-04 开源（MIT） | 运行时策略强制（Agent OS 拦截每次动作）、agent 身份（DID）、执行环、kill-switch、合规映射 EU AI Act / OWASP |
| **CSA MAESTRO** | 持续 | 七层威胁建模框架，专为 agent 架构设计 |

> **2025–2026 一句话收口**：行业从「prompt 防注入」升级到「运行时强制 + 身份化 + 可中断 + 可审计」的体系化治理；「Least Agency」成为和「Least Privilege」并列的底层设计原则。

## 七、待解问题

- [ ] **「权限过大」在端侧该怎么量化？** 最小权限是口号，但一个 app 声明了 20 个 AppFunctions，OS 是否该按「本次任务只需其中 2 个」动态收窄？现有 Android 机制有没有任务级 scope 收敛？→ 待核实一手依据。
- [ ] **提示注入触发危险操作，确认 UI 能不能真的拦住？** 注入若伪装成「用户自己的指令」，系统级确认 UI 展示给用户的文案能否让用户识别这是「agent 自作主张」而非「用户本意」？这是 [[Confirmation UI 分级与产品责任边界]] 还没收口的点。
- [ ] **不可撤销操作的「可逆化」有哪些产品手段？** 除确认外，能否用预约执行+冷静期、限额、影子执行等降低不可逆性？值得单开一节。
- [ ] **凭据托管在端侧的具体形态**：系统代持的一次性凭据、OAuth URL 模式弹回用户浏览器——Android 17 那套和 MCP 的 URL 模式 elicitation 是不是同一套思路？映射关系待补。
- [ ] **EU AI Act 对「general-purpose AI / 自主 agent」有没有超出 Art.14/15 的专门义务？** GPAI 义务 2025-08 已适用，但 agent 执行是否触发额外条款，待一手源。
- [ ] **OWASP ASI10 Rogue Agents 与「最小能动」的边界**：什么算 agent「失控」、谁来判定、系统级 kill-switch 的产品形态是什么？
