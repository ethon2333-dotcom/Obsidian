> 一句话心智模型：端侧 AI 的信任问题不是「数据要不要上传」，而是「在『数据不出端』与『能力不够』之间，用一层**可验证的信任边界**把计算包起来——越往光谱右端，越用密码学/硬件证明去替代对厂商的人肉信任」。

## 术语速查（先看这张，避免概念错位）

| 术语 | 一句话 | 易混点 |
|---|---|---|
| 隐私计算 | 在不暴露原始数据的前提下完成计算的一类技术总称 | 不是某一项技术，是「TEE+DP+FL+HE+MPC」的总称 |
| 机密计算 | 用硬件 TEE 保护「使用中数据」 | 机密计算 ⊊ 隐私计算，侧重硬件 |
| 端云协同 | 端侧做不了时把计算安全地卸载到云 | 重点在「协同」的**信任传递**，不是简单上云 |
| 信任边界 | 数据/计算「可被谁看到」的分界线 | 与 [[Agent 执行安全（PM视角）]] 的「动作边界」是两层 |
| 远程证明 | 设备验证「云节点跑的是未经篡改的代码」 | 是 PCC/TIE「可验证」的根 |

## 学习定位

- **本篇解决什么**：建立「数据与计算的信任边界」这件事的广度地图——技术光谱、手段对比、厂商方案、合规时间表、Agent 场景的特殊性。是 [[安全 MOC]] 下「信任基础设施」分支的广度种子。
- **本篇不解决什么**：**Agent 执行动作的安全**（提示注入、确认弹窗、工具权限、责任边界）已在 [[Agent 执行安全（PM视角）]]、[[工具调用安全 学习笔记]]、[[Confirmation UI 分级与产品责任边界]] 三篇讲透。那套是「**动作层**」；本篇是「**数据/计算层**」，两者正交，请勿混淆。
- **阅读目标**：拿到一张能快速对照的表，知道某需求该落在光谱哪一段，以及哪条合规红线挡在前面。点到为止，深挖见「待解问题」。

## 一、为什么端侧 AI 绕不开这个话题

端侧 AI 的「隐私」不是附加功能，而是由两条物理约束逼出来的核心张力：

| 约束 | 含义 | 后果 |
|---|---|---|
| 数据不出端 | 个人上下文（聊天、照片、通知、位置）永远不上传 | 模型受限于端侧算力/内存，复杂任务做不了 |
| 能力不够 | 大模型、长上下文、检索增强必须上云 | 一旦上云，「数据不出端」被打破，信任转移给厂商 |

结论：纯端侧与纯云端是两个极端，**中间地带（TEE/可验证云/本地差分隐私）才是端侧 AI 产品真正的主战场**。这也直接牵连到「何时在端、何时上云」的调度决策，见 [[OS-PM-AI Runtime动态调度与降级策略]] 与 [[端侧大模型推理 学习笔记]]。

## 二、信任边界的技术光谱（纯端侧 → 普通云 API）

从左到右 = 对厂商的「人肉信任」递减，对「可验证性」的要求递增。

| 位置 | 信任谁 | 数据去哪 | 能力上限 | 典型代表 |
|---|---|---|---|---|
| ① 纯端侧 | 只信自己设备 | 不出端 | 受 NPU/内存限制 | Apple Intelligence 端侧模型、Gemini Nano |
| ② TEE / 安全飞地 | 信芯片硬件 + 远程证明 | 出端但锁在 enclave 内 | 接近云，但受 enclave 限制 | ARM TrustZone/CCA、Intel TDX、AMD SEV |
| ③ 厂商可验证云 | 信厂商 + **可远程验证**的代码/运行状态 | 出端，瞬时、无状态 | 满血云模型 | Apple PCC、Google Private AI Compute |
| ④ 普通隐私增强云 | 信厂商承诺 + 统计保护 | 出端，聚合/脱敏 | 满血云模型 | 联邦学习、差分隐私聚合后端 |
| ⑤ 普通云 API | 完全信厂商 | 出端，明文/留存 | 满血云模型 | 绝大多数第三方 LLM API |

> 关键洞察：③ 与 ④ 的区别在于「**能不能被独立验证**」。PCC 的透明日志、Google TIE 的远程证明，都是把「请相信我」变成「你可以自己查」。这是 2024–2025 年端云协同的范式升级。

## 三、技术手段拆解

### 3.1 TEE / 机密计算（保护「使用中数据」）

机密计算联盟（CCC，Linux Foundation，2019 成立）的定义：用**硬件 TEE** 保护「data in use」（处理中的数据），补足传输中/静态已加密的缺口。核心机制是**远程证明（remote attestation）**——远端在发送敏感数据前，密码学验证对方确实在真实硬件上跑着未经篡改的代码。

| 技术 | 厂商 | 隔离粒度 | 一句话定位 | 移动/端侧可用性 |
|---|---|---|---|---|
| ARM TrustZone | ARM | 两个「世界」（安全世界/普通世界） | 手机指纹支付、DRM 的老牌 TEE | 极强（几乎每部手机） |
| ARM CCA (Realm) | ARM | Armv9 新增「领域」第三态 | 云原生可动态租用的多租户飞地 | 服务端为主，端侧演进中 |
| Intel SGX | Intel | 进程级 enclave | 细粒度但内存小（早期 ~128–256MB），正被淘汰 | 弱（已退场） |
| Intel TDX | Intel | 整 VM 级机密虚拟机 | SGX 继任者，云上整机隔离 | 服务端 |
| AMD SEV-SNP | AMD | 整 VM 级 + 内存完整性 | 主流云机密 VM | 服务端 |
| NVIDIA H100 CC | NVIDIA | GPU 显存/计算受保护 | 把信任边界延伸到 GPU 推理 | 服务端（数据中心） |

- **端侧重点**：手机上的 TrustZone 是「动作安全」的底座（密钥、生物识别），但**做不了大模型推理的飞地**——端侧大模型靠的是 [[端侧大模型推理 学习笔记]] 里的量化/蒸馏，而非 TEE。TEE 在端侧的真正价值是「保护小模型权重/密钥」与「给可验证云做设备端证明」。
- **云侧重点**：PCC / Private AI Compute 的底层都建立在 TEE 之上（Apple 用 Secure Enclave + 自研服务器栈，Google 用 TPU + Titanium 硬件安全架构）。

### 3.2 厂商可验证云（端云协同的旗舰方案）

| 维度 | Apple Private Cloud Compute (PCC) | Google Private AI Compute |
|---|---|---|
| 公布时间 | 2024-06 WWDC 随 Apple Intelligence 发布 | 2025 随 Pixel 10 发布（*待核实具体日期*） |
| 硬件底座 | Apple silicon 服务器 + Secure Enclave | 自研 TPU（第六代 Trillium 起）+ Titanium 硬件安全架构 |
| 隔离机制 | 专用 PCC 节点 + 沙箱 + 进程网络隔离 | Titanium Intelligence Enclaves (TIE)，基于 AMD 硬件 TEE |
| 核心五大要求 | 无状态计算、可执行保证、无特权访问、不可定位、可验证透明 | 隔离、无访问（连 Google 也看不到）、瞬时留存 |
| 可验证手段 | 公开透明日志 + 生产镜像 90 天内可独立审查 + 虚拟研究环境 | 远程证明 + 端到端加密 + 第三方 IP 隐匿中继 |
| 数据留存 | 请求处理完即删除，从不留存、Apple 不可访问 | 输入/结果/过程仅在处理查询期间保留 |
| 首批落地 | Apple Intelligence 复杂请求卸载 | Pixel 10 的 Magic Cue、Recorder 转写摘要 |
| 独立审计 | 苹果承诺开放代码审查（*第三方审计结论待核实*） | 谷歌发布 Technical Brief（*实际攻防验证待核实*） |

- **厂商自述 vs 第三方评价（务必分开看）**：上表「核心要求/可验证手段」主要来自厂商官方博客与技术白皮书（Apple Security Research、Google 官方博客）。**是否真能做到「连厂商都看不到」需要独立安全研究验证**，目前 PCC 已有公开透明日志机制，但「无可攻破」属厂商主张，非第三方定论。
- 与 [[Apple Intelligence 端侧架构 学习笔记]] 互补：那篇讲端侧模型与卸载触发，本篇讲卸载后那段「云上可信计算」到底信什么。

### 3.3 差分隐私（DP）

在数据离开设备前/聚合时加噪声，使单条记录无法被反识别。两种模式：

| 模式 | 噪声加在哪 | 厂商能否见原始数据 | 代表 |
|---|---|---|---|
| 本地 DP (LDP) | 设备端，发送前 | 永远只见噪声数据 | Apple iOS 分析、Gboard |
| 中心 DP (GDP) | 云端，聚合结果 | 先收原始、再脱敏 | 美国人口普查 2020 |

- **Apple 实际用法**（官方《Differential Privacy Overview》）：LDP，按功能设隐私预算 ε——emoji ε=4、QuickType ε=8、Health 类型 ε=2；数据最长留存 3 个月；无设备标识、丢弃 IP。
- **Google 实际用法**：RAPPOR（Chrome，已弃用）、Gboard 联邦学习 + DP-SGD、Maps/广告归因的 DP。Gboard 西语下一词预测曾用 DP-FTRL 训练，官方称 ρ=0.81 zCDP（*具体数值待核实*）。
- **本质张力**：ε 越小越隐私但越不准，ε 是**政策选择不是纯技术值**。学术常见强隐私 ε<5，但真实部署常更高（人口普查 ε=19.61 引发争议）。

### 3.4 联邦学习（FL）

让设备本地训练、只上传「模型更新」而非原始数据。

| 类型 | 数据划分 | 典型场景 |
|---|---|---|
| 横向 FL | 特征相同、样本不同 | 多家医院同病种、Gboard 跨用户 |
| 纵向 FL | 样本重叠、特征互补 | 银行+电商联合建模 |
| 联邦迁移/元学习 | 任务相关 | 跨设备个性化 |

- **经典案例 Gboard**（Google，2017 提出 FL，2019 起大规模落地）：设备下载模型→本地学打字习惯→只回传加密的「小更新」→服务端聚合。辅以**安全聚合（Secure Aggregation，一种 MPC）**使单设备更新不可见。
- **在 LLM 时代的位置与局限**：
  - 位置：仍是「不上传原始数据」的首选范式，适合输入法、推荐等**小模型高频任务**。
  - 局限：① 通信/调度开销大（需设备闲置+充电+WiFi）；② 只解决「数据不出端」，不解决「模型是否记忆敏感样本」——需叠加 DP；③ **大模型全参微调的 FL 在端侧不现实**（带宽与算力），更多走向「云端联邦 + 差分隐私」或参数高效微调；④ 对 Agent 这类「跨 App 行为数据」难以用统一模型刻画。

### 3.5 同态加密（HE）与安全多方计算（MPC）

| 维度 | HE（密文上直接计算） | MPC（多方分片协同计算） | TEE（对照） |
|---|---|---|---|
| 推理延迟开销 | 约 1000×–10000×（BERT 实测 ~149s/query，需 112GB） | 约 10×–100×（BERT 实测 ~2.3s） | 约 1.1×–2× |
| 是否需要可信硬件 | 否（纯软件/密码学） | 否 | 是（依赖芯片） |
| 实时可行性 | 基本不可行（LLM 推理） | 受限（通信瓶颈） | 可行 |
| 典型能用场景 | 加密匹配、私有集交集、离线批处理 | 跨机构联合统计/训练 | 实时敏感数据推理 |

- **为什么 LLM 推理场景仍不实用**：HE 的「自举（bootstrapping）」开销随模型深度指数增长，Transformer 多层必须反复刷新密文噪声，吞吐与延迟都无法接受；MPC 受多轮通信约束。二者当前只在**窄、浅、可离线**的任务（广告转化测量、基因组评分）落地。
- **结论给 PM**：实时 AI 推理的隐私保护，短期现实答案是 **TEE/可验证云**，不是 HE/MPC。HE/MPC 是「强保证但慢」的研究级工具。

## 五、对 Agent 场景的特殊挑战

Agent（尤其是手机 OS 级 Agent，见 [[端侧意图框架 学习笔记]]、[[跨端与多设备意图流转]]）把「信任边界」问题放大了一个数量级——因为它不是处理一段文本，而是**持续拥有上下文与执行力**。

| 挑战 | 为什么比普通 App 更难 | 可能的设计方向 |
|---|---|---|
| 读屏 / 无障碍树 | Agent 能看到屏幕上一切（含其他 App 的敏感内容） | 按需截屏 + 最小上下文窗口 + 屏幕语义脱敏 |
| 读通知 | 通知含验证码、私信、日程 | 通知按敏感度分级，Agent 默认不可读高敏通知 |
| 跨 App 操作 | 一次任务横跨银行/聊天/相册 | 每跳都重新做权限与证明（compound attestation） |
| 长期记忆 | Agent 记忆跨会话留存个人画像 | 记忆加密存储 + 用户可审计/可删除 |
| 工具调用带数据出端 | 调用 [[MCP 与设备侧 MCP]] 工具可能把上下文送出 | 工具侧也需 TEE/可验证，否则信任链断裂 |
| 多 Agent 协作 | 跨 Agent 通信需证明「对方真是它说的那个」 | 消息来源证明 + 新鲜度证明（见 arxiv 2505.03213 综述） |

- **与动作安全的边界再强调**：上表是「**数据怎么被 Agent 看到/带出去**」；[[Agent 执行安全（PM视角）]] 管的是「**Agent 打算做什么动作、要不要确认**」。两者必须配合——一个管「看」，一个管「做」。
- **权限模型建议（广度层面）**：从「App 级权限」升级到「**任务级、瞬时、可撤销**」的权限——Agent 只在执行某一步时临时获得某数据的某视图，步毕即收。

## 六、产品落地速查：需求 → 信任边界落点

把前面所有手段压缩成一张「该用哪段」的查表，方便 PRD 阶段快速定位。

| 产品需求 | 推荐落点 | 理由 |
|---|---|---|
| 离线、低延迟、隐私极敏（本地相册搜索） | ① 纯端侧 | 数据完全不出端，最稳 |
| 端侧算力不够的复杂生成（长文写作/多模态） | ③ 厂商可验证云 | 要满血模型又怕泄露，PCC/TIE 是最佳折中 |
| 跨设备协同的意图/上下文（手机↔车机↔手表） | ①+③ 混合 | 见 [[跨端与多设备意图流转]]，本地缓存+云端验证 |
| 海量用户行为统计（输入法热词、功能使用率） | ④ 本地DP + 联邦学习 | 不收集原始数据也能拿到群体洞察 |
| 跨机构联合建模（银行+电商风控） | ④/⑤ 纵向FL 或 MPC | 数据不出各自域，只交换梯度/分片 |
| 实时敏感推理且须防云厂商（医疗/法务查询） | ②/③ TEE 可验证云 | HE 太慢，TEE 是目前唯一现实选项 |
| 一次性强隐私批处理（加密匹配、转化测量） | ⑤ HE/MPC 窄场景 | 可接受高延迟时 HE 的强保证有价值 |

补充一句：**同一产品的不同功能可能落在光谱不同段**。例如 Apple Intelligence 是「① 默认 + ③ 卸载」，而 Gboard 是「④ 联邦学习 + DP」。PM 的核心动作是「**给每个功能单独定信任边界**」，而非全产品一刀切。

## 七、对 OS PM 的意义

1. **端云协同是产品命题，不是纯技术命题**：用户感知不到 TEE，但能感知「我的数据有没有泄露」。PCC / Private AI Compute 的价值在于把「隐私」做成**可对外宣称且可验证**的卖点。
2. **信任边界要写进产品叙事**：「数据不出端/无状态/可验证」应成为 AI 功能的默认承诺，而非高级开关。
3. **合规是上市门槛**：EU AI Act 透明度标识 2026-08 起适用，GenAI 暂行办法已施行——做面向欧/中市场的 AI 功能，合规清单要前置到 PRD。
4. **Agent 的权限模型是下一代 OS 的核心差异点**：谁先把「任务级瞬时权限 + 可验证工具」做成系统能力，谁就拿到信任红利。
5. **别高估 HE/MPC**：实时 AI 推理的隐私保护现实路径是 TEE/可验证云，PM 做方案评估时别被「密文计算」的想象带偏。
