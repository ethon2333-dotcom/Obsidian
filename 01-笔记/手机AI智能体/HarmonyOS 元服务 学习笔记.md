# HarmonyOS 元服务 学习笔记

> 学习定位：把「元服务」这条线**从应用形态一路推到意图框架**——它是什么、免安装到底换来了什么又付出了什么、它怎么被系统意图框架调度，以及在四平台里它站在哪个位置。
> 本文是**own-words 综合**，不是情报简报。技术细节与情报出处请点深读链接；泛化定义见 [[Atomic Service 元服务]]，本文不重复，只补学习视角与我自己的判断。
> ⚠️ 本文写作过程中**推翻了库内一条既有结论**（「鸿蒙不允许自定义意图」），见第三节 3.3。

---

## 一、一句话心智模型

**元服务 = 免安装、即点即用的「服务原子」。**

它是 HarmonyOS 把「能力」从 App 这个壳里拆出来、交给系统意图框架去调度的**载体**。传统 App 是「一栋楼，用户得先进门」；元服务是「摆在门外的一台自动售货机，系统随时可以替用户按一下」。

三句话把它和邻近概念钉死：

- **元服务** 回答的是「**能力以什么形态存在**」（免安装的轻量程序包）
- **Intents Kit / InsightIntent** 回答的是「**能力怎么被系统找到和调用**」（意图注册 + 调用 + 共享）
- **HMAF / 小艺** 回答的是「**谁来决定调哪个**」（系统级智能体做理解与编排）

三者是**形态 / 契约 / 大脑**，不是同一层的东西——库内不少表述把它们混着讲，这是我自己最容易讲错的地方。

再加一条最反直觉、也最能说明设计意图的：

> **元服务的载体不是设备，是华为账号。**
> 官方对比表里写得很直白：传统应用「跟随设备」，元服务「跟随华为账号」。所以它天然是**跨端**的——不是「装到另一台设备上」，而是「换台设备也还在」。这一条决定了元服务能当跨端流转的单位，而 App 不能。

## 二、元服务是什么（免安装 / 卡片 / 跨端）

### 2.1 官方定义与六大特征

官方原话（元服务概述，更新于 2026-01-22）：

> 「元服务是HarmonyOS提供的一种**轻量应用程序形态**，具备**秒开直达，纯净清爽；服务相伴，恰合时宜；即用即走，账号相随；一体两面，嵌入运行；AI智能，全域流转；高效开发，生而可信**等特征。」
>
> 「元服务**可独立上架、分发、运行，独立实现业务闭环**。」

注意「独立实现业务闭环」这六个字——它不是 App 的一个碎片，而是一个**完整但收窄的产品**。这是元服务和「小组件 / 快捷方式」的根本差别。

另外，**术语沿革**：元服务**原名「原子化服务」（Atomic Service）**。老文档（HarmonyOS 2.0/4.x 时代）说 FA/PA、`installationFree: true`、Ability Gallery；新文档（HarmonyOS NEXT，API 11+）说 Stage 模型、`bundleType: "atomicService"`、只能用「元服务 API 集」。**读到哪套术语，就能判断资料的年代**——这个小技巧在核实鸿蒙资料时非常有用。

### 2.2 元服务 vs 传统应用（官方对比表，逐行）

| 维度 | 传统应用 | **元服务** |
|---|---|---|
| 获取方式 | 手动下载安装 | **免安装**（系统框架后台装好即用） |
| 包大小 | 无限制 | **有硬限制**（见 2.3） |
| 使用模式 | 按需使用 | **即用即走** |
| 更新 | 应用内或应用市场更新 | **自动更新** |
| 功能 | 功能齐全，开发成本高、周期长 | 轻量化完整功能，开发成本较低 |
| **载体** | **跟随设备** | **跟随华为账号** |
| API 范围 | 全量 API | **只能使用「元服务 API 集」** |
| 桌面图标 | 有 | **无桌面 icon**（可手动添加，形式为**服务卡片**） |
| 经营/分发 | 自主运营，**人找应用成本高** | **负一屏等系统分发入口**帮助「人找服务、服务找人」 |

最后一行是这张表的**题眼**：官方自己就把元服务的价值定义为「**系统替你分发**」。这不是技术特性，是**流量模型**——开发者交出「自己拉用户」的主动权，换取「被系统主动推给用户」的机会。第六节会展开这笔交易划不划算。

### 2.3 「免安装」的真实代价：能力被系统性裁剪

这一节是我觉得最值钱的部分，也是所有二手报道**都不讲**的部分。免安装不是白给的，官方上架规范里有一整套硬约束（2026-08-05 核实）：

| 约束 | 具体值 |
|---|---|
| **单包大小** | 压缩后 **≤ 2 MB**（含其 dependency 依赖的 HSP） |
| **总包大小** | 同一设备类型下所有包总和 **≤ 10 MB** |
| **API 面** | **只能使用「元服务 API 集」**，非全量 API；只支持 **Stage 模型 + ArkTS** |
| **组件数量** | **有且仅有一个 UIAbility**，且必须在 entry 模块，启动模式为**单例** |
| **包类型** | 所有 HAP 必须免安装：`bundleType: "atomicService"`（Stage）/ `installationFree: true`（FA） |
| **跳转** | 链接**只支持短链**，不支持 deeplinking 与自认证 applinking，**禁止声明隐式跳转** |
| **Web** | **禁用 arkWeb**，需网页显示只能用 `AtomicServiceWeb` |
| **登录** | 涉及账号体系时**须用华为账号静默登录** |
| **发布** | 目前**仅支持发布到中国大陆地区**；API Level ≥ 10 |

> **一句话收口**：**元服务不是「小一号的 App」，而是「被约束成可被系统随时拉起的执行单元」。**
>
> 2 MB 单包 + 单 UIAbility + 禁隐式跳转 + 强制华为账号，这四条加起来指向同一个设计目标——**让系统能在毫秒级、无歧义、可追溯地拉起它**。免安装是结果，**可预测性**才是原因。
>
> 这条对做 ROM 的人特别有启发：如果安卓要抄免安装，**真正难的不是分发通道，是敢不敢给开发者上这么狠的约束**。国内厂商既没有华为账号这种统一身份底座，也没有强制超级 App 缩到 2MB 的话语权。

### 2.4 卡片：元服务的「常驻表面」

- **服务卡片（Service Widget）**：官方术语，「将用户应用程序的重要信息以卡片形式展示在桌面……达到服务直达、减少层级跳转的目的」。传统应用**可选**配卡片，**元服务必须**至少配一个（老规范里是至少支持 2×2 栅格）。
- **万能卡片**：是元服务卡片的营销/体验说法，强调「桌面上永远打开、无需安装、即用即走、信息外显、动态刷新、一键服务直达」。
- **ArkTS 卡片 vs JS 卡片**：ArkTS 卡片支持自定义动效、自定义绘制、逻辑代码执行；JS 卡片不支持。官方推荐 ArkTS 卡片，纯静态展示才考虑 JS。

> **PM 视角**：卡片是元服务在「用户注意力」上的**唯一常驻资产**。App 有图标，元服务没有——**卡片就是它的图标**。所以「卡片被不被用户留在桌面 / 负一屏」，等价于 App 世界里的「装没装、卸没卸」，是元服务真正的留存指标。

### 2.5 与快应用 / App Clips 的横向对照

| | **HarmonyOS 元服务** | 快应用（安卓联盟） | **Apple App Clips** | Android AppFunctions |
|---|---|---|---|---|
| 免安装 | ✅ | ✅ | ✅ | ❌ **需 App 已安装** |
| 大小约束 | 单包 2MB / 总 10MB | 各家不一（待核实） | iOS 17+ **100 MB**（附条件）；iOS 16 及以前 15 MB；iOS 15 及以前 10 MB | 不适用 |
| 身份载体 | **华为账号** | 设备/厂商账号 | Apple 账号 | 设备 |
| 能否被意图框架调用 | ✅ 注册 `insight_intent.json` | 有限（各家私有） | ❌ **App Intents 在 App Clip 里运行时无功能** | ✅ 这就是它的本体 |
| 常驻表面 | 服务卡片 / 负一屏 | 桌面快捷方式 | 无（用完即走） | 无 |
| 定位 | 能力单元 + 分发单元 | 轻应用 | **App 的试用切片** | **工具接口** |

**这张表里最重要的一格，是 App Clips 那一列的「❌」。** Apple 官方文档明确列出：在 App Clip 运行时**不提供功能**的框架清单里，**第一个就是 App Intents**。

> **这意味着苹果的「免安装」和「意图」是两条不相交的线**：App Clips 解决「没装也能用一次」，App Intents 解决「装了之后能被 Siri 调」——两者不能叠加。
>
> **鸿蒙是唯一把这两条线合并到同一个载体上的平台。** 元服务既免安装、又能注册意图被系统拉起。这是元服务在四平台里**真正独一份**的地方，比「免安装」这个特性本身重要得多。库内此前只强调了免安装，漏掉了这一层。

## 三、与意图框架的关系（`insight_intent.json` / 预置意图）

### 3.1 注册：`insight_intent.json`

App 或元服务通过工程内的 `resources/base/profile/insight_intent.json` 向系统注册自己支持的意图。官方示例（Intents Kit 接入方案，原文含注释）：

```json
{
  "insightIntents": [
    {
      // 名称应当遵循意图框架规范，当前仅支持预置垂域意图，不允许自定义
      "intentName": "PlayMusic",
      "domain": "MusicDomain",
      "intentVersion": "1.0.1",
      "srcEntry": "./ets/entryability/InsightIntentExecutorImpl.ets",
      "uiAbility": {
        "ability": "EntryAbility",
        "executeMode": ["background", "foreground"]
      }
    }
  ]
}
```

几个必须记住的点：

- **`domain` = 垂域**（`MusicDomain`、`BankingDomain`…）。这是鸿蒙意图目录的**一级分类轴**，和 Apple 的 Schema Domains 同构。
- **`intentVersion` 会被校验**：插件引用意图时版本号不一致就调不通。**意图是有版本契约的**，这点比 Android 的 KDoc 描述严格得多。
- **`executeMode: foreground / background`**：决定「拉起可见界面」还是「无界面后台执行」。这是**确认 UI 该不该出现的判据**（见 [[确认机制]]）。
- **上架会校验**：官方注释写「必须声明应用支持插件包含的必选意图，**应用上架时会进行校验**」。→ 意图适配被前置到了**发布关卡**，不是可选项。

### 3.2 双向：意图调用（下行）与意图共享（上行）

- **下行 / 意图调用**：系统（小艺、卡片点击、搜索结果）根据意图拉起元服务，走 `InsightIntentExecutor` 的 `onExecuteInUIAbilityForegroundMode` / `...BackgroundMode`。
- **上行 / 意图共享**：App 主动调 `insightIntent.shareIntent(context, [...])`，把 `intentActionInfo`（动作，含「已执行 EXECUTED」等状态）和 `intentEntityInfo`（实体，含 `keywords`、`rankingHint`、`expirationTime`、`isPublicData` 等）交给系统，用来建本地索引、学行为规律。

这条上行通道正是 [[端侧意图框架 学习笔记]] 6.2 讲的那件事，鸿蒙的术语最清楚。**「服务找人」全靠上行喂出来**，负一屏的推荐质量直接由它决定。

> 值得注意的字段：`isPublicData`、`rankingHint`、`expirationTime`。**开发者可以给系统「排序暗示」**。这在 Android AppFunctions 里没有对应物——那边我一直在追问「谁定排序规则」（见 [[MCP 与设备侧 MCP]] 待解问题），鸿蒙至少**给了开发者一个显式的排序输入口**。这个设计值得单独盯：一旦 `rankingHint` 可被滥用，就是新的「刷排名」战场。

### 3.3 ⚠️ 重要修正：「不允许自定义意图」这句话需要加限定条件

库内 [[端侧意图框架 学习笔记]] 6.1、[[App Intent 的核心作用]]、[[国内安卓厂商做 App Intent 的阻力]] 三处都写了「鸿蒙官方文档明示：仅支持预置垂域意图，**不允许自定义**」。这句引用**本身没错**，但**已经不完整了**。核实结果：

| 开发路径 | 起始 API | 所属 Kit | 能否自定义意图 |
|---|---|---|---|
| **配置文件方式**（`insight_intent.json` 声明 `intentName`/`domain`） | API 11 起 | Intents Kit（智慧分发接入） | ❌ 原文：「当前仅支持预置垂域意图，不允许自定义」 |
| **装饰器方式**（`@InsightIntentEntry` / `@InsightIntentEntity`） | **API 20 起** | **`@kit.AbilityKit`** | ✅ 官方设有专章「**Developing Custom Intents with Intent Decorators**」 |

装饰器方式开发自定义意图时，开发者**必须**自己定义：

- `llmDescription` —— **写给大模型看的能力描述**（例：`'Supports passing song names to play music'`）
- `keywords` —— 意图搜索关键词数组
- `parameters` —— **JSON Schema 格式**的参数定义（type / description / required / minLength…）
- 执行结果结构；复杂参数用 `@InsightIntentEntity` 定义为「意图实体」

而**标准意图**只需填 `schema: 'ViewLogistics'` + `intentVersion`，由系统从附录匹配，**无需**写 `llmDescription`。

> **这条修正的产品含义比技术含义大得多。**
>
> 我此前的整个论述框架是「**预定义派（Apple / 鸿蒙）vs 自由声明派（Android）**」，并由此推出「国内联盟只能走自由声明路线」。现在看：**鸿蒙自己在 API 20 上补了自由声明这条腿**，而且补的方式和 Android AppFunctions 惊人地像——`llmDescription` ≈ KDoc，`parameters` JSON Schema ≈ KSP 生成的 XML Schema。
>
> 所以更准确的表述是：**鸿蒙走的是「预置垂域为主干 + 自定义意图为长尾补充」的双轨制**，而不是纯预定义派。它先用预置垂域锁住高频场景的语义一致性，再开一个口子接长尾——这恰好是我在 [[App Intent 的核心作用]] 待解问题里追问的「预定义覆盖不到的长尾怎么办、这条限制多久会松」的**答案：已经在松，而且是用装饰器 + LLM 描述的方式松的**。
>
> ⚠️ 但要克制：装饰器路径 **API 20 起**，属较新能力，**实际有多少开发者在用、系统路由是否真的平等对待自定义意图与预置意图，未见公开数据**，标为待核实。「不允许自定义」这句话在**智慧分发（搜索/推荐/事件）接入路径**下仍然成立。

## 四、架构要点

自底向上五层，每层只记一句最要紧的：

**① Stage 模型 / UIAbility** —— 元服务**有且仅有一个 UIAbility**、单例、在 entry 模块。意图执行器 `InsightIntentExecutor` 就绑在它上面。`foreground` 走 `startAbility` 拉界面，`background` 走 **Call** 调后台。→ **「无界面执行」在鸿蒙是一等公民，不是变通。**

**② 卡片（FormExtensionAbility）** —— 见 2.4。注意配置文件方式里 `form` 字段绑定的卡片意图**不需要单独写执行器**，系统直接渲染卡片。→ 卡片是「意图的一种返回形态」，不只是入口。

**③ 分布式流转 / 超级终端** —— 官方在元服务设计规范里把 **Service Hopping（服务流转）** 列为核心体验特性之一：「打破设备边界、实现多设备协同」；配合 OneHop 碰一碰、HarmonyOS Connect 标签、Huawei Share 分享即用。因为元服务**跟随华为账号**而非设备，流转天然成立。
⚠️ 「分布式软总线（DSoftBus）」是 HarmonyOS 分布式能力的底层总线术语，但**元服务官方文档中使用的表述是「流转 / 超级终端」**；软总线与元服务免安装拉起之间的具体调用关系，我**未在一手文档中找到明确描述**，标为待核实，不做发挥。

**④ HMAF 2.0（鸿蒙智能体框架）** —— HDC 2026（2026-06-12，东莞松山湖）随 HarmonyOS 7 开发者 Beta 发布。官方口径：主打「**意图即服务**」，**复杂任务成功率 >90%**，**首次开放 GUI 操控能力**，打通 **Agent、Skill、元服务、意图框架、MCP** 多元接入路径。
→ 注意这个清单：**元服务和 MCP 被并列为 HMAF 的接入路径之一**。也就是说在鸿蒙的架构图里，**元服务不是意图框架的全部，只是接入方式之一**。这纠正了我原先「元服务 = 鸿蒙意图框架的载体」的过强表述——它是**主推载体**，不是唯一载体。

**⑤ 小艺：系统级智慧大脑** —— HarmonyOS 7 将小艺升级为基于 **Agentic 自演进架构**的系统级智能体，官方表述为「与操作系统、智能体、应用、**元服务**、Skill 无缝协作」，「基于用户的一句话意图高效匹配服务，自主调用合适的 Agent 或 Skill」。
⚠️ 规模数字（2100+ 系统能力 Skill 化 / 500+ 伙伴 Skills / 2000+ 鸿蒙智能体 / 200+ 项系统级数据 / DAU 1.8 亿）均来自 **HDC 官方通稿的媒体转载**，未在开发者文档中二次确认，**标待核实**。

**⑥ 负一屏 / Today-Task Skill** —— 官方元服务对比表里点名「**负一屏等系统分发入口**帮助人找服务、服务找人」，这是**开发者文档里的正式表述**，不是营销话术。库内 [[AppIntent 每日情报 2026-08-01]] 记录的负一屏 MAU、服务四格→橱窗卡、Today-Task Skill（智能体任务产出自动同步到负一屏）、「探索元服务」LBS 推荐等，属**情报侧口径**，深读见 [[HarmonyOS Intents Kit 与 ArkAF 2026]]。

> **把五层串起来的一句话**：
> **小艺理解 → HMAF 编排 → 意图框架路由 → 元服务执行 → 卡片/负一屏回显。**
> 和我在 [[MCP 与设备侧 MCP]] 里总结的端侧执行总线 `语义理解 → 路由 → 选通道 → 执行 → 结果回显` 是同一根总线，**只是鸿蒙每一段都有自己的品牌名**。看穿这一层，鸿蒙的发布会 PPT 就不再唬人了。

## 五、跨平台对标

| 维度 | **HarmonyOS 元服务** | **Android AppFunctions** | **Apple App Intents / App Clips** | **Windows Copilot Actions** |
|---|---|---|---|---|
| **能力载体** | 免安装元服务 / 已装 App | **已安装 App** | App Intents：已装 App<br>App Clips：免安装切片 | MCP 连接器 / Agent |
| **是否免安装** | ✅ **原生支持** | ❌ | ⚠️ **分裂**：App Clips 免安装但**用不了 App Intents** | ❌ |
| **谁负责发现** | 系统（小艺 / 负一屏 / 搜索 / 服务中心） | **OS 内置 Registry** | Siri / Spotlight / Shortcuts | **ODR 端侧注册表** |
| **谁负责授权** | 系统 + 华为账号；`executeMode` 决定前后台 | **`EXECUTE_APP_FUNCTIONS` 系统权限** | 系统 Confirmation UI + 实体归属 | 隔离工作区 + 低权限 Agent 账号 |
| **谁负责执行** | 元服务自身的 UIAbility（前台/后台） | App 进程内 | App 进程内 | Agent Workspace 内 |
| **Schema 谁定义** | **双轨**：预置垂域（配置文件）+ **自定义（装饰器，API 20+）** | **开发者自由声明**（KDoc → XML） | **平台预定义** Schema Domains | 连接器自述 + 平台受控发现 |
| **自定义开放度** | **中→高**（正在放开） | **高** | **低** | 中 |
| **确认机制** | 系统侧 A2UI / `foreground` 模式；细节待核实 | **下放 App 自己实现** | **系统级 Confirmation UI** | **隔离执行为系统级原语** |
| **跨端流转** | ✅ **强项**（账号载体 + 超级终端） | 弱 | 中（Handoff / 生态内） | 弱 |

**读这张表的三个结论：**

1. **免安装这一格，鸿蒙是唯一的「全绿」。** 安卓压根没有（Instant Apps 已成历史），苹果有但和意图框架**互斥**。这不是小差距，是**结构性差距**——它意味着鸿蒙的意图框架理论上可以覆盖「用户从没装过的服务」，另外三家的意图框架**天花板就是用户已装的 App 集合**。
2. **Schema 定义权这一格，四家正在收敛。** 原先是「预定义派 vs 自由声明派」两极，现在鸿蒙加了自定义装饰器、Android 有 Agent Skill 的 KDoc Refinement 在提升描述质量——**大家都在往「预置主干 + LLM 描述长尾」这个中间态走**。我之前那个二分法该退休了。
3. **确认与隔离这一格，鸿蒙是短板。** Windows 把隔离做成系统级原语，Apple 有系统级 Confirmation UI，鸿蒙这块我**没找到与之对等的一手文档**。考虑到元服务是**免安装 + 可后台执行**，这恰恰是最需要强确认的组合——**没有安装动作，就没有用户显式授予信任的那一刻**，权限边界靠什么锚定？（这个问题 [[HarmonyOS 意图框架竞品观察]] 也提过，至今无解。）

## 六、安卓 PM / 产品视角

### 6.1 入口所有权：元服务是同一命题的更激进版本

我在 [[MCP 与设备侧 MCP]] 里写过一句判断：「一旦工具目录由 OS 托管，**入口价值就从 App 图标转移到系统 Agent**」。元服务把这句话推到了字面意义上的极致——**元服务根本就没有桌面图标**。

对照一下这条链的三级递进：

| 阶段 | App 的形态 | 入口在哪 |
|---|---|---|
| GUI 时代 | 被点的界面 | **App 图标** |
| AppFunctions / App Intents | **被调的工具**（App 还在，图标还在） | 系统 Agent + App 图标**并存** |
| **元服务** | **被拉起的服务原子**（**没有图标**） | **完全在系统侧**（负一屏 / 小艺 / 服务中心 / 卡片） |

→ **元服务不是「入口之争」的一种解法，它是「入口之争」的终局形态**：开发者主动放弃入口，换取系统分发。官方对比表里那句「负一屏等系统分发入口帮助人找服务、服务找人」，本质是一句**交易条款**。

**这笔交易谁会签？** 我的判断是分层的：

- **长尾与工具型服务会签**：本来就买不起流量、装机转化率极低，被系统推是净增量。官方举的新浪财经、喜马拉雅、捷停车、药管家等案例（2023 年口径，⚠️ 待核实）都属这类。
- **头部超级 App 不会签**：2 MB 单包 + 只能用元服务 API 集 + 禁隐式跳转 + **强制华为账号静默登录** + **禁止诱导跳转至 App/微信小程序/快应用**——这几条加起来，等于要求超级 App **交出账号体系、交出跳转、交出交叉推销**。这是它们的命根子，不可能给。

### 6.2 国内厂商做元服务式能力的阻力与机会

阻力这一块 [[国内安卓厂商做 App Intent 的阻力]] 已经把四条讲透了（超级 App 抗拒管道化 / 厂商割据 / 数据主权 / GUI 恶性循环）。元服务这个形态**额外多两条阻力**，是那篇没覆盖的：

1. **缺统一身份底座。** 元服务能「跟随账号」，前提是有一个覆盖全设备、用户默认已登录的华为账号。**国内任何单一安卓厂商的账号体系都做不到这个渗透率**，跨厂商更不可能。没有统一账号，「免安装但保留状态」就落不了地——用户每次都要重新登录，「即用即走」就变成「即用即卡」。
2. **缺强制约束的话语权。** 2 MB 这条线是华为敢下、也下得动的。任何国内安卓厂商跟超级 App 说「你的服务要压到 2MB 才能进我的免安装通道」，对方的回答是可以预见的。**约束能不能落地，取决于平台方的议价权，而不是技术方案的优劣。**

**那机会在哪？** 我认为不在「复制元服务」，而在三个更小的切口：

- **先做「服务卡片 + 上行意图共享」，别急着做免安装。** 卡片是低对抗的——它给 App **增加**曝光而不是**减少**曝光，超级 App 的抵触远小于「后台执行、去界面化」。先把上行通道跑通，「服务找人」的推荐质量才有燃料（[[端侧意图框架 学习笔记]] 6.5 那个「没有上行，服务找人做不起来」的问题，答案可能是：**上行要用曝光去换，不能用合规去逼**）。
- **抄「双轨 Schema」而不是抄「预定义」。** 见 3.3。鸿蒙自己都在往双轨走，联盟标准直接定成「预置高频垂域 + 自定义长尾（带 LLM 描述）」，比纯自由声明的语义质量高，又不需要压倒性号召力。
- **抄「排序暗示 + 归因回传」这个思路。** `rankingHint` 说明鸿蒙意识到「得给开发者一个可以博弈的旋钮」。这正好接上 [[国内安卓厂商做 App Intent 的阻力]] 里我那个待解问题——「能不能让 App 在 Intent 调用中仍获得曝光与归因」。**给旋钮，比给道理管用。**

> **一句话总结这一节**：元服务在鸿蒙成立，靠的是**统一账号 + 单一厂商约束力 + 系统级分发位**三件套。国内安卓这三件都没有，**所以「最值得抄的点是元服务」这个库内旧结论，需要降级为「最值得抄的是元服务背后的分发机制，而不是免安装这个形态」。**

## 八、待解问题

- [ ] **免安装 = 没有安装动作 = 没有用户显式授予信任的那一刻。那元服务的信任模型锚在哪？** 是锚在华为账号、锚在上架审核、还是锚在每次调用时的 `foreground` 弹窗？如果一个 `executeMode: background` 的元服务能被小艺静默拉起并执行，**用户在整条链路上到底在哪一步同意过？** → 一手文档中**未找到**元服务专属的授权/确认规范，待核实。（与 [[Atomic Service 元服务]] 的同名待解问题重合，说明这是真空白而非我没查到。）
- [ ] **API 20 的自定义意图装饰器，系统路由会平等对待自定义意图与预置垂域意图吗？** 如果预置意图在小艺的匹配里天然优先，那「开放自定义」就只是姿态。→ 未见公开的路由/优先级规则，待核实。
- [ ] **`rankingHint` 这个字段会不会长成新的 ASO 战场？** 开发者可以自报排序权重，系统凭什么信？有没有反作弊机制？如果没有，头部服务只要把 `rankingHint` 拉满就能压制长尾——**那「系统分发更公平」这个卖点就不成立了。**
- [ ] **2 MB 的硬约束，在「元服务要接入 Agent、要跑端侧插件」之后还守得住吗？** 一个要和 HMAF 交互、要渲染 A2UI、要处理多轮意图的元服务，2 MB 够用吗？还是说复杂 Agent 逻辑其实都跑在系统侧/云侧，元服务只是个薄壳？→ **这个问题的答案决定了元服务到底是「能力单元」还是「展示单元」**，很关键，但我没找到一手依据。
- [ ] **国内安卓如果做不了「跟随账号」，有没有「跟随设备但免安装」的次优解？** （类似快应用 + 端侧缓存 + 厂商账号打通联盟）这条路的用户体验损失有多大，值不值得？
