# 端侧大模型推理 学习笔记

> 学习定位：本篇是**广度种子笔记（BREADTH > DEPTH）**。目标是在一张图里把"在手机上跑 LLM"这件事的全貌铺开——定义、为什么重要、技术分类、2025-2026 新进展、与端侧意图框架/OS 的连接。深度子方向（具体量化方案、KV-cache 调度、各框架性能对比）一律用 `- [ ]` 待解问题留白，等 Ethon 后续按兴趣深挖。
> 本文是 **own-words 综合**，不是情报简报。具体数字凡来自二手综述的都标了「⚠️ 待核实」，不编造。

---

## 一、一句话心智模型

**端侧大模型推理 = 把 LLM 的"大脑"塞进手机 NPU/CPU 本地跑，让模型权重和你的数据都不必离开设备。**

再补一句最容易讲错的：

> **"模型在端侧跑"≠"整个体验在端侧"。** 它只解决了"推理发生在哪"，没解决"谁在做规划（Planner）"和"数据是否曾离开端"。真正的隐私/延迟红利，要等**端侧 Planner + 端侧工具 + 本地数据**三件套齐活才成立（这条和 [[MCP 与设备侧 MCP]] 里"执行侧本地化 ≠ 全栈本地化"是同一个坑）。

---

## 二、是什么（定义 / 为什么重要）

### 2.1 定义

端侧大模型推理（On-Device LLM Inference）：把参数量从几亿到几十亿的 LLM，直接部署在**手机 SoC 的 CPU / GPU / NPU** 上做前向推理，而不是把请求发到云机房。典型载体是 1B–8B 量级的小模型（或稀疏 MoE 的"激活子集"），配合量化把内存压到 1–4GB 可跑。

### 2.2 为什么重要 —— 四个理由必须分开算账

| 理由 | 成立的真正条件 | 容易过度承诺的地方 |
|---|---|---|
| **隐私** | 推理的输入/输出留在设备 | 仅对"执行段"成立；若 Planner 在云上，用户那句话本身可能已上云 |
| **延迟** | 省掉"Agent → 云 server"的网络往返与冷启动 | 若 Planner 在云，端到端延迟仍被云上那一跳支配 |
| **离线** | 端侧模型 + 端侧工具 + 本地数据，三者缺一不可 | 被调 App 自己要联网（查快递、下订单），照样离不了线 |
| **成本** | 跳过按 token 计费、省云 GPU 资源 | 换来的是端侧算力/功耗/发热的硬约束，不是免费 |

> 一句话收口：**端侧推理是"成本与信任结构的转移"**——把云的钱、延迟、隐私风险，换成端的电、热、内存墙。PM 对外讲"更隐私/更快"时，必须限定到"执行段"，否则就是过度承诺（也见 [[MCP 与设备侧 MCP]] 4.3）。

### 2.3 它解决的根本矛盾

百亿参数模型 vs 手机严苛资源约束（内存、带宽、功耗、散热）之间的鸿沟。所有技术（量化、NPU、KV-cache 优化）本质上都在"填这条鸿沟"。

## 三、主流方案 / 分类（表格）

我把端侧推理拆成四层：**硬件加速层 / 模型压缩层 / 系统优化层 / 推理框架层**。PM 视角重点记住"方案 = 哪一层在发力"，别混成一锅。

### 3.1 硬件加速：NPU 是主角

| 厂商 | 方案 | 要点 |
|---|---|---|
| **高通 Qualcomm** | **Snapdragon NPU（Hexagon）** + AI Engine Direct (QNN) | 旗舰骁龙 8 系标配；NPU 在 prefill（预填充）阶段相对 CPU 可高倍数加速 ⚠️ 待核实 |
| **联发科 MediaTek** | **NeuroPilot** APU | 天玑旗舰多核 APU；LiteRT-LM / ExecuTorch 均已接入 |
| **Apple** | **Neural Engine (ANE)** | M 系/NPU 统一内存架构；Core ML + MLX 直打 ANE，INT4 量化 |
| **Google** | **Tensor NPU** | Pixel 专属；Gemini Nano 跑在上面；LiteRT-LM 一等支持 |
| **华为海思** | **达芬奇 NPU** | 麒麟配套（⚠️ 国内生态口径较封闭，待核实） |

> ⚠️ 关键认知：**NPU 在"预填充"阶段收益大，在"逐 token 解码"（batch=1）阶段优势有限**——解码受内存带宽和 kernel 启动延迟拖累。所以"NPU 加速 10 倍"这种口号要问清楚是测的哪一段。

### 3.2 模型压缩：量化是必选项

| 技术 | 在干什么 | 代表 |
|---|---|---|
| **权重量化** | FP16/BF16 权重压成 INT8/INT4/INT2 | GGUF 的多档 IQ 量化（llama.cpp）、4-bit HQQ（ExecuTorch）、INT4（Core ML） |
| **稀疏 / MoE** | 推理时只激活部分参数 | Qwen3-Next 的 80B-A3B（仅 ~3B 激活）、Gemma 4 的 MoE 变体 ⚠️ 待核实 |
| **架构级省内存** | PLE（Per-Layer Embeddings）、MatFormer | Gemma 3n 把 8B 原始参数压到"等效 4B"内存占用 |

### 3.3 系统优化：KV-cache 是性能命门

- **KV-cache 是什么**：自回归解码时缓存历史 token 的 Key/Value，避免重复计算。它是端侧内存墙的主要来源。
- **常见优化**：KV-cache 量化（压缩显存）、Paged KV（MLC-LLM）、KV-cache 溢出到 Flash/DRAM 混合存储（MNN-LLM 的 DRAM-Flash 技术，支持长上下文）。
- **Prefill/Decode 拆分**：把算力密集的预填充甩给 NPU，逐 token 解码交给 GPU/CPU 的异构分工，是端侧推理的主流趋势。

### 3.4 推理框架：选哪个决定你能落哪

| 框架 | 出身 | 定位 / 特点 | 硬件后端 |
|---|---|---|---|
| **llama.cpp** | Georgi Gerganov（C/C++） | 社区事实标准；GGUF 单文件 + 多档量化；最便携 | CPU / CUDA / Metal / Vulkan / **QNN（高通 NPU）** |
| **Ollama** | 基于 llama.cpp | 开箱即用本地服务，暴露 OpenAI 兼容 API | 同 llama.cpp |
| **MLC-LLM** | Apache TVM | GPU-first + **WebGPU（浏览器内跑）**；paged KV | Metal / Vulkan / OpenCL / WebGPU |
| **ExecuTorch** | Meta | 移动端生产标准；**50KB 最小运行时**；PyTorch 原生导出 `.pte` | Core ML / QNN / XNNPACK / Vulkan / MediaTek / Exynos |
| **MediaPipe LLM** | Google | 与 Google AI Edge 生态一体；多模态提示 | Gemma 系 + AI Edge 后端 |
| **LiteRT-LM** | Google（TF Lite 接班人） | 专为 LLM 重做：原生 KV-cache、NPU/GPU/CPU 三重调度、`.litertlm` 格式 | 同上 + **NPU 一等支持** |
| **MLX** | Apple | Apple Silicon 专属，统一内存，吞吐最高 | Apple GPU/NPU |
| **ONNX Runtime** | Microsoft | 企业 Windows 路线，DirectML 走 NPU/GPU | Windows NPU/GPU |

> ⚠️ 性能数字（如 MLC-LLM 在 Mali/Adreno 仅 5–20% ALU 利用率、MNN-LLM 比 llama.cpp 快 8.6× 预填充等）多来自二手综述/论文，本文不背书具体倍数，深读时以一手基准为准。

## 四、2025—2026 进展与代表产品

### 4.1 端侧小模型"军备竞赛"已成型

| 模型 | 时间 | 关键点（一手源优先） |
|---|---|---|
| **Gemma 3n** | 预览 I/O 2025-05，正式发布 **2025-06-26**（DeepMind 官方） | 移动优先多模态（图/音/视频/文）；E2B(等效2B/2GB)、E4B(等效4B/3GB)；**MatFormer + PLE** 架构；LMArena >1300（<10B 首个）；支持 140 语言文本、35 语言多模态；兼容 llama.cpp / Ollama / LiteRT / MLX |
| **Qwen3-Next** | **2025-09** 发布（Unsloth/阿里口径） | 80B-A3B 稀疏 MoE，**每 token 仅 ~3B 激活**；256K 上下文；MoE + Gated DeltaNet/Gated Attention 混合架构；Instruct / Thinking 双变体；训练成本 < Qwen3-32B 的 10% ⚠️ 待核实倍数 |
| **Phi-4-mini** | 微软小模型家族 | 3.8B，指令遵循/推理越级；4-bit GGUF 约 2.5GB，Ollama/MLX 均可跑 |
| **Gemma 4 / 系列延伸** | 2026（⚠️ 型号与节点待核实） | 出现了 Gemma 4 2B MoE 的端侧部署样例（LiteRT-LM + 骁龙 NPU） |

> 趋势判断：**"小模型 + 架构创新（MoE/MatFormer/PLE）"正在把端侧可用模型从 2B 拉到等效 4–8B 质量档**，这是 2025-2026 最值得 PM 盯的主线。

### 4.2 框架与平台里程碑

- **ExecuTorch 1.0 GA**：2025-10 发布、2026-01 v1.1.0（⚠️ 二手综述口径，待一手源对齐）——被视为移动端生产标准，已用于 Instagram/WhatsApp/Quest 等数十亿用户产品。
- **Apple Foundation Models**（WWDC 2025-06）：开发者可免费调用设备端 Apple Intelligence 模型，支持 guided generation / tool calling / 结构化输出——但**只限苹果自家模型、苹果设备**。
- **LiteRT-LM / MediaPipe LLM**：Google 把端侧 LLM 推理收进 AI Edge 统一工具链，NPU 加速对接高通、联发科、Tensor。
- **Google AI Edge Gallery**：Android 端直接部署 Gemma 系做对话/图像理解的应用样板。

### 4.3 代表产品（已在售 / 已落地）

| 产品 | 端侧模型载体 | 状态 |
|---|---|---|
| **Google Pixel** | Gemini Nano（Tensor NPU） | 已落地于系统级摘要/改写等 |
| **iPhone / Apple Intelligence** | 设备端 Foundation Models（ANE） | iOS 18+，开发者可调 |
| **Samsung Galaxy（骁龙 8 系）** | 高通 NPU + 各家端侧模型 | 骁龙 8 Elite 等旗舰 |
| **各类 Android App** | 经 LiteRT-LM / ExecuTorch 集成 | 开发者自集成阶段 |

## 五、与端侧意图框架 / OS 的连接

这是本篇和库内其他笔记的咬合点，也是 PM 最该关心的"组合价值"：

1. **端侧推理是端侧 Agent 的"大脑"，意图框架是"手脚"**。[[端侧意图框架 学习笔记]] 讲的是 OS 如何发现/授权/路由 App 能力；本篇讲的是"理解用户意图的那坨模型"能不能也在端上跑。
2. **只有两者都在端侧，低延迟/隐私才闭环**。回看 [[MCP 与设备侧 MCP]] 4.3 的结论：AppFunctions 只解决了"工具在端侧"，若 Planner（规划/理解）在云，延迟和隐私的红利就被云上那一跳吃掉了。**端侧 LLM 推理补上的正是"Planner 本地化"这一半**。
3. **与 [[Android AppFunctions 设备侧意图 2026]] 的关系**：AppFunctions 是"被调工具"，端侧 LLM 是"调用方的大脑"。两者合起来 = 一个完整端侧 Agent：模型在 NPU 上理解意图 → 经 OS Registry 发现 AppFunctions → 在端侧执行。这条链路正是 Android 想推的"端侧执行总线"。

> **PM 判断**：端侧推理的商业化价值，不单在"跑个模型"，而在它和端侧意图框架叠加后，能把**入口价值从 App 图标挪到系统 Agent**（和 [[MCP 与设备侧 MCP]] 4.4 的判断同源）。但前提是 Planner 和工具都本地化，否则只是半截方案。
