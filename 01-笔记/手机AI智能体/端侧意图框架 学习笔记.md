# 端侧意图框架 学习笔记

> 学习定位：把「端侧意图框架」这个主题一次性串起来——它是什么、四大平台各自怎么建、各家的核心构件是什么，以及**作为一个安卓/AOSP PM 我真正要关心的待解问题**。
> 本文是**综览/地图**，不是深度报告。每一块都给出「深读」链接，点进去才是细节。自己的判断请写到 [[App Intent 的核心作用]] / [[竞品情报 MOC]] 等手写笔记里。

## 一、一句话心智模型

- **意图框架 = 让"我说一句话，系统去办成"成为操作系统级能力的那套机制**：自然语言/任务 → 语义理解 → 路由到正确的 App 能力 → 端侧执行 → 结果回显。
- 它和「应用层 Agent 框架」不是一回事：前者是**系统级意图总线**（OS 提供标准门窗 + 调度 + 安全），后者是**应用内编排**。对照见 [[应用层 Agent 框架 vs 系统级意图框架 对照]]。
- 当下所有厂商都在抢同一件事：**把 LLM 的"理解"接到真实软件世界上**，但落地路线差异极大。

## 二、四平台格局对照（学习用对比表）

| 维度 | Android（AppFunctions） | HarmonyOS（Intents Kit / ArkAF） | Apple（App Intents） | Windows（Copilot Actions / Agent Workspace） |
|---|---|---|---|---|
| 意图形态 | 设备侧意图，官方 Agent Skill 生命周期（发现/实现/KDoc/测试） | Want 显式意图 + 权限校验 | App Intents 2.0：streaming / 富实体 / 多轮 | Copilot Actions |
| 服务发现 | 依赖 App 安装 + Registry | **元服务免安装**（installationFree） | App 声明的 Intents | Agent accounts / Workspace |
| 架构层次 | AppFunctions → Registry/权限 | ArkAF 2.0 三层：意图 → 技能 → A2A | Schema Protocol + Confirmations + entity ownership | 四支柱：User Control / Agent accounts / Workspace / Transparency |
| 理解放哪 | 明示"理解可能在云端" | 图谱推理（Graph Reasoning Engine） | 端侧+云端协同 | 端侧隔离 Agent |

## 六、深化补充（2026-08，官方文档核实）

### 6.1 对照表要加的第三个维度：**Schema 由谁定义**

第二节那张表比的是「形态/发现/架构」，漏了一个更根本的分歧——**能力目录的词汇表由谁写**：

| 平台 | 登记方式 | 谁定义 Schema |
|---|---|---|
| Apple | `@AppIntent(schema: .audio.addToPlaylist)` 对齐系统 App Schema Domains | **平台预定义** |
| HarmonyOS | `insight_intent.json` 声明 `intentName`/`domain`/`intentVersion` | **平台预定义**——官方文档明示「当前仅支持预置垂域意图，**不允许自定义**」 |
| Android | `@AppFunction(isDescribedByKDoc = true)`，KDoc 即工具描述，KSP 构建期生成 XML Schema | **开发者自由声明** |
| Windows | MCP 连接器注册进 ODR | 连接器自述 + 平台受控发现 |

**这条分歧决定了推行方式**：预定义派要求平台有压倒性生态号召力（Apple、华为在自家生态里有）；自由声明派没有这个门槛，但路由质量吃开发者文档质量——所以 Google 官方 Agent Skill 专门设了一步 **KDoc Refinement**。**国内任一安卓厂商都不具备预定义派的号召力，联盟标准现实上只能走自由声明路线。**

### 6.2 补一条心智模型：意图框架都是**双向**的

第一节的模型「自然语言 → 路由 → 执行 → 回显」只画了**下行**。真实框架都还有一条**上行通道**，且它才是「主动推荐」的燃料：

| 方向 | HarmonyOS（术语最清楚） | Apple 对应物 |
|---|---|---|
| **下行：意图调用** | 系统主动调用 App 功能（播放音乐、查旅游攻略） | Siri 执行 App Intent |
| **上行：意图共享** | App 主动向系统共享意图，供系统建**本地索引**、学**行为规律**；动作分「**完成时**」（已执行，供搜索与建议）与「**将来时**」（基于预测，供搜索） | `IntentDonationManager` 交互捐献（学规律）+ `IndexedEntity`→Spotlight 语义索引（可搜索）+ `RelevantEntities`（主动声明情境相关性） |

→ **对 PM 的用处**：「一句话直达」只用到了下行；**「服务找人」（负一屏卡片、小艺建议、Siri 建议）全靠上行**。评估一个 App 的意图适配完成度，不能只看它注册了几个 Intent，还要看它有没有在共享/捐赠。鸿蒙官方把智慧分发拆成 5 类特性：习惯推荐 / 事件推荐 / 位置推荐 / 技能调用-语音 / 本地搜索——**只有一类是「调用」，其余四类全是上行喂出来的**。

### 6.3 回填第五节待解问题 #1（Registry / 权限）——部分有答案了

| 问题 | Android（已核实） | Apple / HarmonyOS / Windows |
|---|---|---|
| 谁能调用 | 调用方须持 `EXECUTE_APP_FUNCTIONS` 权限 | 待补 |
| 适用版本 | Android 16+；Gemini 集成自 2026-05 起**可信测试人员私测**，官方标注**实验性预览** | 待补 |
| **动态可见性** | ✅ `@AppFunction(isEnabled = false)` + `AppFunctionManager.setAppFunctionEnabled(...)`——**Registry 是随账号状态实时变化的动态视图，不是静态清单** | ❌ 三家均**无公开 API，待补** |
| 验证手段 | `adb shell cmd app_function list-app-functions`；官方 AppFunctions 测试代理 App | 待补 |

**Android 是四家里唯一有公开动态可见性 API 的**——这条对做 ROM 侧 Registry 设计直接有参考价值。

### 6.4 第五节待解问题 #2（意图元数据来源分级）——答案是「成熟模型已存在，四大 OS 都还没采纳」

微软 Agent Governance Toolkit 给出了完整参考实现：六类来源枚举（`tool_output`/`api_response`/`agent_message`/`user_input`/`database`/`file`）+ 四级分类（`public→internal→confidential→restricted`）+ **单调棘轮**（敏感度只升不降）+ 两阶段闸口（`post_tool`/`pre_output`）。

⚠️ 但它是**开源治理层，不是 OS 层**；Apple/Android/HarmonyOS/Windows 的意图元数据**都没有来源类型字段，也没有分级**（2026-08-04 逐条复核）。→ **这不是技术空白，是产品优先级问题**，可直接作为竞品分析与内部 PRD 的论据。详见 [[数据溯源分级与单调棘轮]]。

### 6.5 新增待解问题
- [ ] 上行通道（意图共享/捐赠）是**隐私成本最高的一段**——App 要持续把用户行为交给系统。国内超级 App 连下行调用都不给，凭什么给上行数据？**没有上行，「服务找人」在国内安卓是不是根本做不起来？**
- [ ] 鸿蒙「不允许自定义意图」是保语义一致性的强手段。如果安卓联盟也这么干，**第一批该预置哪些垂域**？预置得越少推得越快、覆盖越差，这个平衡点怎么定？
- [ ] Registry 动态可见性一旦普及，会不会出现新的博弈形态——**超级 App 把能力注册进去但常年 `isEnabled = false`**，用来应付合规/联盟要求却不真开放？这种「形式适配」怎么被系统识别和治理？
