> 心智模型：端侧模型增量更新 = 用「最小差异包」把新模型权重贴到旧模型上；差分量化工程让这个 diff 既小又准——核心矛盾是**补丁体积 vs 合并后精度**，diff 算法负责「小」，量化感知负责「准」，二者共同决定端侧模型能否低成本反复进化。

## 广度覆盖

| 工程子领域 | 定义 | 分类 | 主流方案 | 2025–2026 进展 | 代表产品 / 厂商 |
| --- | --- | --- | --- | --- | --- |
| **二进制 diff（whole-file delta）** | 把新旧模型文件当作不透明字节流，计算其差异补丁，设备端用旧文件 + 补丁还原新文件 | 通用二进制 diff：bsdiff、xdelta、vcdiff（RFC 3284）、courgette（Chrome 的二次 diff，对指令流重排版后再 diff）；需配合双分区 / A/B slot 与签名校验 | bsdiff（基于后缀数组 + bzip2）、xdelta3、VCDIFF、courgette（语义感知）、bsdiff4 | 仍是边缘 AI 模型「架构不变、仅换权重」冷更新的事实标准；普遍与「下载临时区 → hash+签名校验 → fsync → 原子 rename」的原子替换流程绑定（厂商/博客口径，待核实） | 通用算法（bsdiff / xdelta / courgette 社区）；TinyMLDelta（TFLite Micro 差分更新，社区方案）；边缘 OTA 平台 Memfault / Mender |
| **块级 / 张量级 delta（block-wise / tensor-wise delta）** | 不把模型当黑盒，而是按权重张量 / 分块对齐后逐块求差，避免「一处改动导致整文件无法匹配」的错位 | 对齐策略：按 layer name、按 tensor、按固定字节块；差异表示：稀疏非零索引 delta（仅存变化权重）、结构化 chunk diff | 华为云示例「按 layer 对齐 → 存非零 delta → 设备端加权合并」；tensor 级 diff（权重矩阵分块后逐块 diff，便于内容寻址去重） | 与「内容寻址存储（CAS）+ 分层 base+adapter」结合成主流范式：稳定 base 不动、常更新的小 adapter 走块级 delta 减带宽（匿名 pilot 口径，待核实） | 华为云（按层 delta 合并示例）、Google AI Edge / LiteRT、Meta ExecuTorch（PyTorch 直接导出，2024 GA） |
| **量化感知 delta / 差分量化（quantization-aware delta & differential quantization）** | 在「量化空间」里做差分：要么存全精度残差以修正量化误差，要么对 delta 本身做混合精度量化，使补丁小且合并后精度可恢复 | ① 残差矩阵法（存「全精度−量化」残差修正，如 DecDEC）；② 锚点+delta 分解（高精锚点吸收 outlier、低比特存 delta，如 DeltaQuant）；③ 低秩+量化残差（LQ-LoRA / QA-LoRA）；④ 训练侧差分量化（DQ error-feedback，联邦/分布式梯度压缩） | DecDEC（OSDI 2025，残差存 CPU、按需取显著通道修正）、DeltaQuant（CVPR 2026，时空 delta 平滑）、LQ-LoRA / QA-LoRA、SVDQuant、Differentially Quantized Gradient Methods（Lin et al.） | 2025–2026 出现「量化 + delta/残差」融合浪潮：用极小残差/低秩项补偿量化损失，使 3~4bit 模型更新后近乎无损；端侧焦点在「delta 在 INT4/2bit 上合并是否安全」 | 学术界（Seoul National Univ. DecDEC；CVPR 2026 DeltaQuant；LQ-LoRA/QA-LoRA 社区）；框架层 LiteRT / ExecuTorch 量化工具链 |
| **端侧模型 A/B 实验** | 在亿级异构设备上对「模型版本」做随机分流与在线指标回收，验证新模型效果后再全量 | ① Remote Config 模型参数 + 远程模型下载 + 激活事件（Firebase ML 范式）；② 双分区 A/B slot；③ 影子 / holdout 对照 | Firebase ML A/B Testing（Remote Config 指定模型名 → 不同用户加载不同远程模型 → 自定义 Analytics 事件作目标指标，无需发版即可换模型）、Google Play 实验、厂商自研 cohort 系统 | Firebase ML 已有**官方端侧模型 A/B 文档**（两版模型对比、远程可配、自定义事件指标）；Google I/O 2025 推 **Play for On-Device AI（beta）** 管理自定义模型下载/更新 | Firebase ML（Google）、Google Play 控制台 / Play for On-Device AI（beta）、Apple（Foundation Models 随 OS 更新，非独立 A/B）、安卓厂商自研 |
| **带宽 / 存储收益度量** | 量化增量更新的 ROI：补丁体积 vs 全量、设备端缓存去重、存储占用 | 度量维度：补丁压缩比、内容寻址去重率、delta adapter 体积、回滚保留的双份占用 | bsdiff 补丁通常仅为全量 10%~30%（厂商/博客口径，待核实）、TinyMLDelta 67KB 变更仅 475 字节（社区口径，待核实）、分层 base+2~5MB adapter（匿名 pilot，待核实） | 共识：差分更新可省 70–90% 下发流量（厂商外媒体/咨询口径，待核实）；存储侧靠「base 共享 + adapter 增量 + CAS 去重」把端上冗余收敛到最小 | 边缘 OTA 平台（Memfault / Mender）；Google AI Edge Portal（端侧 benchmark/evals，I/O 2025）；厂商 fleet 管理 |

### 关键工程要点（点到为止）
- 二进制 diff 对模型「重打包/重排」敏感：两个数值等价但字节不同的模型，diff 会失效 → 需固定序列化 / 对齐。
- 块级 delta 必须保证张量对齐，否则索引错位会**静默破坏**权重。
- 量化感知 delta 本质是用「残差 / 低秩 / 锚点」换取精度恢复，代价是额外存储极小的修正项。
- 合并后必须做校验（hash / 签名 + 离线回归测试），防止精度漂移累积。
- 端侧 A/B 关键在：稳定设备 ID 分流、激活事件埋点、指标回收不能拖垮功耗 / 网络。

## 深度盲区

- [ ] 待解问题：量化感知 delta 的「残差 / 低秩修正项」在端侧占多少额外存储？与省下的补丁体积是否划算（ROI 拐点）？
- [ ] 待解问题：端侧 A/B 实验如何在**亿级异构设备**上做随机分流与在线指标回收，且不被功耗 / 网络拖垮？Firebase ML 范式之外有无厂商自研的轻量方案？

- [ ] 待解问题：差分更新失败 / 补丁损坏时的**安全回退**边界——双分区占用双倍存储，低端机存储预算如何取舍？
