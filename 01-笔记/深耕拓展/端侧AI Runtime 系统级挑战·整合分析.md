## 0. 一句话收口

端侧 SLM 带来的不是某一项指标挑战，而是**推翻了 OS 三十年的一条隐含假设：「后台任务是可以被牺牲的」**。它同时具备「系统服务的不可杀性」+「远超普通 App 的资源占用」，这个矛盾是全部挑战（ZRAM 失效、LMK 两难、NPU 抢占难、热降频）的共同根。

---

## 1. 三条横切主线（贯穿所有源笔记）

### 主线 A：无损优化 vs 有损优化 —— PM 唯一必须守住的边界

| 手段 | 性质 | PM 该怎么处理 |
|---|---|---|
| PagedAttention（合租，消碎片） | **无损** | 无脑上，工程做到极致 |
| KV INT4 量化（压缩） | 极小损（PPL<1%） | 基本无脑上 |
| **Token Eviction（断舍离，扔历史）** | **有损、不可逆** | **必须回到产品桌决策，不能工程自决** |
| **投机采样 SpecDec** | **无损（数学保证）** | **唯一不用 A/B 验证质量的优化**，落地阻力小一个数量级 |

> 推论：凡「工程说能自动降内存」的，先问它是不是承重墙（如 Attention Sink——最前 4 token 删了模型瞬间崩，是机制必需不是语义重要）。

### 主线 B：公地悲剧 —— 系统 Runtime 存在的唯一硬理由

System AI Runtime（Android AICore / Apple Foundation / HarmonyOS CANN）的 4 大护城河里，**只有「全局资源仲裁」不可替代**（单个 App 看不到全局 NPU/内存）。其余（硬件适配、沙盒、系统特性）App 侧都能部分自解。

- 历史同构：推送连接（2018）→ 定位权限（2020）→ **NPU/AI 内存（2026）**，每一仗都是「野蛮生长→公地悲剧→系统收权+统一 API→App 最终接入」。
- **谈判话术**：别拿「我们适配更好」说服 App 接入，要拿「不接入你会在 NPU 冲突时被无差别限流，接入才有 QoS 优先级」——后者对方无法自己解决。

### 主线 C：降级不变量 —— 模型变笨，确认反而要更强

动态调度（热×电×存）+ QoS 分级（P0/P1/P2）是已有框架。两个关键修正：
1. **矩阵应是四维**：热×电×存×**前台性（用户是否在等）**——同样高温低电，前台等待要保速度，后台静默应直接暂停。第四维直接对齐 QoS 分级，不另造概念。
2. **风险阈值必须随降级同步收紧**：降级只动速度/质量/功耗，**不能动安全边界**；能力变弱时若保不了确认/隔离，应主动降级为「不可用并提示」。很多系统在降级时同时放宽确认，是最危险的组合。

## 2. 四个被原文回避 / 低估的产品级问题

1. **频次才是真门槛**：2GB 常驻＝用户不知情地少了 1/6 内存。立项标准应是「预估 DAU 频次 × 单次价值 > 常驻内存机会成本」。系统级入口（负一屏、全局搜索）拼命做，本质是**把频次做上去让这笔账算平**。
2. **端→云降级是隐私决策不是性能决策**：降级切云端绝不能静默，需一次性 opt-in 授权（默认关，参考 Windows 姿态）。
3. **共享 System Prompt KV 是平台权力**：谁定义它谁定义全系统 Agent 的基础行为规范；也是全系统级攻击面（污染即全崩）。工程优化悄悄变成产品决策的典型。
4. **软失败不可观测**：Agent 理解错意图不崩不卡不报错，传统 Crash/ANR/Jank 三件套失效。需行为信号埋点（中途取消率 / 执行后立即手动重做率 / 置信度分布）。

## 3. 实测方案如何补上「原理→真机」的缺口

[[OS-PM-端侧AI Runtime 实测实验方案]] 给出 6 个实验，PM 最该盯的 3 条：
- **NPU 真执行率**：「支持 NPU」≠「整图在 NPU」，weight-only INT4 易因反量化 fallback 到 CPU；Runtime/driver/模型/SoC 必须进同一兼容矩阵。
- **持续热性能**：峰值≠可持续，看 20 分钟后 P95 TPOT、每 1K token 能耗、前台掉帧。
- **App Runtime vs 系统 Runtime**：系统是否托管不只看速度，还看内存/更新/隐私/跨 App 复用——这是 OS PM 区别于推理工程师的关键判断。
