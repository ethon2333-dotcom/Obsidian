# 设备侧 MCP 与跨应用执行总线·深化

> 衍生深耕笔记（Round 1）。在 [[MCP 与设备侧 MCP]] 的基础上，把「端侧执行总线 vs 设备侧 MCP」的边界讲透，并补上源笔记里被带过、但对 PM 决策最关键的几处：三通道分工的本质、隐私/延迟/离线的分账、以及「总线」为什么是入口所有权的技术载体。
> 本文是 [[手机端AI智能体·意图框架横切全景]] 的技术支撑篇。

---

## 1. 先纠三个常见错位

1. **设备侧 MCP 改变的是「工具在哪执行」，不自动解决「谁在思考」「数据从哪来」。**
2. **MCP 没有 "1.0"**：用 `YYYY-MM-DD` 日期版本（当前 2026-07-28）。有 1.0 的是 A2A，两件事常被混。
3. **端侧工具 ≠ 另一套系统**：Google 官方明说 agent 会「同时考虑 remote MCP tools 与 local AppFunctions」——它们是**同一份工具清单里的两类条目**。

---

## 2. 端侧执行总线：那根被收进 OS 的主干

总线 = `语义理解 → 路由 → 选通道 → 执行 → 结果回显`。
设备侧 MCP 是这根总线上**结构化通道的一种具体形态**，不是总线本身。

**为什么它配叫「总线」而不只是一个 API——因为三件事都被收进了 OS：**

| 能力 | 谁来做 | 含义 |
|---|---|---|
| 发现 | OS 内置 Registry（Android） | 不是各 Agent 自己维护清单 |
| 准入 | `EXECUTE_APP_FUNCTIONS` 系统权限 | 不是 App 间私下约定 |
| 编排 | agent 把端侧 + 云侧工具放同一清单统一挑 | App 只负责「声明」 |

→ App 从「被点的界面」退化成「被调的工具」。这是入口所有权转移的技术落点（见 [[手机端AI智能体·意图框架横切全景]] ⑤）。

---

## 3. 三通道分工的本质：风险准入分级链

| 通道 | 干什么 | 风险档 | 类比 |
|---|---|---|---|
| built-in intents | 拉起并履约 | 低 | 传统意图 |
| **AppFunctions** | **带类型参数 + 返回结构化结果** | 中 | ← 设备侧 MCP 在这里 |
| UI Automation | 未适配长尾兜底 | 仅限低风险只读/可重试 | GUI 路线 |

> 关键修正（来自 [[安卓厂商意图识别破局策略]] 深化）：L3 GUI **只能做低风险只读与可重试动作，绝不能做写操作和支付**。三分边界 = 系统理解 / App 履约与支付 / 用户最终决定权。

---

## 4. 隐私 / 延迟 / 离线：必须分开算账（防 PPT 骗自己）

| 好处 | 成立条件 | 真实边界 |
|---|---|---|
| **隐私** | 仅「执行段」留端 | 理解段可能上云（Android 官方明示 system agents may process on server）→「执行在端」≠「全链路在端」 |
| **延迟** | 省掉下半程 | 若 Planner 在云，端到端仍被云支配；真低延迟要端侧 Planner + 端侧工具两头齐 |
| **离线** | 端侧模型+端侧工具+本地数据 三缺一不行 | AppFunctions 只解决第二项；被调 App 自己要联网照样离不了线 |

> **收口**：设备侧 MCP 是「执行侧本地化」，不是「全栈本地化」。对外讲隐私必须限定到执行段，否则就是过度承诺。

---

## 5. 协议三件套：同一件事的三个切面

MCP / A2A / 端侧 Intent 框架其实是**让能力可被①描述②授权③调用**的三种实现：

| | 描述 | 授权 | 调用 |
|---|---|---|---|
| MCP | `tools/list` / schema | OAuth 2.1 + 受众绑定 | JSON-RPC |
| A2A | AgentCard（可签名） | OAuth / mTLS | JSON-RPC / gRPC |
| 端侧 Intent | KDoc→XML / 意图声明 | 系统权限 | OS Registry + Manager |

→ `AgentCard`、`tools/list`、OS Registry 是**同一概念的三种实现**。看懂这一层，任何新协议都不晕。
