# 代码助手的供应链与依赖安全评测 学习笔记

> [!abstract] 一句话心智模型
> 当 Copilot / Cursor / 通义灵码生成代码并「顺手」引入一个包时，**这行 import 不是建议，而是一条供应链入口**——它可能是不存在的「幻觉包」（slopsquatting）、被投毒的孪生名、带 GPL 传染条款的代码片段，或藏着一个已知 CVE；评测的本体，是「AI 替你决定的依赖」是否可信、可追、可审计。

> 本篇刻意区别于 [[AI 编程助手的代码安全评测基准 学习笔记]]（聚焦「生成代码自身」的安全评测基准，如不安全补全率 / 漏洞修复率 / 代码内提示注入）与 [[AI 模型供应链安全与开源投毒防护 学习笔记]]（聚焦「模型权重 / 料包」投毒）。**本篇聚焦「AI 生成代码所引入的第三方依赖/包」这一层供应链的评测**——即从 `import`/`pip install` 这一跳进入的物料风险。与 [[AI 编程助手的代码安全责任 学习笔记]]（谁担责 + 护栏范式）互补。

## 一、广度覆盖

### ① 问题定义 / 为什么这是独立议题

AI 编程助手在补全代码时会**主动或被动地建议第三方依赖**（import 语句、install 命令、框架选型）。这些依赖并非开发者从已知清单中挑选，而是模型基于训练语料「生成」出来的。由此引出三类经典软件供应链风险在「AI 生成」语境下的新形态：

- **信任错配**：开发者信任 AI 的建议，但 AI 不验证包是否真实存在 / 是否安全。
- **审计盲区**：AI 生成的代码片段（非 manifest 声明的依赖）常游离于 SCA 工具之外（Black Duck OSSRA 2026：约 17% 的开源组件经复制粘贴 / AI 生成进入代码库，传统 manifest 扫描看不见）。
- **监管对齐**：EU CRA 规定 AI 生成代码与人类代码同责，且强制机器可读 SBOM——评测缺失 = 合规缺口。

### ② 按风险类型分类

| 风险类型 | 本质 | 触发机制 | 代表性攻击/术语 |
|---|---|---|---|
| **依赖投毒（Poisoning）** | 安装的包本身是恶意代码 | 攻击者抢注 AI 推荐的（含幻觉的）包名；或接管合法包发布恶意版本 | slopsquatting（幻觉包抢注）、typosquatting、dependency confusion（依赖混淆）、maintainer takeover |
| **许可证风险（License）** | AI 生成代码夹带 copyleft 义务 | 模型在 GPL/AGPL/LGPL 语料上训练，生成片段不带许可证上下文 → 企业闭源代码被「传染」 | license laundering（许可证漂洗）、GPL/AGPL 传染、M&A 尽调暴雷 |
| **已知 CVE / 漏洞** | 引入含已知漏洞的依赖版本 | AI 倾向推荐训练语料里常见、但历史悠久有 CVE 的库；或推荐过时版本 | SCA / CVE / EPSS / KEV 评测 |
| **幻觉包（Hallucinated Package）** | 包根本不存在，被攻击者预注册 | LLM 凭空生成 plausible 但虚假的包名（如 `strutils-pro`、`secure-random`），攻击者埋伏同名恶意包 |  coined by Seth Larson（PSF）；"slop" + squatting |

### ③ 主流评测方案与代表工具（按能力分层）

| 能力层 | 代表工具 | 评测对象 / 原理 | 说明 |
|---|---|---|---|
| **SBOM 生成（代码-gen 物料清单）** | `cdxgen` / `@cdxgen/cdxgen`（OWASP）、Syft（Anchore）、Trivy（Aqua，含 SBOM 输出）、CycloneDX CLI、SPDX tools | 从源码/lockfile/容器生成 CycloneDX 或 SPDX 清单 | 2026 起 cdxgen 支持 AI-BOM 命令（记录 prompt 文件、AI 服务、MCP 配置、模型元数据） |
| **AI-BOM（AI 物料清单）** | CycloneDX ML-BOM、SPDX 3.0 AI/Dataset profiles、BearingPoint FOSS AI-BOM 服务 | 在 SBOM 之外补充：AI 生成代码溯源、模型/数据集、license、prompts、MCP server | G7 2026「SBOM for AI — Minimum Elements」七簇框架：metadata / system / models / datasets / infrastructure / security / KPIs |
| **已知漏洞扫描（SCA）** | Snyk、Dependabot（GitHub）、`osv-scanner`（Google，OSV 库，语言无关）、pip-audit（PyPA）、Grype（Anchore）、SonarQube SCA | 对照 NVD/OSV/KEV 等库查已知 CVE、EPSS、可 exploited 性 | 多为「已知 CVE」层；**不覆盖**幻觉包名与新建可疑包 |
| **行为/投毒前置检测** | Socket（安装前行为分析：网络/文件/壳执行/混淆/typo 相似度）、Phylum、Aikido、Semgrep | 在包进入前分析「它会做什么」，而非查 CVE 库 | Socket 2025 起专门标注 AI 幻觉包名；与 CI PR 评论集成 |
| **许可证合规评测** | Black Duck SCA（snippet 级匹配）、FOSSA、ScanCode | 代码片段/依赖级 license 识别、冲突报警、notice 文件生成 | 针对「AI 生成片段无 license 上下文」的 snippet 匹配是关键 |
| **安装期降低攻击面** | `npm install --ignore-scripts` / `pip install --no-deps` 等策略 | 阻断 install 脚本执行（多数投毒靠 preinstall/postinstall） | 工程习惯，非「评测」但属评测后的缓解闸门 |

### ④ 2025–2026 进展（点到为止）

- **幻觉包被量化（USENIX Security 2025）**：UT San Antonio + Virginia Tech + Univ. of Oklahoma「We Have a Package for You!」在 16 个代码生成模型上生成 2.23M/57.6 万样本（Python/JS），**19.7% 样本含至少 1 个不存在的包**，产生 205,474 个虚构包名；商业模型平均 5.2%、开源模型 21.7%（CodeLlama 系最高超 33%，GPT-4 Turbo 最佳 3.59%）。
- **术语「slopsquatting」确立**（Seth Larson, PSF）：区别于 typosquatting——开发者没打错字，是模型替你错。
- **2026 复测收窄但未消失**：对 5 个前沿模型复测，幻觉率降至 4.62%–6.10%；但发现 **127 个包名被 5 个模型「完全一致」地虚构**，其中 53 个仍可注册 → 跨模型共享幻觉 = 攻击者一次性埋伏即可覆盖全生态。
- **真实攻击已发生（2026）**：研究者抽取 107 个幻觉包名上传 npm，成本约 $496，6 个月内 35.2% 安装来自真实开发者；**给生成器加 web 搜索反而更糟**（幻觉持久率 11.2%→17.3%，因搜索结果本就被 AI 内容污染）。
- **云安全联盟（CSA）2026-04 定调**：把每个「AI 推荐的依赖」当作不可信输入处理。
- **监管落地**：EU CRA（Reg. 2024/2847）强制机器可读 SBOM，AI/人类代码同责，漏洞报告义务 2026-09-11 生效、全面适用 2027-12-11；EU AI Act 透明度义务 2026-08 起；CISA 2025 Minimum Elements 增补 Component Hash / License / Tool Name / Generation Context；G7「SBOM for AI」七簇框架（自愿）。
- **许可证冲突创历史新高（Black Duck OSSRA 2026）**：947 个商业代码库，68% 含 license 冲突（较去年 56% 跳升 12pt，史上最大单年涨幅），主因 AI「license laundering」；仅 54% 组织对 AI 代码做 IP/license 评估。

## 二、深度盲区（待解问题）

- [ ] 待解问题：AI 生成依赖的「幻觉率」能否进入持续评测/CI 门禁，而非一次性研究？（现有 SCA 工具多数仍不检查「AI 虚构包名」这一层）
- [ ] 待解问题：当 AI 助手**自动执行** `npm install`（自主 SWE Agent 场景）时，人工 `npm view` 校验失效，如何把「预安装验证」做成 agent 自身的强制步骤？
- [ ] 待解问题：AI-BOM 与 SBOM 的边界如何落地——模型权重、prompt、MCP server 该进哪个文档？CycloneDX ML-BOM vs SPDX 3.0 AI profile 谁做主格式？
- [ ] 待解问题：license laundering 的「责任归属」——生成 GPL 片段的 AI 厂商、采用代码的开发者、发布产品的组织，谁为传染义务负责？（接 [[AI 编程助手的代码安全责任 学习笔记]]）
- [ ] 待解问题：跨模型「共享幻觉包名」是否应建立行业级预注册/抢注预警（类似域名抢注监测）？谁来运营？
- [ ] 待解问题：评测基准本身的可比性——幻觉率、CVE 引入率、license 冲突率由不同厂商/学术团队各自测量，缺乏统一口径（呼应 [[AI 编程助手的代码安全评测基准 学习笔记]] 的「基准不可比」挑战）。
