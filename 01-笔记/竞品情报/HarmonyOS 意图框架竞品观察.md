# HarmonyOS 意图框架竞品观察

> 竞品视角：鸿蒙（HarmonyOS NEXT）的意图框架，对安卓 PM 有什么可借鉴。
> 技术细节见 [[HarmonyOS Intents Kit 与 ArkAF 2026]] / [[Atomic Service 元服务]]。

## 鸿蒙怎么做
- **Intents Kit（Want）**：系统级意图分发，类似 Android Intent 但更强调**显式意图 + 权限校验**。
- **元服务（Atomic Service，installationFree）**：免安装即点即用，能力以「元服务」形态被系统调度——这点是安卓（尤其国内）最缺的：**服务发现不依赖 App 安装**。
- **ArkAF 2.0 三层**：意图（Intent）→ 技能（Skills）→ A2A（端侧/云侧双模智能体互操作）。比单点 Intent 更进一步到「技能编排 + 跨智能体」。
- **A2UI**：意图结果可直接渲染为系统 UI，减少跳 App。
- **Graph Reasoning Engine**：意图理解用图谱推理，而非纯 LLM。

## 对安卓的启示（PM 可抄的点）
1. **元服务/免安装**是「打破应用孤岛」的更激进形态——国内安卓被安装壁垒困住，值得推动「快应用/元服务」级能力。
2. **A2A 端侧协议**会是下一战场：智能体之间互调能力，比 App 互调更高维。
3. **意图→技能→A2A 分层**可作安卓意图框架演进路线参考。

## 风险/差异
- 鸿蒙有系统统治力（单一厂商），国内安卓是群雄割据——同样的框架，落地难度不同（见 [[国内安卓厂商做 App Intent 的阻力]]）。

## 深化补充

### 一句话心智模型

> **鸿蒙在做的不是「更好用的语音助手」，而是把「App」这个封装单位拆小成「能被系统检索到的能力单元」。**

我自己的类比：安卓现在的 Intent 像**敲门**——我知道隔壁住着人（App 已安装），我去敲，他开不开门看他心情（有没有实现那个 Intent Filter）。鸿蒙的元服务 + Skill 像**黄页 + 上门服务**——系统手里有一本目录，知道谁能干什么（`describe`）、怎么干（`execute`），用户根本不需要知道"隔壁住着谁"。

这个差别的要害在**分发权归属**：敲门模型下，用户先选 App、App 再干活，流量入口在应用商店；黄页模型下，系统先解析意图、再挑能力，**入口挪到了 OS**。所以这不是技术选型问题，是生意问题（详见下面的关联）。

### 具体例子与对比

三个我觉得最能说明问题的落地样本（均为厂商披露口径，见文末待核实）：

| 场景 | 走的通道 | 为什么这么选 |
|---|---|---|
| 头部银行 App，覆盖 1000+ 金融意图 | **端侧 A2A** | 余额/转账是隐私数据，**不出端**是硬约束，宁可牺牲推理深度 |
| 大麦「问答→选座→购票→支付」闭环 | **云侧 A2A** | 选座是复杂多轮决策，需要云端深推理；票务数据本来就在云上 |
| 小艺「帮帮忙」操作支付宝/淘宝/拼多多 | **GUI Agent 兜底** | 对方没接 Skill，只能靠"看屏幕点按钮" |

**第三行才是最值得盯的一行。** 它暴露了一个所有意图框架都逃不掉的现实：**生态接入永远不可能 100%**。鸿蒙的答案是"官方通道 + GUI 兜底"双轨——能接的走高速路，不接的走小路照样过去。而且实测里**微信提示「尚未接入」**——最大的那个 App 不进你的黄页，这件事本身就说明了平台方和超级 App 的博弈没有终局（见 [[意图框架的商业与生态博弈]]）。

再对比一下三家的"分层"，会发现大家其实收敛到同一个骨架，只是叫法不同：

| 层 | 鸿蒙 ArkAF / HMAF 2.0 | 安卓 | Windows |
|---|---|---|---|
| 意图理解 | 端侧盘古 6.0 解析 | AppFunctions 声明式 schema | Copilot 自然语言 |
| **编排/调度** | **图推理引擎，拆 DAG 并行调度** | 待明确 | Copilot Actions 链式执行 |
| 能力封装 | Skill（`describe`/`execute`） | AppFunction | MCP 连接器 |
| 发现机制 | 小艺开放平台 | EAP 受控发现 | ODR 注册表 |
| 隔离执行 | 相对弱（重端侧隐私） | 待明确 | **Agent Workspace 最成体系** |

看这张表我的判断是：**鸿蒙强在编排层，Windows 强在隔离层**。鸿蒙敢公开讲"图推理引擎拆 DAG 并行调度"，是四家里唯一把编排引擎结构摊开讲的；而 Windows 把"Agent 跑坏了炸不到系统"做到了标杆。安卓要抄，**这两块得分别抄**，而不是抄一家。

### 一个反直觉的点

"图推理引擎而非纯 LLM 做意图理解"——初看像技术保守，细想是**产品选择**。纯 LLM 做多步任务拆解，成功率上不去且不可解释；用图谱约束搜索空间，能把复杂任务成功率做到官方称的 >90%。代价是**只能处理图里已建模的意图**，泛化差。这就是典型的 **可靠性 vs 泛化性** 权衡——面向"办正事"（转账、买票）的系统级 Agent，应该往可靠性一侧偏，这个 trade-off 我认同（参考 [[Intent Router 语义路由]] 里的路由分层思路）。

### 待解问题

- [ ] 鸿蒙的「图推理引擎」，那张图是**人工建模**的还是**从日志挖掘**的？如果是人工建，1000+ 金融意图的维护成本谁扛？这决定了这套东西能不能被安卓这种多厂商生态复制。
- [ ] 元服务免安装 = 服务发现不依赖安装。但**免安装的信任模型**是什么？没有安装动作 = 没有用户显式授予信任的时刻，那权限边界靠什么锚定？（对比 Windows 是靠"Agent 数字签名 + ACL"）
- [ ] 微信不接入，鸿蒙靠 GUI Agent 兜底。**如果超级 App 主动做反 GUI-Agent 对抗**（改布局、加验证），这条兜底路线还成立吗？安卓做同样的事会不会更早撞上这堵墙？
- [ ] 「入口从应用商店挪到 OS」，那**元服务的商业化分成**怎么算？如果没有清晰的钱路，头部 App 有什么动力把能力交出来？
