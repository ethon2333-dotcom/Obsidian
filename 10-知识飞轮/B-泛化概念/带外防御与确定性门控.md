# 带外防御与确定性门控

## 一句话定义

**带外防御（out-of-band defense）** 指把 Agent 的**参考监视器（reference monitor）移到模型之外**，由**确定性门控**（规则 / 能力凭证 / 信息流控制）而非「模型守卫模型」来裁决动作是否放行。核心口号：**「门不能是模型」**——因为 guardrail 模型本身也是模型，它自己就可被注入。

## 为什么重要

- **它给出了「检测 vs 结构」之争的结论**：in-band（带内）防御**没有安全保证**——Nasr 等人已在 **>90% 成功率**下攻破 12 种既有防御；OWASP LLM01:2025 亦指出护栏模型可被注入。**检测输了，结构赢了。**
- **它把 LLM 安全接回经典安全学**：论文用 **Biba 完整性模型、reference monitor、Saltzer–Schroeder 原则、capabilities / IFC** 重述提示注入问题，并做 **8 维度系统化**——意味着这不是「新领域没有理论」，而是**已有理论没被用上**。
- **它给出了安全税的量价**：确定性门控效果确实好，但**代价是可用性与调用量**（见下表）。这是评估任何 Agent 安全方案时的成本锚点，与 [[Agent Data Injection 数据注入攻击]] 记录的「CaMeL Strict 归零 → 可用性 36.5%」构成同一条兑换曲线的两个采样点。
- **AIMS 是它对确认机制的反向论点**：**Agent Identity Management System（AIMS）** 主张 **「LLM MUST NOT hold credentials」**，且**授权应由授权服务器完成，而不是由本地 UI 确认**——直接冲击 [[Confirmation UI 安全机制]] 的默认假设。

## 适用边界

- **适用**：高价值 / 不可逆 / 涉钱涉隐私的动作裁决；服务端或算力充裕环境。
- **不适用**：**端侧全量上门控算不起账**——~15× LLM 调用叠加端侧本就紧张的算力（LFM2.5-8B-A1B 笔记本 253 tok/s、手机约 30 tok/s，见 [[Function Calling 端侧工具调用]]），交互感会直接崩塌。
- **现实路径是按动作风险分层**：只读 / 可逆动作走快路径不加门；破坏性 / 不可逆 / 涉钱涉隐私走带外门 + 硬件级审批（[[Agent 身份与硬件级审批]]）。
- **更便宜的半替代品**：[[数据溯源分级与单调棘轮]] 的「来源打标 + 单调棘轮」近乎零推理成本，是端侧唯一现实可落地的那一半。

| 项目 | 数值 |
|---|---|
| ASR（逐级加固） | **25.8% → 4.2% → 2.6%** |
| 可用性代价 | **~45% → ~26%** |
| LLM 调用量 | **~15×** |

⚠️ 作者自己标注：该 7B 是**弱 agent**，绝对数字有 artifact 成分，趋势可信、绝对值不可外推。

**对照锚点**（来自 [[Agent Data Injection 数据注入攻击]]）：CaMeL Strict 对 ADI 归零，代价是可用性 **81.2–84.8% → 36.5%**。两组数字共同说明：**当前架构下「强隔离 / 强门控」与「可用」是硬兑换关系。**

## 可复用启发

1. **评估任何 Agent 防注入方案，先问「裁决者是不是模型」**。若是，它就在攻击面之内。
2. **本地点击 ≠ 授权**（AIMS）。若 Agent 已被 ADI / IPI 污染，它呈现给用户的确认文案本身就是被操纵的产物——用户确认的是攻击者写好的话。这条把 [[Confirmation UI 安全机制]] 的判据推到第三档「带外授权」。
3. **安全预算要按动作分层，不能按系统统一定价**。给 PM 的落地形态：一张「动作 × 可逆性 × 资产敏感度 → 门控档位」的矩阵，而非全局开关。
4. **端侧的正确问法不是「能不能上带外门」，而是「带外门能不能不靠 LLM 实现」**——例如放进 TEE / 安全芯片，避开重复推理开销。

## 2026-08-09晚 增补：「门不能是模型」的第一次工业现实校验（来源 [[AppIntent 每日情报 2026-08-09-晚]]）

本笔记原则来自 arXiv 2606.26479 的实验室结论。**Chrome 的 agentic 安全架构**（Nathan Parker，**2025-12-08**，详见 [[Chrome Agent Origin Sets 与用户对齐评判器 2026]]）是目前唯一可对照的**大规模产品实现**，它对本原则给出的答案是**「部分成立 + 一个折中变体」**：

| 判断项 | 本笔记原则 | Chrome 实际做法 | 判读 |
|---|---|---|---|
| origin 能否加入白名单 | 门必须确定性 | **确定性门控函数**，且不暴露给不可信内容 | ✅ 完全一致 |
| 模型生成的 URL 能否导航 | 同上 | **确定性检查**，限已知公开 URL | ✅ 一致 |
| 是否银行 / 医疗站点 | 高后果动作走确定性 | **确定性清单**，不用分类器 | ✅ 一致，且是对「按动作分层定价」的直接印证 |
| origin 是否与任务相关 | —— | **模型**（critic 变体） | ⚠️ **折中**：语义相关性无法确定性判定 |
| 动作是否对齐用户目标 | 裁决者不应是模型 | **模型**（User Alignment Critic） | ⚠️ **折中**：靠**隔离**（只喂动作元数据、不喂网页正文）而非确定性来保证不被污染 |

**提炼出的第三条路线（本库新增判据）**：除了「确定性门」与「模型门」，工业界实际在用第三种——**隔离门**：裁决者仍是模型，但其**输入面被架构性收窄到不可被攻击者写入的部分**。Chrome 的 critic 只看 planner 产出的动作元数据，官方称其 `"cannot be poisoned directly from the web"`。

- **代价**：它把风险从「门被注入」转移到「**门的输入被上游污染的 planner 伪造**」。若被污染的 planner 能编出一段「看起来对齐」的动作描述，critic 无从分辨——**这正是本笔记既有未决问题「Progent 策略由 LLM 撰写」的同构变体**，两处自指漏洞可合并跟踪。
- **对端侧的意义**：隔离门比确定性门更容易落地（不需要穷举策略），也比 TEE 方案更便宜（无需硬件），**是端侧 Agent 现阶段最现实的中间档**。但它**不能**用于不可逆动作的最终授权——那一档仍须带外（[[Agent 身份与硬件级审批]]）。

新增未决问题：

- [ ] 「隔离门」的输入面收窄到什么程度才算安全？是否存在可形式化的判据（如：输入中不含任何攻击者可控字节）？
- [ ] Chrome 首版仅实现 read-writeable 集合，read-only 集合缺席期间，隔离门的实际保护强度如何？
