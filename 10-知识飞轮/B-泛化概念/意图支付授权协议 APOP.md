# 意图支付授权协议 APOP

> 净新增概念节点（2026-08-03 晚）。库内既有 [[确认机制]] / [[意图模式规范]] 无法承载「协议层意图凭证」这一面，故独立成节点。

## 一句话定义

**APOP（Agentic Payment Open Protocol，智能体支付开放协议）** 是把「用户授权 Agent 代为支付」这件事，从**应用层的一次性确认弹窗**，提升为**协议层可验证、可持久、可追责的意图授权凭证**的标准。

## 为什么重要

四大 OS 的意图框架目前**全部停在「执行」这一层**：

| 平台 | 解决了什么 | 没解决什么 |
|---|---|---|
| Apple App Intents | Agent 怎么调到 App 的能力 | 这次代理行为的**授权凭什么算数** |
| Android AppFunctions | 同上（+ Registry 权限） | 同上 |
| Windows Copilot Actions | 同上（+ 隔离账户） | 同上 |
| HarmonyOS Intents Kit | 同上（+ 元服务免安装） | 同上 |

它们回答的是「**能不能调**」，不回答「**这次代理决策的责任归属与凭证**」。APOP 是目前检索到的**首个把「意图授权」本身标准化**的协议：把「用户授权了**什么意图** / **多少额度** / **多久时效** / **谁担责**」写成可验证凭证，而不是一个点完就消失的弹窗。

**对 OS PM 的意义**：确认机制（Confirmation UI）的下一形态大概率不是「更好的弹窗」，而是「**弹窗产出一份可核验的授权凭证**」。谁先把这层做进系统 API，谁就拿到了跨应用 Agent 编排的信任底座。

## 适用边界

- 目前是**中国银联主导的支付垂域协议**，不是 OS 级通用授权框架；能否泛化到非支付类高风险操作（发邮件、删文件、改配置）**未验证**。
- 与 OS 意图框架的对接路径**待补**：AppFunctions / App Intents 调起支付时能否携带 APOP 凭证，还是必须走各自 SDK，未见公开说明。
- 协议全文与技术规范链接**待补**，本节点内容基于媒体报道，非一手规范。

## 证据与例子

- **发布时间**：2026-04-02（APOP 本体）；配套 **AVOP（Agent Value-added service Protocol，智能体增值服务协议）**。
- **协议覆盖链路**：意图管理 → 身份与授权 → 风控 → 清算。
- **2026-08-03 生态里程碑**：**40+ 机构接入**；新增「**支付 Skills 开发技能包**」，商户/开发者接入周期从 **5–7 天压缩到分钟级**。
- ⚠️ AVOP 细节在 2026-07-27 报道中已出现，08-03 属**生态进展**而非协议变更。

## 可复用启发

1. **区分「执行授权」与「能力授权」。** 现有 OS 权限模型（`EXECUTE_APP_FUNCTIONS` 等）授的是**能力**（这个 Agent 可以调支付），APOP 授的是**单次执行**（这个 Agent 可以为这件事花这么多钱）。做系统设计时这两层必须分开，合并会导致要么过度授权、要么每次都打断用户。
2. **确认 UI 的产物应该是数据，不是事件。** 弹窗点「确认」只产生一个事件（不可追溯、不可核验、可被注入绕过）；应产生一份**带意图内容哈希的凭证**——这样即使 Agent 被 [[XPIA 跨提示注入]] 劫持改单，凭证与实际请求不匹配即可拦截。⚠️ APOP 是否真做到内容绑定，**待补核实**。
3. **凭证四要素可作为通用检查表**：授权内容 / 额度或范围 / 时效 / 责任主体。评审任何「Agent 代替用户做高风险操作」的方案时，缺任一项即为设计缺口。
