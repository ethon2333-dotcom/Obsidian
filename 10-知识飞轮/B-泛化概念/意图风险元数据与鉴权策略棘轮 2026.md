# 意图风险元数据与鉴权策略棘轮 2026

## 一句话定义

**意图风险元数据（intent risk metadata）** 是操作系统给每个可被 Agent 调用的意图预置的「后果性标签」，由 **schema 承载、采用即继承**；配套的 **鉴权策略棘轮** 规定开发者只能把继承来的鉴权要求**改严不能改松**——两者合起来，把「危险动作是否要确认 / 要解锁」从 App 的自由裁量收回成系统的确定性判定。

## 为什么重要

这是本库追踪 8 天的最高优先待办的**实质性突破，但答案与预期不同**：

- 此前判定「四平台意图元数据分级**全空白**」（见 [[Agent Data Injection 数据注入攻击]]）。
- WWDC26 Session 347 证明：**Apple 早已有意图元数据分级，只是分级轴不是「数据来源」而是「动作副作用」**。
- 因此结论必须拆成两条正交轴：
  | 轴 | 问的问题 | Apple 现状 |
  |---|---|---|
  | **副作用轴**（动作有多危险） | 这个 intent 执行后会删数据 / 花钱 / 外泄吗？ | ✅ 已有：schema 内置 risk metadata + 默认 authenticationPolicy |
  | **来源轴**（数据可信吗） | 填进参数的这段文本来自谁？可信吗？ | ❌ 仍全空白：无来源绑定 / 签名 / 密级 |

**对 OS PM 的直接含义**：副作用轴是「已被证明可做、且 Apple 已做完」的工程，来源轴才是真空白。做 Registry 设计时不该再把两者混为一谈——前者可以照抄 Apple，后者仍需原创。

## 适用边界

- **只覆盖 schema 采用者**。风险元数据「技术上属于 schema 本身」；纯自定义 intent 不继承任何东西，须开发者手写 `authenticationPolicy`——**这就是分级的漏底**：不采用 schema = 不被分级。
- **风险判定是静态 + 动态的合成**，不是查表。系统把 intent 的静态 risk metadata 与**系统动态状态**一起喂给风险评估组件，两者结合才得出「本次是否需要确认」。这意味着同一个 intent 在不同上下文下确认行为**不一致**——对开发者是黑盒，对测试是不可复现风险。
- **风险元数据的具体取值 Apple 未公开**。只知道分类维度（破坏性 / 外泄性 / 更新共享内容 / 持久化存储），不知道枚举值、不可读取、不可查询。**待补**：是否有 API 让 App 查询自己 intent 被判成几级。
- **棘轮只管鉴权，不管确认**。`authenticationPolicy` 有「只能改严」约束；但**确认（confirmation）没有对应的开发者可写字段**——确认完全由系统判，开发者既不能加强也不能削弱。

## 证据与例子

**机制链路（Session 347 官方口径）**

1. intent 采用 App Schema → 自动成为 Siri 模型可见的 tool；
2. 模型选中某 intent → **执行前**系统用该 intent 的 risk metadata 调用风险评估系统；
3. 风险评估系统同时读取**系统动态状态**；
4. 合成风险偏高 → 弹出用户确认；用户**拒绝则执行被阻断，intent 根本不被调用**。

**风险元数据继承（无需开发者做任何事）**

```swift
@AppIntent(schema: .photos.deleteAssets)
struct DeletePhotoIntent {
    var entities: [LooseLeafPhoto]
    // deleteAssets schema 自带「破坏性副作用」→ 本 intent 自动继承
    // 该 schema 默认 authenticationPolicy 为 .requiresAuthentication → 亦自动继承
    func perform() async throws -> some IntentResult { /* ... */ }
}
```

**自定义 intent 须手写鉴权策略**

```swift
struct DeletePhotoIntent: DeleteIntent {
    var entities: [LooseLeafPhoto]
    static var authenticationPolicy: IntentAuthenticationPolicy = .requiresAuthentication
    func perform() async throws -> some IntentResult { /* ... */ }
}
```

**棘轮规则原文口径**：schema 采用者继承 schema 默认策略，开发者**可以覆写，但只能覆写成更严格的策略，不能更宽松**（"developers may override it only with a stricter policy, not a weaker one"）。

**为什么需要动态状态：`createTimer` 反例（Apple 亲自举的）**

- 表面看「创建一个计时器」无副作用，似乎不必确认；
- 但 schema 定义了**可选的 String 标签**字段，而参数由模型决定 → 注入可把标签设成攻击者文本；
- 后续「列出我的计时器」把该标签读回上下文 → **新上下文被污染**（即 persistent poisoning / stored injection）；
- 结论：**对 `createTimer` 一律跳过确认是不安全的**，系统靠动态状态识别这类中间态。

> ⚠️ **口径纪律**：以上 API 名（`IntentAuthenticationPolicy`、`.requiresAuthentication`、`authenticationPolicy`）来自 Session 347 官方视频页与结构化转录；`risk metadata` 是 Apple 在讲述中使用的**内部机制名，非公开 API 符号**——不可当作可调用接口写进 PRD。风险等级枚举值、可查询性均**待补**。

## 可复用启发

1. **「后果性标记」应由 Schema 承载而非 App 声明**——App 会为了少弹窗而低报风险，schema 是系统资产，天然免疫这种激励错位。这正是 [[Confirmation UI 安全机制]] 中「触发器分类法第 3 档（确定性规则）」的官方实例。
2. **单调棘轮是可复用的授权原语**。本库在 [[数据溯源分级与单调棘轮]] 中记录的「密级只升不降」，与 Apple 的「鉴权只严不松」是**同一形状用在不同对象上**（数据密级 vs 动作授权）。凡是「默认值由平台给、允许方自行调整」的设计，都应加单调约束。
3. **低风险动作的写入面才是真风险面**。`createTimer` 的教训可外推成判据：**任何允许模型填自由文本、且该文本后续会被读回上下文的字段，都是持久化注入点**——与 [[XPIA 跨提示注入]]、[[Agent Data Injection 数据注入攻击]] 的写回路径三问判据（见 [[Agent 写回路径 XPIA 风险评估 SOP]]）直接接续。
4. **不采用 schema = 逃出分级**。任何基于 schema 的分级体系都有这个天然漏底；Registry 设计时应考虑「自定义意图默认按最高风险处理」的兜底，而非默认最低。

## 2026-08-17 增补：Session 347 逐字稿补代码级护栏 + 来源轴待办收口（来源 [[AppIntent 每日情报 2026-08-17]]）

> 接续本笔记 08-16 创建时的 Session 347 机制链路。本期 wwdc.ai / nonstrict.eu 镜像放出**完整逐字转录**，补齐 Foundation Models 侧的**确定性护栏代码**，并**收口连续第 8 日最高优先待办「四平台意图元数据来源分级」**。

**Foundation Models 侧确定性护栏（Session 347 代码级）**
- **`.onToolCall` 修饰符**：在 LLM 输出工具调用后、**Executor 运行工具前**确定性触发；回调抛错则工具永不执行、控制权立即返回循环——这是注入**执行前**拦截的最佳位置（与 [[XPIA 跨提示注入]] 读路径防护同源）。
- **`.historyTransform` 修饰符**：在脚本呈现给模型推断**之前**改写尾部条目；用于给**不可信工具输出加 spotlighting 分隔符** + **脱敏 PII**（替换为占位符）；⚠️ 转换**仅限当前推断迭代**，下次调用需重新应用；需持久化用 `@SessionProperty`。
- 两者都证明 Apple 的官方缓解范式是 **「对输入零信任（标注/脱敏不可信来源）+ 对动作按风险确定性拦截」**，**不是给实体/意图打「来源可信度」标签**。

**→ 连续第 8 日最高优先待办收口结论（已确认，非假设）**
- 经逐平台核验（Apple Session 347 / Android AppFunctions 元数据 / HarmonyOS insight_intent.json / Windows ODR connector 元数据），**四平台意图 Registry 层均无「数据来源 / 可信度」元数据字段**——来源轴空白从「待查」升级为「**架构性空白（confirmed）**」。
- 含义改写：Apple 用副作用轴（08-16 已解）回答了「动作多危险」，**用零信任输入处理回答了「数据可不可信」**；但 Registry 本身不记录 provenance。最低成本补丁仍是 08-16 提的「意图 Registry 加 `readOrWrite` 声明位」，仍非完整 provenance。完整横向对照见新建 [[四平台意图 Registry 来源轴与权限模型对比 2026]]。
