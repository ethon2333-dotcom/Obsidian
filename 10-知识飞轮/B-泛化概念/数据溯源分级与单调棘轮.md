# 数据溯源分级与单调棘轮

> 新建于 2026-08-04。**攻击面**见 [[Agent Data Injection 数据注入攻击]]；**隔离架构**见 [[Dual View 智能体数据视图隔离]]；本节点讲的是二者之间缺的那一层——**数据本身的来源标注、分级与状态机**。

## 一句话定义

**数据溯源分级（provenance classification）+ 单调棘轮（monotonic ratchet）** 是一套让 Agent 的每一份输入都携带「**从哪来、多敏感、被怎么改过**」的机器可读元数据，并让会话的敏感度**只能升不能降**的机制——它把「这条数据可不可信」从模型的主观判断变成**系统的确定性状态**。

## 为什么重要

- **它是 ADI 的正面答案。** [[Agent Data Injection 数据注入攻击]] 的结论是「Agent 从不怀疑结构化元数据，攻击者伪造元数据即可零指令劫持」。防线不能靠「识别恶意语气」，只能靠「**这条结构从哪来、能不能被第三方写**」——那就必须先有 provenance 字段。
- **它比隔离便宜一个数量级。** [[Dual View 智能体数据视图隔离]] 的带外防御代价约 **15× 调用**，端侧承受不起；棘轮只是「一个会话变量 + 一个有序枚举」，**近乎零推理成本**，是端侧唯一现实可落地的那一半。
- **它已经是法律要求，不只是工程选择。** EU AI Act **Article 10（数据治理）**高风险条款自 **2026-08-02** 起适用，与同日生效的 Article 15 构成一对：**Article 15 管「防不防得住攻击」，Article 10 管「数据从哪来、怎么被处理」**（见 [[Windows Copilot Actions 与 Agent Workspace 2026]]）。
- **它给出了「确认机制」的第二、第三个触发点。** 传统 Confirmation UI 只在「动作前」弹一次；两阶段策略门把检查挪到 **`post_tool`（工具返回后）** 与 **`pre_output`（输出前）**，堵住「工具已经把脏数据吃进上下文才想起来确认」的窗口（见 [[Confirmation UI 安全机制]]）。

## 适用边界

- ⚠️ **当前唯一的成熟公开实现是治理层，不是 OS 层。** 微软 Agent Governance Toolkit 是 microsoft GitHub 组织下的**开源治理工具包 / 参考实现**（Python 命名空间 `agentmesh.governance`），面向企业 Agent 合规；**Windows OS 的 agentic security 文档中不存在任何数据来源分级**（2026-08-04 逐条复核确认）。
- **四大 OS 意图框架截至 2026-08-04 均未采纳**：Apple `.appEntityIdentifier`、Android `AppFunctionMetadata` / `app_metadata`、HarmonyOS A2A 消息与 Skill 元数据、Windows Agent Workspace 工具响应，**都没有来源类型字段，也没有分级**（全部待补）。
- **最大的未解问题是「谁来打标」。** 若 classification 由 AppFunction 的开发者自报，就又回到 ADI 靶面（可伪造）；只有**系统按来源类型强判**（如「来自 UGC 页面的一律 untrusted」）才有安全意义。这是把该机制搬进 OS 时的核心设计题。
- 棘轮是**单调**的，意味着长会话会不可逆地滑向高门槛。端侧长驻 Agent 需要配套的**会话切分策略**，否则用户体验会持续劣化。

## 证据与例子

**来源**：`microsoft.github.io/agent-governance-toolkit/compliance/data-provenance-model`（2026-08-04 抓取）

**① 溯源记录的四段结构**

| 段 | 关键字段 | 作用 |
|---|---|---|
| `source` | `type`（**六类枚举**：`tool_output / api_response / agent_message / user_input / database / file`）、`tool_name`、`source_agent_did`、`source_classification` | 回答「**从哪来**」 |
| `data` | `classification`（**四级**：`public / internal / confidential / restricted`）、`contains_pii`、`pii_types`、`jurisdiction`、`hash`（sha256 内容哈希，做完整性校验） | 回答「**多敏感、有没有被改**」 |
| `transformation` | `type`：`none / aggregation / anonymization / redaction / enrichment` | 回答「**被怎么处理过**」 |
| `purpose` + `retention` | `decision_type`、`policy_decision`、`audit_entry_id`、保留期、`legal_hold` | 回答「**用来干了什么、留多久**」 |

**② 单调棘轮**

```python
SessionAttribute(
    name="data_sensitivity",
    ordering=["public", "internal", "confidential", "restricted"],
    monotonic=True,
)
# 工具返回 confidential 后，会话敏感度升级且本会话内不可复位
```

**③ 两阶段策略门**

| 阶段 | 触发条件示例 | 动作 |
|---|---|---|
| `post_tool` | `tool.output.classification == 'restricted'` | `deny`（禁止转发给其他 Agent） |
| `pre_output` | `response.provenance.contains_pii` | `require_approval`（转人工审核） |

**④ 溯源链**：多 Agent 传递时记录形成父子链（`parent: prov-00x`），链上同时记录 classification 棘轮变化与变换类型。

**⑤ 官方实现状态自述**：溯源模式 ✅ 已定义｜审计集成 ✅ 已发布｜会话棘轮 ✅ 已发布｜多阶段策略 ✅ 已发布｜**溯源链父子追踪 🔜 计划中**｜`ProvenanceTracker` API 🔜 计划中｜自动 PII 检测 🔜 计划中。

**⑥ 端点侧的姊妹机制（2026-08-03，Project Perception 配套）**：Defender for Endpoint 可检查 Windows 本地 Agent 的 **agent loop 本身——用户提示 / 工具调用 / 工具响应**——并在风险动作**执行前阻断**。这是把「工具响应」当作**可检测流量**的第一个端点侧实现，与本节点的「把工具响应当作**可分级数据**」互为表里。

## 可复用启发

1. **给 Registry 加字段的最小提案**：任何意图/工具元数据表，至少加两列——`source.type`（谁写的：平台 / 开发者声明 / 运行时抓取 / 第三方内容）与 `classification`。**没有这两列，就无法回答「这条元数据能被伪造吗」。**
2. **判断一个 Agent 平台的数据安全成熟度，看它有没有「不可降级」的状态。** 只有分级没有棘轮 = 模型可以在下一轮"忘记"刚读过高敏内容；棘轮才是把分级变成**强制约束**的那一步。
3. **确认机制要三点部署，不是一点**：动作前（经典）+ 工具返回后（`post_tool`）+ 输出前（`pre_output`）。
4. **端侧落地的性价比排序**：棘轮（近乎零成本，先上）→ 来源类型枚举（改 Schema，中等）→ 符号化隔离（~15× 调用，仅高危路径）。见 [[Agent 读入路径可信数据边界 SOP]]。
5. **对 OS PM 的一句话结论**：**成熟模型已经存在且开源，四大 OS 只是还没采纳。** 这不是技术空白，是产品优先级问题——可以直接作为竞品分析与内部 PRD 的论据。
