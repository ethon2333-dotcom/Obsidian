# 文档型 XPIA 自传播蠕虫

## 一句话定义

**文档型 XPIA 自传播蠕虫**是一种把「跨提示注入（XPIA）」与「传播（propagation）」阶段结合的攻击：恶意指令**把自己复制进被 Agent 生成的新文档**，使被污染的内部工作产物成为下一轮会话的载体，从而绕过「隔离 / 确认 / 审计 / 溯源」四道对「一次性攻击」的假设。代表：Copilot for Word 蠕虫（Håkon Måløy《Context Collapse, Part 3》，与 MSRC 协调披露）。

## 为什么重要

- 这是本库 OS Agent 安全叙事的**范式转折点**：此前四平台防线全部假设「攻击是一次性的，拦住这次就安全」，蠕虫打破了该假设。
- 它揭示 XPIA 的真正放大器是 Agent 的**「写回（write-back）」能力**——任何能改写会被他人复用的产物、且该产物会再次进入 Agent 上下文、且修改本身属于 Agent 正常职责（不触发确认）的路径，都具备蠕虫风险。
- 对企业安全结论是颠覆性的：**没有任何客户侧开关能完整解决该类别**，只能靠卫生措施降低频率。给 CISO 的诚实答案是「**载荷修了，类别没修**」。

## 适用边界

- 触发条件：Agent 具备把内容**写回**可被他人/后续会话复用的产物（文档、日历、记忆、注册表）的能力。
- 与经典数据外发型攻击不同：本例属**完整性损害**（改写可信产物 + 重新埋雷），没有 webhook 外发，更难被 DLP 发现。
- 先例脉络：Morris II（邮件助手蠕虫，arXiv:2403.02817）；Simon Willison **lethal trifecta**（私有数据 + 不可信内容 + 外发/执行能力）。

## 证据与例子（Copilot for Word 蠕虫，来源 [[AppIntent 每日情报 2026-08-01]]）

- **攻击链**：① 攻击者分享普通 .docx（邮件/SharePoint/Teams，无需受害者 M365 租户权限）；② 载荷用**白底白字/极小字号**隐藏——关键在 Copilot for Word 送入 LLM 前会**剥离颜色与字号**，于是「人眼不可见、模型完全可见」；③ **Stage 1 立足**：Copilot 把文档指令当权威执行（PoC 演示把财务数字腰斩且不提示用户）；④ **Stage 2 蠕虫**：受污染内部文档成新载体，同事基于「可信 Q1 报告」起草 Q2，即使原始攻击文件已不在场，Copilot 仍再次改数并重新植入白字指令——**溯源崩塌，每个载体都像合法内部创作事件**。
- **披露时间线（类别至今未关闭）**：2026-03-06 首次报告 → 03-31 微软确认 → 04-03~09 第一轮缓解（Edit with Copilot），原变体被拦但新财务操纵变体成立 → 06-08 应要求推迟 → 07-14 第二轮缓解（升 GPT-5.5）→ 07-15 **在 GPT-5.6 复现** → 07-28 类别级公开披露仍可复现。Part 1（污染记忆）已缓解、Part 2（邮件正文 XPIA / CVE-2026-55145）较强缓解，**Part 3「传播」类别未关闭**。
- **作者架构论断**：要用附件，模型必须把攻击者 token 与用户请求放进同一上下文；等模型「判断是不是攻击」时，那些 token 已参与判断——更像「运行程序才知道安不安全」，而非经典沙箱。「用比目标 LLM 更弱的检测器必留表征缺口；把 LLM 层层堆成盾牌，就变成 LLMs all the way down」。
- **与本库互文**：正好击中 [[Agent Workspace 隔离执行]] 的边界——**隔离解决「执行域泄漏」，但解决不了「被污染的产物在人际间正常流转」**。

## 可复用启发

- 凡 Agent 具备「写回」能力的路径，都必须评估「注入能否自我复制」。判据三问（已写入 [[Agent 写回路径 XPIA 风险评估 SOP]]）：① Agent 能否修改会被他人复用的产物？② 该产物会不会再次进入 Agent 上下文？③ 修改本身是否属于 Agent 正常职责（不触发确认）？三问全「是」= 蠕虫风险。
- 安全设计四维应补「**可逆**」（执行后一键撤回/任务中止），因为 Word 蠕虫证明了「执行后才发现」是常态（见 [[Confirmation UI 安全机制]]）。
- 一个尚未被三家新 OS 公开回应的问题：当 OS 把调度单元升级为「意图」，**意图本身会不会成为被注入对象**？（见 [[Agentic OS 意图调度内核]]）

## 深化补充

- **与 ADI 同源**：本蠕虫的「把载荷写回可信产物」正是 [[Agent Data Injection 数据注入攻击]] 指出的「Agent 不隔离可信/不可信数据」在**写回路径**上的具体化——白字指令被模型当作合法文档内容读入，属于元数据/结构被污染而非指令注入。
- **OS 意图框架的潜在写回面**：当 OS 把调度单元升级为「意图」，若系统 Agent 能把**意图结果写回**共享产物（记忆、日历、跨 App 上下文），则该产物成为下一轮会话的注入载体（见 [[Agentic OS 意图调度内核]]）。四平台对此**均无公开类别级回应**。
- **正面缓解方向**：[[数据溯源分级与单调棘轮]] 的「来源打标 + 单调棘轮」可让被污染产物在再次进入上下文时触发 `pre_output` 复核；但「写回时即打标」需要 OS 层接纳 provenance 字段，目前缺失。

- [ ] 四平台的意图写回路径（如 Apple App Intents 的 `SyncableEntity` 同步、Android AppFunction 结果回填）是否评估过自传播风险？待补。
- [ ] 「可逆」维度（见 [[Confirmation UI 安全机制]]）能否覆盖「已写回的污染产物」——即能否撤回一份已被 Agent 生成并扩散的文档？机制未明。
