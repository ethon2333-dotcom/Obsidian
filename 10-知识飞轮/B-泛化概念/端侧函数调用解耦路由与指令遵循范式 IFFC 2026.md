# 端侧函数调用解耦路由与指令遵循范式 IFFC（2026）

> 全新主题，库内此前无对应笔记。聚焦 2026-08 新论文提出的「把工具选择从主 LLM 解耦 + 用指令遵循上下文替代工具调用上下文」的端侧 Planner 范式。

## 一句话定义

**IFFC（Instruction-Followed Function Calling，指令遵循式函数调用）** 是一种端侧函数调用的范式重构：用一个独立的 **SRM（Small Reasoning Model，0.5B–15B）** 承担「意图→工具选择→参数抽取」的路由职责，与主 LLM 的对话/合成上下文**完全隔离**；并主张小模型在**标准指令遵循（Instruction-Following）上下文**里做工具选择，比在**专用工具调用（Tool-Calling）上下文**里准确率更高。

## 为什么重要

- **上下文隔离带来可量化收益**：主 LLM 的上下文只保留用户交互与最终合成，SRM 的上下文独立且不被最终长回复污染——多轮下 SRM 输入不会随回复增长而膨胀（token 优化）。
- **小模型可行性上修**：论文用 Qwen-3 0.6B/1.7B/4B/8B 验证「指令遵循上下文」普遍优于「工具调用上下文」，把端侧主路由的可行规模下限向下推。
- **与库内既有结论同频**：呼应本库「<1B 模型只在窄域+微调+严格约束下才堪用」的纪律（见 [[Function Calling 端侧工具调用]] 07-31 节），并给出一种**架构级**而非**纯模型级**的解法——解耦本身即护栏。

## 适用边界

- SRM 负责「选工具 + 填槽」，**复杂推理/多步规划仍交主 LLM**，不是用一个 0.6B 取代整个 Agent。
- 解耦路由对**窄域固定 Schema**（单应用 App Intents / AppFunctions）收益最大；开放域仍需主模型。
- 论文数字为 **BFCL V3**（arXiv 2608.22472），**非 v4 口径**——与库内 08-04 起建立的「每分标版本」纪律一致，引用须标 v3。

## 证据与例子（arXiv 2608.22472，2026-08）

**① 两阶段范式**
- 解耦工具选择逻辑（SRM）与主生成模型：SRM 评测用户意图决定是否需要外部工具/上下文。
- 把 function-calling 重构为**标准指令遵循交互**，而非专用 `<function_call>` 标签 + 刚性 JSON schema 上下文。

## 可复用启发

- **端侧 Planner 选型要分两层看**：一个「对话/合成主模型」+ 一个「解耦的工具路由 SRM」。路由 SRM 越小越便宜越可控，且可独立量化、独立红队。
- **小模型训练/提示的默认上下文应是「指令遵循」而非「工具调用」**：刚性 tool-call schema 对 <3B 模型反而制造格式错误与幻觉（见 [[端侧 Router 置信度门控与工具可达性收缩 2026]] 的「置信度门控」互补——解耦解决路由，门控解决误触发）。
- **延续库内口径纪律**：IFFC 论文用 BFCL V3，与库内 v4（Agentic 40% + Multi-Turn 30%，见 [[Function Calling 端侧工具调用]] 08-04 节）不可比；任何引用须双标版本。
