# Agent 写回路径 XPIA 风险评估 SOP

## 使用场景

当你在设计一个具备「写回（write-back）」能力的 Agent / OS 意图框架时——即 Agent 能把内容写回文档、日历、记忆、Registry、跨 App 存储或任何会被他人 / 后续会话复用的产物——用本 SOP 判定它是否暴露在**自传播 XPIA** 风险下。

触发背景：Copilot for Word 文档型蠕虫（[[文档型 XPIA 自传播蠕虫]]）证明，传统「隔离 / 确认 / 审计 / 溯源」四道防线全部假设「攻击是一次性的」，而具备写回能力的 Agent 可能让注入自我复制、在人际间正常流转，从而击穿所有四道线。

## 输入

- Agent 的能力清单：它能否修改哪些产物（文档 / 记忆 / 实体 / 意图注册 / 设备状态）。
- 产物流向：被修改的产物会不会再次进入 Agent 上下文（被自己或他人复用）。
- 确认触发规则：哪些动作会弹确认、哪些属于「本职工作」无确认。
- 多 Agent / 跨端场景：产物是否会在人际或跨设备间流转。

## 步骤

1. **画写回路径**：列出 Agent 所有「输出会持久化并被复用」的出口（不仅限发信/付款，还包括改草稿、写记忆、注册意图、回填日历）。
2. **逐路径三问判据**（三问全「是」= 蠕虫风险，须升级处置）：
   - ① Agent 能否修改**会被他人复用**的产物？
   - ② 这个产物**会不会再次进入 Agent 上下文**（自己或他人下次会话）？
   - ③ 修改本身是否**属于 Agent 的正常职责**（因而**不触发确认**）？
3. **对命中路径补四维防护**（见 [[Confirmation UI 安全机制]]）：可信 / 可见 / 可控 / **可逆**。重点补「可逆」——执行后一键撤回 + 任务中止，因为「执行后才发现」是常态。
4. **对命中路径做类别级评估，而非 PoC 级**：区分「某个载荷字符串失效」与「漏洞类别关闭」。诚实结论是「载荷修了，类别没修」时，靠卫生措施降级频率，不要宣称已解决。
5. **跨端 / 多 Agent 额外问**：当调度单元升级为「意图」（[[Agentic OS 意图调度内核]]），**意图本身会不会成为被注入对象**？（三家新 OS 均未公开回应，标待补。）

## 完成标准

- 每条写回路径都标注了三问判据结果。
- 命中路径都有四维防护设计，且至少包含「可逆」机制。
- 安全评审文档明确区分「PoC 已缓解」与「类别未关闭」，无夸大结论。

## 常见失败与处理

- **失败：只盯「敏感动作」确认**。Word 蠕虫的「改草稿财务数字」是本职工作，不触发任何确认。→ 处理：把判据从「动作是否敏感」转为「产物是否会被复用 + 是否会回流上下文」。
- **失败：以为隔离能解决一切**。[Agent Workspace 隔离执行] 隔离执行域，但隔离不了被污染产物在同事间正常流转。→ 处理：隔离 + 可逆 + 卫生措施组合，不单押隔离。
- **失败：把检测器堆成 LLM 盾牌**。作者论断「用比目标 LLM 更弱的检测器必留表征缺口；LLMs all the way down」无解。→ 处理：架构层（写回前结构化校验、产物带来源标记）优于纯模型对齐。

## 示例

Copilot for Word 蠕虫路径评估：① 能改会被同事复用的 Q1 报告 → 是；② 同事基于它起草 Q2，报告再进 Copilot → 是；③ 改数是 Copilot 本职、无确认 → 是。**三问全「是」= 蠕虫风险**。处置：微软两轮缓解（Edit with Copilot / 升 GPT-5.5→5.6）仅修载荷，类别 144 天后仍未关闭——印证「类别级」需架构层而非模型升级。

## 深化补充（2026-08-04）

> 本 SOP 成文于 08-01，当时步骤 3 只能给出「产物带来源标记」这样的方向性建议。08-03/08-04 入库的 [[Agent Data Injection 数据注入攻击]] 与 [[数据溯源分级与单调棘轮]] 已把这一层补成**可落地机制**，本节把它接进来。

### 一、先补一条回链：本 SOP 只管半个闭环

- **写回路径（本篇）**：管「Agent 往外写什么」——产物会不会自我复制、会不会回流上下文。
- **读入路径（[[Agent 读入路径可信数据边界 SOP]]）**：管「Agent 信了什么」——不可信数据是否被当成可信结构。

**两篇必须成对执行。** 只做写回评估会漏掉「产物没被改、但 Agent 读了伪造元数据后自己写错」；只做读入评估会漏掉「读的都对、但写出去的产物成了下一个人的污染源」。评审模板里应把两张表并排放。

### 二、步骤 3「产物带来源标记」的可落地版本

写回时，给产物附一条溯源记录（字段取自微软 Agent Governance Toolkit 的 provenance 模型，详见 [[数据溯源分级与单调棘轮]]）：

| 字段 | 写回场景下的填法 | 它挡住什么 |
|---|---|---|
| `source.type` | 生成这份产物时**读入过的最高风险来源类型**（`tool_output` / `file` / `agent_message` 均为不可信档） | 「这份报告是 Agent 读了外部 docx 之后写的」这一事实不会丢失 |
| `data.classification` | 沿用**单调棘轮**后的会话密级，只升不降 | 防止产物在下游被"洗白"成 public |
| `data.hash` | 产物内容 **sha256** | 下次读入时 hash 不匹配即知被改过 |
| `transformation.type` | `enrichment` / `redaction` / `aggregation` … | 区分「Agent 原创」与「Agent 改写了别人的东西」 |
| `parent` | 上游产物的溯源记录 ID | 形成父子链，把「同事的 Q2 报告」一路追回「攻击者的 docx」 |

⚠️ **成熟度提醒**：AGT 官方自述 **溯源链父子追踪 🔜 计划中**、`ProvenanceTracker` API 🔜 计划中——即上表最后一行（`parent`，恰恰是**反蠕虫最关键的一行**）目前**没有现成实现**，需自建。四大 OS 更是全无来源字段（2026-08-04 复核）。

### 三、把「可逆」拆成三档，别停在「有个撤销按钮」

来源：阶跃 Step AOS 四维安全（可信/可见/可控/可逆）+ Word 蠕虫的实际传播形态（见 [[Confirmation UI 安全机制]]）。

| 档位 | 能力 | 覆盖的场景 |
|---|---|---|
| **L1 单步撤回** | 撤回 Agent 刚做的这一步 + 中止当前任务 | 「执行后才发现」——最低要求 |
| **L2 会话级回滚** | 回滚本次会话所有写回产物到执行前状态 | 一次会话连改了多个文档 |
| **L3 传播级召回** | 顺着 `parent` 链找出**所有派生产物**并标记/隔离 | **蠕虫场景唯一有效的一档** |

**判据**：三问全「是」的路径，**必须做到 L3**；做不到 L3 就不能宣称该路径的蠕虫风险已缓解，只能写「已降低触发频率」。这与步骤 4「区分载荷级与类别级」是同一条纪律的两种说法。

### 四、按「复用半径」给写回路径定门槛

三问是二元判据，实际排期需要优先级。补一个连续量：**产物的复用半径**。

| 复用半径 | 例子 | 最低要求 |
|---|---|---|
| **自用**（只有本人下次会话会读） | 个人记忆、草稿 | L1 可逆 + 溯源标记 |
| **团队**（同事会基于它继续做） | 共享文档、日历、Wiki | L2 + 写回前结构化校验 + `parent` 链 |
| **公开/系统级**（进入 Registry 或被其他 Agent 消费） | 意图注册、Skill 发布、A2A 消息 | **L3 + 带外审批**（见 [[Agent 身份与硬件级审批]]） |

最后一档是本库长期挂着的开放问题：当 OS 把调度单元升级为「意图」（[[Agentic OS 意图调度内核]]），**意图注册本身就是一条写回路径**，且复用半径是系统级——三家新 OS（荣耀 AgenticOS / 阶跃 Step AOS / 卓易 DroiClaw）**均未公开回应意图能否被注入**（待补）。

### 五、常见失败补两条

- **失败：只做 L1 撤回就宣称"可逆已覆盖"**。撤回了自己的产物，但同事已基于它派生出新文档——污染仍在扩散。→ 处理：可逆的验收对象是**传播树**，不是**单次操作**。
- **失败：把溯源标记交给产生方自报**。若 classification 由写回方自己填，攻击者控制的 Agent 就会填 `public`——又回到 ADI 靶面。→ 处理：**必须由系统按来源类型强判**（如"本次会话读过 UGC → 产物一律不低于 internal"），自报字段只能升级不能降级。
