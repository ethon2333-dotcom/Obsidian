# Agent 读入路径可信数据边界 SOP

## 使用场景

当你在设计一个**会读入外部数据**的 Agent / OS 意图框架时——即 Agent 把网页、文档、邮件、工具返回、文件、跨 App 上下文等内容纳入自身推理上下文——用本 SOP 判定它是否暴露在 **ADI（Agent Data Injection，智能体数据注入）** 与 **Stored IPI（存储型间接提示注入）** 风险下。

触发背景：ADI（[[Agent Data Injection 数据注入攻击]]，arXiv 2607.05120）证明，攻击者**不需要注入指令**，只要伪造 Agent 视为可信的**结构化元数据**（元素 ID、数据来源、发件人、工具调用/响应格式），Agent 就会自己推出错误结论；同环境对照经典指令注入 0–0.7%，ADI 最高 **100%**。姊妹研究 DualView（[[Dual View 智能体数据视图隔离]]，arXiv 2607.03821）证明，即便传统隔离对即时注入有效，**存储型注入（数据落盘还原后被重读）仍有 53.3%** 失守。

本 SOP 与 [[Agent 写回路径 XPIA 风险评估 SOP]]（08-01）构成**双向闭环**：写回路径管「Agent 往外写什么（会不会自我复制 / 回流上下文）」，读入路径管「Agent 信了什么（不可信数据是否被当成可信结构）」。

## 输入

- Agent 的读入来源清单：网页 / 文档 / 邮件 / 工具返回 / 文件 / 跨 App 上下文 / 之前的会话记忆。
- 每条来源是否携带**结构化元数据**（标识符、来源标记、发件人字段、工具/响应格式）。
- 该数据会不会在**落盘 / 跨会话 / 跨 Agent** 后被再次读入（生命周期判定）。
- 当前是否已有隔离机制，以及隔离对象（进程？账号？还是数据形态？）。

## 步骤

1. **分类信任边界**：对每条读入来源标注「可信 / 不可信 / 条件可信」。规则：`api.github.com/*` 等白名单源可信；UGC 页面、`imports/*.csv`、`agent:public-chat` 等默认**不可信**（参考 DualView 的 data-trust 策略）。
2. **核验元数据来源（2026-08-04 升级为可执行分级判据）**：凡 Agent 依赖其做决策的结构化字段（元素 ID、`appEntityIdentifier`、工具响应格式、`app_metadata`），**检查它是否来自可信源、是否有来源绑定 / 签名**。⚠️ ADI 的靶心正是「Agent 从不怀疑的结构」。

   原先「无法证明来源就一律按不可信处理」过于粗糙，落地时要么全拦（可用性崩）要么形同虚设。改用微软 Agent Governance Toolkit 的三件套（详见 [[数据溯源分级与单调棘轮]]）：

   **2a. 六类来源打标**——每条读入数据在**进入上下文的那一刻**标注来源类型，缺一不可：

   | 来源类型 | 典型对应 | 默认信任 |
   |---|---|---|
   | `user_input` | 用户当面输入 | 可信（但仍可能被社工） |
   | `database` | 自有结构化存储 | 可信 |
   | `api_response` | 第三方 API 返回 | **条件可信**（看是否白名单 + 签名） |
   | `tool_output` | 工具/浏览器/文件读取返回 | **不可信**（ADI 三类攻击的主载荷入口） |
   | `agent_message` | 其他 Agent 传来的消息 | **不可信**（A2A 场景重点） |
   | `file` | 磁盘文件内容 | **不可信**（Stored IPI 入口） |

   **2b. 四级密级 + 单调棘轮**——`public → internal → confidential → restricted`，**只升不降**。规则：任一环节读入了更高密级数据，整条上下文的密级立即抬升且**下游不得降级**。这挡的正是 ADI 的核心手法「伪造结构让 Agent 自己推出『这份数据其实没那么敏感/已被验证』」。

   **2c. 两阶段闸口**——`post_tool`（工具一返回就打标，不等到推理后）与 `pre_output`（输出/执行前按当前密级复核）。**打标必须发生在模型看到内容之前**，否则打标本身就能被注入内容影响。

   ✅ **判据升级后的完成线**：不再是「能否证明来源」这个二元问题，而是三问——① 这条数据的来源类型枚举值是什么？② 它把当前上下文的密级抬到了哪一档？③ 该密级下这个动作是否还被允许执行？

   ⚠️ **层级提醒**：这套模型目前的成熟实现在**应用/治理层**（AGT 开源工具包），四大 OS **均未内建**（已复核 Windows 官方 agentic security 文档确认无来源分级）。做 OS 侧设计时这是**你要自己补的一层**，不能假设平台提供。
3. **符号化隔离不可信数据**：对不可信内容做**符号化/脱敏**（如 `$web_01.content`），Agent 只能引用、不能直读原文；对必须处理原文的工具调用，在调用前**去符号化**、返回后**重新符号化**（参考 [[Dual View 智能体数据视图隔离]] 的视图路由）。
4. **生命周期覆盖**：确认隔离**跨落盘与跨会话有效**——数据写文件后重读仍是符号，不出现「落盘还原 → 符号关系消失 → 高权限 LLM 直读原文」的 Stored IPI 缺口。
5. **高风险动作走带外门**：凡读入数据可能影响「破坏性 / 不可逆 / 涉钱涉隐私」动作，**不靠 Agent 自身确认**（被污染后确认文案即被操纵），改由**带外**组件（授权服务器 / 硬件级审批，见 [[Agent 身份与硬件级审批]]）完成。确认机制按三档判据自查（Agent 自组织 / 系统据元数据渲染 / 带外授权）。
6. **按风险分层**：只读 / 可逆动作走快路径、不加门；破坏性 / 不可逆 / 涉钱隐私走带外门。端侧尤其要算清「~15× 调用」的安全税不可承受——**分层是现实唯一路径**。

## 完成标准

- 每条读入来源都标注了信任边界（步骤 1）。
- 所有「决策依赖的结构化元数据」都有 **①来源类型枚举值 ②当前上下文密级 ③该密级下动作是否放行** 三项结论；打标发生在模型读到内容之前，且密级只升不降（步骤 2）。
- 不可信数据在 Agent 上下文中恒为符号化形态，且跨落盘/跨会话不失效（步骤 3–4）。
- 高风险动作有带外授权/审批机制，不依赖 Agent 自组织确认（步骤 5）。
- 安全评审明确区分「载荷修了」与「类别未关闭」，无夸大结论。

## 常见失败与处理

- **失败：只过滤「指令语气」**。[XPIA 跨提示注入] 的旧思路找祈使句、过滤命令式。→ 处理：ADI 证明攻击可零指令，必须按「结构/元数据是否可信」而非「语气是否像命令」判别。
- **失败：以为隔离机制一次配置永久有效**。传统 Dual LLM 即时注入 ASR≈0，但 Stored IPI 仍 53.3%——隔离机制被绕过的是生命周期。→ 处理：把「跨落盘 / 跨会话」纳入隔离有效性判定，而非只看即时上下文。
- **失败：把确认当授权**。被 ADI 污染的 Agent 呈现给用户的是攻击者写好的确认文案。→ 处理：高危动作走带外（[[Confirmation UI 安全机制]] 第四维），本地 UI 确认不足以构成授权。

## 示例

某 Web Agent 读取含 UGC 的页面后点击按钮：① 页面元素 ID 属不可信 UGC → 按步骤 2 核验，来源无法证明；② 若 Agent 直接信任该 ID 去点击，即落入 ADI 场景一（伪造元素标识符），实测 Claude in Chrome / Antigravity / Nanobrowser 中招；③ 处置：对页面 DOM 做符号化（元素以 `$dom_xx` 引用），工具调用前才去符号化、返回后重新符号化；点击等不可逆动作再走带外确认。**关键判据：Agent 在推理时从未「看见」可信的原文结构，因此伪造的 ID 无法驱动其结论。**

## 深化补充：落地顺序（步骤 1–6 不是同时上的）

六个步骤全量落地成本很高，端侧尤其扛不住。按**性价比**排序，先上前两项就能覆盖大部分风险：

1. **单调棘轮**（步骤 2b）——一个会话变量 + 一个有序枚举，**近乎零推理成本**，先上。
2. **六类来源枚举打标**（步骤 2a）——改 Schema / 加 hook，中等成本，且是后续一切的前提。
3. **两阶段闸口**（步骤 2c）——`post_tool` / `pre_output`，成本取决于策略条数。
4. **带外授权**（步骤 5）——只对破坏性/不可逆/涉钱隐私动作开。
5. **符号化隔离**（步骤 3–4）——约 **15× 调用**开销，**仅高危路径**，端侧默认不开。

**验收口径**：只做了 1 而没做 2，等于有状态机没有输入；只做了 2 而没做 1，等于有标签但模型下一轮就能"忘记"——**这两项必须捆绑上线**。

## 待解问题

- [ ] **打标器本身会不会成为新靶面？** 若 `source.type` 由 AppFunction 开发者自报即可伪造；若由系统强判，则规则表成为攻击目标。系统强判的规则应该放在哪一层——内核、Framework、还是 Registry？
- [ ] **单调棘轮与长驻端侧 Agent 的体验冲突**：棘轮只升不降，长会话会不可逆滑向 `restricted`，用户体验持续劣化。会话切分策略的触发条件该怎么定（按时长？按任务边界？按密级跨档？），切分会不会反过来成为攻击者"洗白密级"的手段？
- [ ] **【连续挂起】四大 OS 是否有任何一家在跟进来源分级？** 已复核 Windows 官方 agentic security 文档确认无；Apple `.appEntityIdentifier` 是否有来源绑定/签名仍未取到官方说明。下轮改查各平台**安全白皮书 PDF** 而非开发者文档。
