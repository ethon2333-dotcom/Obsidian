# 知识库搭建 SOP

## 使用场景

把零散信息转换为可复用知识，并从知识反复产出内容。

## 每次收集

1. 在 `A-原始资料` 新建笔记，使用 [[_模板/原始资料]]。
2. 记录来源、原文重点和你真正想解决的问题。
3. 不在 A 中过度整理；无法判断价值的资料也先保留。

## 每周蒸馏

1. 浏览 A 中本周新增资料。
2. 每个可迁移结论在 B 新建一篇独立概念笔记，使用 [[_模板/概念蒸馏]]。
3. 当一个概念已能稳定指导行动时，在 C 写成步骤化方法，使用 [[_模板/方法SOP]]。
4. 用链接保留 A、B、C 之间的来源关系。

## 每次输出

1. 从 C 选择适用的方法，而不是从空白页开始。
2. 将草稿或成品放入 D，使用 [[_模板/输出复盘]]。
3. 发布或使用后记录反馈、失败原因和新问题。
4. 将新问题或素材回写到 A，形成下一轮输入。

## 完成标准

- A 中每个待处理条目都带有来源与问题。
- B 的概念可脱离原素材单独理解。
- C 的方法可由未来的自己按步骤执行。
- D 的输出带有实际反馈或明确的待验证假设。

## 深化补充

> 本节把上面的原则版 SOP 补成**可执行版**。素材来自本库 2026-07-30 ~ 08-04 连续 6 天真实跑飞轮的经验（见 [[知识飞轮看板]] 各期「本次新增」与待办），不是理论推演。

### 一、归属判定树：一条信息进哪一层

按顺序问，第一个「是」就落哪层，**不要同一内容进两层**：

1. 它有**外部来源和时间戳**，且你还没想清楚它意味着什么 → **A**。
2. 它是一句**脱离原素材也成立的可迁移结论** → **B**（一篇只放一个概念）。
3. 它能变成**下次遇到同类问题时照着做的步骤** → **C**。
4. 它是**给别人看的成品或阶段性判断** → **D**。

边界情形：
- **同一天的多条情报** → 全进 A 的一篇日报，**不要拆成多篇 A**；蒸馏时才在 B 分裂成多个概念节点。
- **既有 B 已覆盖的新进展** → 不新建节点，用「`## YYYY-MM-DD 增补`」追加到既有 B（本库 08-02 当天 5 条全部走此路径，未新建任何节点）。
- **判断不了的** → 留在 A，不要为了整洁强行升层。

### 二、每层的合格线与不合格症状

| 层 | 合格判据（可自查） | 不合格的典型症状 |
|---|---|---|
| **A** | 有一手来源链接/编号 + 真实日期 + 「我想解决什么」 | 只有摘要没有链接；日期用的是"抓取日"而非"事件发生日" |
| **B** | 能回答「一句话定义 / 为什么重要 / **适用边界** / 证据 / 可复用启发」五问 | 只有定义和证据，缺**适用边界**——这是最常漏的一栏，也是最值钱的一栏 |
| **C** | 含触发条件、步骤、**完成标准**、常见失败、示例 | 步骤写成了原则（「要注意安全」），未来的自己无法照做 |
| **D** | 有明确读者、有可执行结论、有**回流待办** | 只是把 B 的内容重排一遍，没有新判断 |

**一个反向自查**：如果 C 里的某条步骤，你无法说出「不这么做会踩什么坑」，那它多半还停留在 B 层，不该写进 C。

### 三、增量落库纪律（连续跑飞轮时最容易崩的地方）

1. **追加，不覆盖。** 既有笔记用「`## YYYY-MM-DD 增补（来源 [[...]]）`」小节追加，保留旧结论与旧口径，让「认知怎么变的」本身可追溯。本库 08-04 修订 [[Agent 读入路径可信数据边界 SOP]] 时保留了 08-03 的原判据并注明升级原因，就是这条。
2. **双链去重先于写作。** 动笔前先搜库内是否已有同名概念；有就追加，没有才新建。每期落库结束在看板记「净新增 N / 既有增补 M」。
3. **显式记录「已复核·无净新增」。** 检索了但没结果的源要写下来，否则下一轮会重复检索同一批空源（本库 08-03 晚、08-04 两期都用了这一招）。
4. **窗口太窄就放宽，别硬凑。** 本库自动化最初用 24h 窗口，连续两天硬命中只有 1 条，被迫「补漏」注水；08-02 起改 **7 日滚动窗口 + 首次入库存量去重**，质量立刻回升。**周期性输出的窗口长度应由真实信息密度决定，不是由排期决定。**

### 四、事实口径纪律（本库靠它避免过至少三次误判）

写进 B/C/D 的任何外部数字，落笔前过三道：

1. **来源三问**：官方榜单还是自建同名基准？微调还是零样本？全量还是子集？
   - 真实教训：`prism-coder` 宣称「BFCL 100%」，实为自建 6-tool 基准；`FunctionGemma 46%→90%` 是早期简报口径，官方实为 **58%→85%**——本库两次因此校准。
2. **版本号必须跟着数字走**。同名基准换版本＝换了考试科目：BFCL **v3** 分数与 **v4** 分数不可同栏比较（详见下方 [[系统级 Intent 路由评估 SOP]] 的三基准表）。
3. **拿不准就写「待补 / 待核实」，不写约等于**。本库所有待补项集中挂在 [[知识飞轮看板]] 的期末待办里滚动，解决一条划掉一条——**待办清单本身就是 D→A 的回流通道**，这比"想起来再补"可靠得多。

### 五、把回流做实：D 的产物必须有两个出口

一篇 D 写完，除了发布，还要产生：
- **出口一（→A）**：本次没查清的问题，逐条写进看板待办，下一轮当作检索输入。
- **出口二（→C）**：本次输出中反复用到的判断动作，沉淀成 SOP 步骤。本库 [[端侧执行通道选型 SOP]]、[[Agent 写回路径 XPIA 风险评估 SOP]]、[[Agent 读入路径可信数据边界 SOP]] 三篇都是这样从日报里长出来的。

没有这两个出口的 D，飞轮就停在 D，退化成"写完就完"的内容生产。
