# 端侧执行通道选型 SOP

> 与 [[系统级 Intent 路由评估 SOP]] 分工：那篇解决「**用哪个模型做路由**」，本篇解决「**路由完之后走哪条通道去执行**」。二者串联即为 OS Agent 的完整链路。

## 使用场景

- 要为系统级助手 / Agent 手机 / 桌面 Agent 决定某项能力（如「点一杯咖啡」「查公积金」「发消息」）的执行方式。
- 已有 GUI Agent 在跑，想评估是否该迁移到官方 Intent / MCP 通道（如豆包手机二代的路线切换）。
- 要给管理层解释「为什么某些 App 我们接不进来」以及代价。

## 输入

1. **能力清单**：用户最常让助手做的 Top-N 任务。
2. **每项任务的属性**：是否写操作、是否涉及支付/资金、是否可逆、失败代价。
3. **目标 App 的通道现状**：是否已提供 App Intents / AppFunctions / Skill / MCP 连接器；是否有商务合作可能。
4. **平台约束**：目标 OS（见 [[Intent Schema Protocol 意图模式规范]]）、可用权限、是否有 GUI 兜底框架。

## 步骤

1. **给每项能力打三个标签**：`写/读`、`资金相关 是/否`、`失效可容忍 是/否`。
2. **查通道可用性**：
   - Apple → 是否有对应系统 Schema `@AppIntent(schema:)`；
   - Android → `adb shell cmd app_function list-app-functions` 是否列出目标函数；
   - HarmonyOS → 是否有 Skill / 意图注册，或可否用 API/MCP 打包为 Skill；
   - Windows → 目标连接器是否注册在 ODR。
3. **按下表定通道**（硬规则，不允许为了上线速度绕过）：

   | 能力属性 | 通道 | 理由 |
   |---|---|---|
   | 资金相关（支付、转账、下单） | **① 官方 Intent/Function，且确认落在被调用 App 原生页面** | 可审计可追责；GUI 必被风控 |
   | 写操作、不可逆（发消息、删除、改密） | **① 官方 Intent/Function** | 结构化参数可校验，避免误操作 |
   | 跨生态服务编排（第三方 SaaS/云服务） | **② MCP 连接器** | 跨平台且可注册进 Registry |
   | 只读、低风险、长尾未适配 | **③ GUI 兜底** | 换覆盖面与上线速度 |
   | 无官方通道 + 写操作 | **暂不上线**，转商务谈判 | 别用 GUI 硬闯 |

4. **为 ③ 设退出条件**：记录每个 GUI 任务的调用量与失败率，作为「优先游说哪些 App 开放官方通道」的排序依据。
5. **验证确认层**：对所有 ①②，确认高危动作有系统级 Confirmation UI；能用系统选择器（如 Android 17 `ACTION_PICK_CONTACTS`、系统渲染位置按钮）替代长期权限的，一律替代（见 [[Confirmation UI 安全机制]]）。
6. **上线后度量**：三通道各自的**成功率、失效率（UI 改版导致）、被风控拦截次数、云端逃逸率**。

## 完成标准

- 每项能力都有明确通道归属，且**无资金/不可逆能力落在 ③ GUI**。
- GUI 任务有台账与退出条件，不是无限期方案。
- 高危动作 100% 覆盖系统级确认，且确认发生在被调用方原生界面。
- 度量指标已接入看板（至少：成功率、风控拦截数、云端逃逸率）。

## 常见失败与处理

| 失败模式 | 表现 | 处理 |
|---|---|---|
| 用 GUI 做支付 | 阶段性可用，规模化后账号被风控封禁 | 立即下线，转 ①；参考豆包手机一代→二代切换 |
| 把自建基准当官方基准 | 选型时高估模型能力 | 引用前三问：官方/自建、微调/零样本、全量/子集（见 [[Function Calling 端侧工具调用]]） |
| 超级 App 拒绝接入 | 关键场景空白（如微信「尚未接入」） | 明确标注能力边界并对用户可见，不要用 GUI 偷跑 |
| 只测能力不测准入 | Demo 惊艳、量产失败 | 评测须含「风控拦截率」，不只 OSWorld 式能力分（见 [[OSWorld 计算机操作基准]]） |
| 权限长期化 | Agent 持有 `READ_CONTACTS` 等长期权限 | 改用系统一次性选择器 |

## 示例

**任务：「帮我点一杯冰美式」**
- 标签：写操作 / 资金相关 / 不可逆 → 必须走 ①。
- HarmonyOS：拉起瑞幸元服务 + Skill 完成选品下单，支付停在支付确认页 → 合规。
- Android：若瑞幸已声明 AppFunction 则直连；未声明则**不用 GUI 兜底下单**，退化为「打开 App 并预填」。

**任务：「去淘宝领金币」**
- 标签：写操作但可逆 / 非资金 / 失效可容忍 → 可走 ③ GUI 兜底（小艺现状），并记入台账等待官方通道。

**任务：「支付宝查公积金」**
- 标签：只读 / 非资金 → ③ 可接受；若支付宝开放 AHA 接口则升级为 ②。

## 深化补充（2026-08-04）：通道选完还差一层「授权凭证」

> 本 SOP 成文于 07-31，那张三通道表回答的是「**怎么调**」。08-03 入库的 [[意图支付授权协议 APOP]] 指出四大 OS 的意图框架**全部停在执行层**，都不回答「**这次代理行为的授权凭什么算数**」。本节补这一层。

### 一、区分「能力授权」与「执行授权」

| | 能力授权 | 执行授权 |
|---|---|---|
| 授的是 | 这个 Agent **可以调**支付类 Function | 这个 Agent 可以**为这件事**花这么多钱 |
| 现有载体 | OS 权限（`EXECUTE_APP_FUNCTIONS` 等）、Registry 注册 | 目前只有一次性确认弹窗 |
| 缺陷 | 粒度过粗，一次授权长期有效 | 弹窗只产生**事件**，不产生**可核验凭证** |

**两层合并会二选一地出错**：要么过度授权（授了能力就等于授了每次执行），要么每次都打断用户。步骤 3 定完通道后，**必须再问一句「这条通道上的高危动作，授权以什么形式留存」**。

### 二、凭证四要素检查表（可直接用于方案评审）

评审任何「Agent 代替用户做高风险操作」的设计，缺任一项即为缺口：

- [ ] **授权内容**：授权的是哪个具体意图（最好绑定意图内容哈希，而非只绑动作类型）
- [ ] **额度或范围**：金额上限 / 可操作对象范围
- [ ] **时效**：单次？本会话？还是长期
- [ ] **责任主体**：出事找谁——用户、Agent 厂商、还是被调用 App

⚠️ **待核实**：APOP 是否真做到「意图内容与凭证绑定」，库内记录为**媒体报道口径、非一手规范**；协议全文链接待补；能否与 AppFunctions / App Intents 对接（还是必须走各自 SDK）**未见公开说明**。作为方法论上的检查表可用，作为技术选型依据**需先拿到规范原文**。

### 三、为什么这一层比"把确认做得更好"更重要

被 [[XPIA 跨提示注入]] / [[Agent Data Injection 数据注入攻击]] 污染的 Agent，**呈现给用户的确认文案本身就是攻击者写好的**——用户点了确认，确认的是攻击者的话。所以：

> **确认 UI 的产物应该是「数据」而不是「事件」。** 弹窗产出一份带意图内容哈希的凭证，即使 Agent 被劫持改单，凭证与实际请求不匹配即可在协议层拦截。

这也是本 SOP 步骤 5「验证确认层」的升级方向：从「有没有弹」升级为「**弹完留下了什么可核验的东西**」。三档成熟度判据见 [[Confirmation UI 安全机制]]（Agent 自组织 / 系统据元数据渲染 / **带外授权**）。

### 四、③ GUI 兜底的退出条件量化（内部约定，非外部标准）

步骤 4 要求「记录调用量与失败率」但没给阈值。建议内部先按下表约定，跑一个季度后再校准：

| 触发条件 | 处置 |
|---|---|
| 单任务月调用量进入 Top 20 **且** UI 改版导致失效 ≥ 2 次/季 | 升级为商务优先级，进入游说清单 |
| 风控拦截次数 > 0 | **立即下线**，不等季度复盘 |
| 连续两个季度调用量 < 阈值且无官方通道 | 直接砍掉，不再维护 |

⚠️ 上述阈值是**内部约定**，无外部依据，需用真实数据校准后固化。
