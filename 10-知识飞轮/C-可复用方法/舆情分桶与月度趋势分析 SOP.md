# 舆情分桶与月度趋势分析 SOP

> 配套模板：[[10-知识飞轮/_模板/舆情分析填写模板|舆情分析填写模板]]
> 相关笔记：[[01-笔记/PM决策层/用户研究方法 学习笔记|用户研究方法]]

适用场景：用户投诉、产品反馈、客服记录、应用评论、问卷开放题。

这是一套面向实际工作的操作方法。研究方法基础是“定性内容分析”，整理结构采用“层级编码”；下面的步骤、表格和月度判断规则是针对产品舆情整理的建议做法。

## 一、先用一个日常例子理解

想象你收到一堆写着用户意见的纸条，要把它们整理给产品和研发看。

第一遍，你按大方向分开：翻译质量、拍照翻译、语音翻译、软件打不开。

第二遍，你拿出“翻译质量”这一摞，发现用户说的其实是不同的事情：有人说品牌名变成另一个品牌，有人说动词被译成名词，有人说日期的月和日颠倒，还有人只写了“不准”。

于是，你在这摞纸条里面再分几个小格子。每个小格子装一类能说清楚的问题；细节不够的纸条留在“待补充”。

接下来，把每个小格子的纸条按月份排开。你就能看到：哪一类一直有人说，哪一类逐渐减少，哪一类很久没再出现，哪一类最近突然多了。

**这就是“分桶后继续分桶”的实际含义：把笼统抱怨，逐步整理成可以跟进的具体问题。**

它最终要回答三个问题：

1. 用户到底遇到了什么？
2. 同一个大类里，主要是哪几个具体问题？
3. 这些具体问题是在持续、缓解，还是可能已经消退？

## 二、记住三个词就够了

|词|通俗解释|例子|
|---|---|---|
|大桶|问题的大方向|译文质量|
|小桶|这个方向下的具体问题|品牌名称被译成另一个品牌|
|标签|描述问题发生的条件|日译中、拍照入口、某版本、9月|

大桶和小桶回答“出了什么问题”；标签回答“在什么情况下出现”。

例如，一条原声说某品牌被译成了另一个品牌，可以这样记录：

|项目|填写内容|
|---|---|
|大桶|译文质量|
|小桶|实体名称错译|
|进一步表现|品牌名称被替换成其他品牌|
|词语对象标签|专有名词—品牌名|
|入口标签|按原声填写；没说就记未知|
|语种标签|按原声填写；没说就记未知|
|证据|用户给出的原词、实际译文、截图或原声位置|

这里有一个容易混淆的地方：“专有名词”属于名词，“词义选错”描述错误表现。两者适合分别记录。这样既能查品牌词相关问题，也能统计实体错译有多少。

## 三、完整流程：七步做完一轮分析

### 第一步：把原声留住，把统计范围说清楚

先保存原始记录，再建立分析副本。每条记录保留来源、日期和一个稳定编号，方便以后回到原文核对。

开始前写清楚：

- 统计哪段时间，最后一个月是否完整。
- 包含哪些渠道，渠道是否中途新增或停止采集。
- 哪些记录是投诉，哪些是需求、咨询、好评或无关内容。
- 计数单位是原声记录、问题条目、事件线索，还是可识别的用户。

**不要默认“一条记录就是一个用户”。** 同一事件可能同时留下聊天记录、客服摘要和追问。没有可靠身份或关联信息时，保留原声数，并把疑似重复另做一套对照。

本步产物：一份可以追溯的原声清单，以及一段清楚的统计范围说明。

### 第二步：把一段话里的不同事情拆开

原声示意：“翻译结果不准，而且要等很久，另外我找不到历史记录。”

这段话至少包含三个问题：准确性、速度、历史记录查找。可以建立三个问题条目，并让它们共同关联同一条原声。

|原声编号|问题条目|用户实际说的事|
|---|---|---|
|R001|R001-1|翻译结果不准|
|R001|R001-2|等待时间长|
|R001|R001-3|历史记录找不到|

原声中的“找不到”还不能证明记录已丢失，也可能是入口难找。此时先保留用户描述，继续核对。

遇到“翻译很垃圾”这种简短评价，可以记录为负向评价或准确性待核对，不补写用户没提供的错词。

本步产物：原声和问题条目的对应关系。

### 第三步：先立大类，再从材料里长出小类

已有分类可以作为起点。随后逐条阅读，遇到已有分类容纳不了、且可以独立描述的问题，再新增小类。

以下是结构示意：

|大方向|具体问题|能进一步说清楚的表现|
|---|---|---|
|译文质量|实体错译|品牌名变成另一个品牌|
|译文质量|词性错配|动词被按名词处理|
|译文质量|数值错误|金额或数量级发生变化|
|译文质量|语境选义不当|选了一个合法词义，但不适合当前句子|
|拍照翻译|文字识别错误|图片中的字先被识别错了|
|拍照翻译|没有译文|能进入扫描，但没有翻译结果|
|拍照翻译|调用异常|选择图片后跳回、转圈或退出|

建议先用两到三层，层数根据需要决定。小类达到下面三个条件，就可以停止往下拆：

1. 能用一句话说清用户遇到什么。
2. 能找到对应原声或证据。
3. 能提出有针对性的核对或验证动作。

只有一条但影响严重的问题也可以独立保留，标注“小样本”。拆分的依据是问题是否不同，不只看数量。

本步产物：一棵问题分类树。

### 第四步：给每个桶写一张“收纳说明”

这张说明正式叫“编码本”或“分类字典”。它的作用是让不同的人、不同月份按照相同规则分类。

每个桶至少写清五件事：

|内容|示例：品牌实体错译|
|---|---|
|这个桶是什么|原输入指向某品牌，译文却指向另一个品牌|
|什么情况收进来|用户给出了原品牌和实际错误输出，或原文明确描述品牌替换|
|什么情况放别处|只有发音不对；原图先被识别成另一个词；用户只称“不准”|
|典型例子|原品牌A，实际译文为品牌B（流程示意）|
|证据不足怎么办|登记“实体翻译待核对”，补原文、译文或截图|

如果后续调整了分类，记录调整原因，并对相关历史月份采用相同规则重新归类。否则，分类口径变化也可能造成“投诉下降”的假象。

本步产物：有版本记录的分类字典。

### 第五步：给问题补条件，并区分事实与推测

建议保留的条件标签：

- 词语对象：普通名词、专有名词、动词、数词、短语、句子等。
- 使用入口：手输文本、拍照、相册、全局翻译、同传等。
- 语言方向：源语种和目标语种。
- 设备条件：机型、系统版本、应用版本、网络。
- 问题性质：故障、能力需求、使用咨询，或需要核对。

标签没有信息时就填“未知”。例如damage在不同句子里可以作名词或动词，只有这个单词时，词性先记“需上下文”。

同时，把判断分成三层：

|判断层次|可以怎么写|
|---|---|
|用户明确说了什么|“选择照片后一直转圈”|
|从描述可以初步定位什么|“图片翻译调用未完成，具体阶段待核”|
|需要日志或复现才能确定什么|“是否因接口超时、图片处理或客户端异常导致”|

分桶阶段主要整理前两层。技术根因保留为待验证项，避免猜测改变分类。

本步产物：带条件标签、证据位置和判断边界的问题清单。

### 第六步：先试分，再统计

全量处理之前，先拿一批原声试分。样本应覆盖不同月份、渠道、大桶、短反馈和多问题反馈。

有两位分析者时，可以分别分类，再讨论分歧；一个人处理时，也可以隔一段时间重新抽看一批，检查自己的规则是否一致。

优先检查：

- 同样的问题是否被放进了不同桶。
- 一个桶里是否混进了不同故障。
- 是否仅凭关键词就误判，例如“好了”实际指日志上传成功。
- 一条原声有多个问题时，是否漏掉了其中一项。
- 截图或原句缺失时，是否仍然做出了过细判断。

主分类的计数规则可以选一种，选定后保持一致：

|做法|适合什么情况|如何计数|
|---|---|---|
|拆问题条目后分类|原声经常包含几件不同的事|一个问题条目一个主分类；原声数另外去重统计|
|每桶内选一个主方面，另留副标签|需要让桶内各子类数量相加等于桶总量|写明主方面的判定顺序；其他问题用副标签保留|

本步产物：校准后的分类结果、数量统计和待核对清单。

### 第七步：按“小桶”看月度，再判断“大桶”

一个大桶可能同时包含已经消退的异常和持续存在的需求。因此先看每个具体问题，再汇总大类结论。

每个问题至少看四组信息：

1. **月度数量**：有没有连续下降、连续沉寂、反弹或首次出现。
2. **反馈占比**：该问题占当月全部有效痛点的多少。
3. **重复记录对照**：疑似同事件合并后，趋势是否仍然成立。
4. **前后原声内容**：后期用户是否还在说同一个具体问题。

一个数值示意：某问题从20条降到10条，但全部痛点从400条降到100条。它的反馈占比从5%变成10%。可以说该问题原声变少，同时在当前反馈中更突出；仅凭绝对数下降，无法确定产品体验改善。

如果最后一个月只有12天，就单列这12天的实际数、日均和反馈占比。不要把不完整月的绝对数直接与完整月比较，作为改善依据。

本步产物：每个具体问题的月度趋势和状态预估。

## 四、月度预估统一怎么写

以下为工作中的判断口径，不是经过校准的修复概率模型。

|状态|什么情况下使用|建议表述|
|---|---|---|
|持续存在|近月仍有同类具体反馈，趋势没有稳定下降|“该问题仍在持续暴露”|
|明显缓解|多个完整月下降，反馈占比和重复合并口径也支持下降|“高频问题明显减少，仍有残留”|
|疑似消退|此前有一定量反馈，随后连续多个完整月没有同类描述，且已检查跨桶迁移和采集变化|“从月度数据看，该具体问题可能已消退”|
|近期回升或新增|低月后再增加，或此前未出现而近期集中出现|“近期重新暴露／出现新的反馈”|
|无法判断|样本太少、时间太短、信息不足，或采集方式明显变化|“暂不足以估计解决状态”|
|已确认解决|有明确的修复或交付信息，并在相应版本、机型和场景完成验证|“已在所列范围验证解决，其他范围另行核对”|

可以先把“连续三个完整月未再出现”设为筛选消退候选的工作起点，再根据样本量、使用频率和渠道稳定性调整。这个月数是可调整的工作规则，不能单独触发“已确认解决”。

对需求另换一种措辞：

- 用户不再提某功能，写“需求热度下降”。
- 有上线信息但未测，写“已交付，待验证”。
- 用户目标场景已经验证可用，写“该场景需求已满足”。

“新增罗马音”和“假名注音消失”应分别观察。前者是能力需求，后者是已有体验回退；两者共用一个大桶，也不能共用一个解决结论。

## 五、每个桶最终交付一张说明卡

每张卡包含以下内容，让读者能判断问题、证据和下一步：

1. **一句话概括**：用户在什么场景，遇到什么不符合预期的现象。
2. **桶内拆分**：有哪些具体方面，各有多少条，计数单位是什么。
3. **代表原声**：原文、日期、编号，以及可追溯位置。
4. **月度变化**：原声数量、反馈占比、重复合并对照及内容变化。
5. **状态预估**：持续、缓解、疑似消退、回升、新增或无法判断，并说明理由。
6. **后续动作**：还要补什么证据，怎样验证，验证覆盖什么范围。

可直接使用的结论句式：

> 在【场景】下，用户主要遇到【具体问题】。本桶进一步拆为【方面A、B、C】，其中【方面A】占比较高。它从【起始月份】的【数量】变为【近期数量】，反馈占比【变化】，重复合并后【是否一致】。结合后期原声，预估为【状态】。当前仍有【残留或证据缺口】，下一步核对【动作】。

## 六、交付前的检查清单

- [ ] 每个结论能回到具体原声。
- [ ] 一条话里的不同问题已经保留。
- [ ] 同一层的分类使用相同划分依据。
- [ ] 分桶和条件标签已分开；缺失信息填写未知。
- [ ] 细节不足的反馈没有被强行指定词性或根因。
- [ ] 计数单位、去重方式、占比分母写清楚。
- [ ] 同桶子类是否可相加、是否允许多标签已经说明。
- [ ] 所有月份使用一致分类口径。
- [ ] 不完整月份单列；采集渠道变化已经检查。
- [ ] 已检查问题是否被移到了其他桶。
- [ ] 缺陷消退与需求热度下降分开表述。
- [ ] “可能消退”和“验证解决”分开记录。
- [ ] 小样本问题与高频问题的判断强度有所区分。
- [ ] 原始资料保持原样，分析结果单独保存。

## 七、可以写进汇报的简版方法说明

> 本分析以用户原声为依据，先将混合反馈拆成可独立描述的问题，再按统一分类规则建立大类与子类，并保留语种、入口、版本等条件标签。分类结果经过抽查校准后，分别统计各类问题的数量、占比和月度变化，同时对疑似重复事件进行对照。结合前后原声的具体内容，判断问题是在持续、缓解、疑似消退还是近期重新暴露。解决状态属于证据支持下的预估；有修复或交付信息并完成相应场景验证后，才记录为已确认解决。

## 方法依据与适用边界

ATLAS.ti官方说明了父类、子类及宽泛类别继续拆分的组织方式，也支持把暂时无法匹配的原文保留待定。本手册采用这一层级结构，具体流程和业务判断规则由本项目按需要组织。[父类与子类编码说明](https://atlastihelp.helpscoutdocs.com/article/617-how-to-use-and-organize-sub-codes-in-atlasti)

定性内容分析提供类别建立、分类定义、例证、编码规则及迭代修订的研究方法基础。可参阅Philipp Mayring的原著。[Qualitative Content Analysis：理论基础与操作程序](https://www.ssoar.info/ssoar/bitstream/handle/document/39517/ssoar-2014-mayring-Qualitative_content_analysis_theoretical_foundation.pdf)

这套方法能把“用户说了什么”整理得更清楚，并形成可复核的趋势判断。它提供的是问题线索、分类与跟进依据；确认具体技术根因仍需要相应的原图、输入输出、日志或复现结果。
